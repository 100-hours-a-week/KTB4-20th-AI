# Grill: Semantic ID 생성 모델로 ADR-0000 규칙 선정을 대체
Date: 2026-10-14

## Intent
일정 추천에 필요한 장소를 규칙이 아니라 학습된 모델이 추론해 제공한다. 정형 데이터에는 LLM이 맞지 않으므로 LLM이 아니라 어텐션 기반 추천 모델을 쓴다. 가능한 한 규칙으로 채우는 부분은 최후순위로 둔다("AI를 온전히 활용"). 이 작업은 학습자가 AI 개발자 취업을 준비하는 프로젝트이기도 해서, GPU 서빙과 트래픽 확장 경험이 목표에 포함된다.

## Constraints
- 후보는 `ai_places`(서버·로컬 동일, 10,165건)에서 가져오며 DB에 없는 장소는 생성하지 않는다.
- 후보 하한(하드 필터): 영업 중(`OPERATIONAL`), 평점 3.0 초과, 평가 수 10 이상. 이 필터 적용 후에도 7,680건 조합 테스트가 모두 통과했다.
- 서비스 지역은 서울·부산·경주·전주·제주 5곳이며, 서비스 지역 밖(경기 등) 로그는 v1 학습에서 제외한다.
- 서비스 사용자 설문 응답 데이터와 행동 로그는 없다. 학습은 AI-Hub 국내 여행로그로 대신한다. 사용자 수는 100명 내외에서 시작하지만 중견·대기업 수준의 트래픽까지 단계적으로 확장하는 계획을 전제로 한다.
- 결과는 4개 invariant(5~6개, 2·5번째 FOOD, 회피 type 없음, 장소 중복 없음)를 통과해야 한다.
- 같은 입력에는 같은 결과(결정론). 단, 모델·후보 DB 버전이 같다는 조건에서다.
- 서버: 호스트 2 vCPU, 메모리 3.8GB(여유 약 2.5GB), 컨테이너 메모리 제한은 백엔드 1g·프론트 128m·AI 서버 없음. 백엔드 → AI 서버 타임아웃은 연결 3초, 읽기 30초.
- GPU는 RunPod를 쓴다. 학습은 Pod를 일시적으로 켜고, 서빙은 Serverless이며 VLM(Qwen2.5-VL-7B)과는 별도 엔드포인트다. GPU 비용은 지원되므로 소프트웨어 관점만 본다.
- 서빙은 모델 학습과 평가를 끝낸 뒤 진행한다.

## Key decisions
- Decision: ADR-0000을 대체할 새 ADR을 쓴다(ADR-0003). 대체는 평가 통과 후 확정한다. Reason: ADR-0000이 새 ADR 선행을 요구하고, 대체의 근거를 평가로 보이는 것이 설계 취지다. Alternative considered: 규칙 + LLM 보완(ADR-0000에서 기각).
- Decision: 아이템은 Semantic ID로 표현한다. 임베딩(오픈 모델) → RQ-VAE(3단계 × 256, 충돌 시 구분 코드) 구조이고 양자화기는 DB 장소만으로 학습한다. Reason: 로그 방문지와 DB 장소의 ID 대응이 17.5~34%에 그친다. Alternative considered: ID 임베딩(NAIS/FIAN).
- Decision: 임베딩 모델은 오픈 모델로 한다(Gemini 결제 취소). 1순위 비교는 Qwen3-Embedding-0.6B(Apache 2.0 확인)와 BGE-M3(MIT는 기억 기준, 확인 필요)이고, 정렬 검증 지표로 확정한다. EmbeddingGemma-300M(Gemma 라이선스)은 후보다. jina-embeddings-v3는 라이선스 불확실로 제외한다.
- Decision: 임베딩 입력 텍스트는 정규화한 이름 + 시도·시군구이고 카테고리 라벨은 넣지 않는다(2026-10-16 확정). Reason: 정답 쌍의 32%에서 한쪽에만 라벨이 있거나 구성이 달라 코드 일치율이 1~4%이고, 라벨을 넣으면 첫 코드 일치율이 15%p 안팎 떨어지며 검색 성공률은 달라지지 않는다. 카테고리는 디코딩 후보 제한에서 DB 값으로 쓴다. Alternative considered: 라벨을 넣는 안(ADR-0003 대안 6). 띄어쓰기 제거는 별개의 개선안으로 두고 효과를 재 본 뒤 도입 여부를 정한다.
- Decision: 생성 모델은 소형 트랜스포머를 처음부터 학습한다(사전학습 백본 사용 안 함). Reason: TIGER가 약 1,300만 파라미터 모델을 처음부터 학습한 선례가 있다. 단, 학습 규모가 선례보다 작다는 위험이 있다(아래 가정 참조).
- Decision: 입력은 시작 토큰, 취향 토큰(카테고리 4개의 0/1), 지역 토큰이다. 회피조건과 슬롯 제약은 입력이 아니라 디코딩 후보 제한이다. 첫 장소도 모델이 생성한다.
- Decision: 취향 입력의 학습 값은 여행 미션 코드(`TRAVEL_MISSION`)를 4개 카테고리로 매핑한 0/1이다. HISTORY_CULTURE {3, 6, 12, 13}, NATURE_HEALING {8, 10, 21, 27, 28}, ACTIVITY {2, 5, 7, 9, 11}, CONVENIENCE_SHOPPING {1, 23}. 미매핑 코드(4 시티투어, 22, 24, 25, 26)는 무시하고, 4개 카테고리가 모두 0인 여행은 학습에서 뺀다. FOOD 차원은 입력에서 제외한다. 서비스 입력은 그룹 점수(ADR-0002) 상위 2개를 1로 하고 동점은 고정 순서로 처리한다. 3단계 입력은 추가 실험으로 둔다.
- Decision: 정답 신호는 만족도·재방문 의향·추천 의향이 모두 4 이상인 방문이다. 시퀀스 단위는 하루(집·숙소 제외), 분할은 여행자 단위 70/15/15(학습/개발/최종)이며 최종용은 한 번만 본다.
- Decision: 평가 지표는 장소 단위 Recall(대응된 방문만), 코드 접두사 적중률(전체 방문), 카테고리 일치도, invariant 통과율, 연속 거리이다. 지역별 최종용이 100일 미만이면 판정 보류, 규칙 대비 비교는 같은 날에 대한 대응 비교와 신뢰구간으로 한다. 기준선은 규칙 파이프라인, 인기순, CatBoost 점별 회귀이다.
- Decision: 디코딩은 결정론 빔 서치이고 빔 폭은 개발용 데이터로 정한다. 샘플링은 "다른 일정 보기" 같은 기능이 생길 때 별도로 도입한다.
- Decision: 동선(좌표)은 v1에서 입력에 넣지 않고 격자 토큰도 쓰지 않는다. 연속 거리를 평가 지표로 두고 기준에 못 미치면 디코딩에 반경 제한을 추가한다.
- Decision: 정답에 부정 예시는 학습에 쓰지 않는다. 인기 편향은 평가(인기순 기준선, 고유 장소 수, 상위 장소 집중도)로 측정한다. NVIDIA 페르소나 증강은 v1에서 제외한다.
- Decision: 서빙은 RunPod Serverless GPU(별도 엔드포인트)와 컨테이너 내 CPU 경로를 모두 구현하고, 측정(콜드 스타트 포함) 후 기본 경로를 정한다. GPU 경로 실패 시 CPU 경로로 폴백한다. 코드 사전의 키는 `google_place_id`이고 재수집 후 절차는 수동이다.
- Decision: 요청 경로에서 외부 임베딩 API를 호출하지 않는다(ADR-0001 취지 유지).
- Decision: 한 장소가 두 카테고리에 속할 때 같은 장소가 두 슬롯에 나오던 버그를 이미 쓴 장소를 건너뛰는 방식으로 고쳤다(후보를 슬롯 수보다 5개 더 조회). 품질 필터와 함께 PR #70으로 머지되었다(2026-10-15).

## Surfaced assumptions
- `TRAVEL_ID`는 한 여행자가 기록한 여행 한 건이다. 동반자는 성별·연령대·관계만 있고 취향 점수나 방문 로그가 없다. 데이터의 "그룹"은 기록자 한 명의 시점이다.
- 개인 취향으로 학습한 모델이 그룹 점수(상위 2개 카테고리)를 입력해도 작동한다는 가정은 데이터에 그룹 취향 정보가 없어 직접 검증할 수 없다.
- 미션 코드가 참가자가 고른 선호인지 수집 과제로 주어진 것인지는 문서에서 확인하지 못했다. 5개 상한이 있는 선택형으로 보이는 정황만 있다.
- 전체 데이터에서 여행 14,400건과 여행자 14,400명이 1:1이라, 여행 단위 분할과 여행자 단위 분할의 결과는 같다(여행자 단위는 안전장치).
- 방문 데이터의 여행 16,000건 중 여행 메타(미션)가 있는 것은 14,400건이다. 메타가 없는 1,600건(10%)은 취향 벡터를 만들 수 없어 제외된다.
- 학습 가능한 규모: 세 값 4 이상 하루 시퀀스 29,050개 → 메타 있음 26,170개 → 매핑 카테고리 1개 이상 25,081개 → 서비스 5개 지역 12,870개(여행 5,828건). 시작 표시 포함 학습 문제는 서비스 지역만으로 45,146개이고, 서비스 지역 밖을 포함하면 78,056개다. 지역별 하루 수는 서울 3,403, 부산 1,071, 제주 7,237, 전주 505, 경주 654이다.
- 이 규모는 TIGER 논문의 가장 작은 데이터(Beauty 22,363명, 12,101개 아이템, 평균 시퀀스 8.87로 약 20만 상호작용 추정)의 약 4분의 1이다. 처음부터 학습이 과소·과적합이 되면 서비스 지역 밖 데이터를 지역 토큰과 함께 포함하는 방법이 있다.
- 로그 방문지와 DB 장소의 이름 일치는 서비스 지역 방문 64,336건 중 엄격 11,272건(17.52%), 완화 21,851건(33.96%)이다. 고유 (이름, 장소) 쌍은 엄격 1,273, 완화 2,146이다. 이름 유사도로 고른 쌍이어서 이름 기반 임베딩에 일치율이 유리하게 나올 수 있다. 정답 쌍은 엄격 기준만 쓴다.
- 서비스 지역 방문의 POI_ID는 24,330건(37.8%)에만 채워져 있다.
- 현재 규칙 파이프라인의 연속 장소 거리 중앙값은 서울 7.7km, 부산 7.6, 경주 5.9, 전주 3.0, 제주 25.6이고, 실제 로그는 0.9, 1.7, 1.1, 0.5, 6.0이다(무작위 쌍은 9.2, 10.3, 5.0, 2.4, 28.1).
- 서비스 지역 만족 방문 44,603건에서 상위 1% 이름(123개)이 방문의 32.3%를 차지하는 인기 편향이 있다.
- AI-Hub의 Validation은 별개 여행자 집단이 아니라 같은 여행의 방문 일부다. 합쳐야 여행이 온전해지고, 여행자 단위 분할이 누수를 막는다.
- `TRAVEL_STYL_1~8`은 1~7점 척도이고 정의서(카테고리정의서.xlsx)가 없어 의미를 확인하지 못했다. v1 모델 입력에는 쓰지 않는다.
- 로컬 DB와 서버 DB는 같은 상태다(10,165건, 컬럼 101개). 레포 CI용 덤프는 구버전(10,715건)이었으나 PR #70에서 서버와 같은 10,165건과 `business_status` 컬럼으로 갱신되었다(ai_places는 조회에 쓰는 10개 컬럼 + `business_status`, 레거시 테이블은 제외).
- DB 이름에 한글과 다른 언어가 섞인 경우가 있다(예: `카페 아래헌 / Cafe Arae-Heon / カフェアレホン`). 서버가 지운 것은 한글이 하나도 없는 이름뿐이다.

## Open questions
- 임베딩 모델 최종 선택(정렬 검증 지표 결과), 정렬 합격 기준의 수치(무작위 대비 상대 기준, 측정 후 확정).
- 상위 2개 규칙 적용 시의 동점 처리 순서(고정 우선순위 값).
- 서비스 설문 응답이 쌓이면 취향 변환 기준 재보정. 설문 응답 로깅 설계는 후속.
- 서비스 기본 서빙 경로, 상시 워커 사용 여부, 폴백 전환 타임아웃 수치, RunPod payload 제한과 호출 방식.
- 양자화기·모델 재학습 기준 수치.
- 학습 규모가 작을 때 서비스 지역 밖 데이터를 포함할지.
- 연속 거리 기준 미달 시 반경 제한 R의 값과 후보 부족 시 보충 규칙.
- 미션 코드의 선택/부여 여부 확인.

## Out of scope
- LLM 호출로 장소를 선정하거나 설명을 생성하는 것.
- Google Places 실시간 호출을 요청 경로에 추가하는 것(ADR-0001 유지).
- NVIDIA 페르소나 증강(v1 제외, 후속 검토).
- 서비스 사용자 행동 로그 수집 설계(추후 도입 계획).
- 위치 격자 토큰(v1 제외), 3단계 취향 입력(추가 실험).
