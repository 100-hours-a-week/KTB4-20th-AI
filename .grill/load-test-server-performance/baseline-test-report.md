## 1. 요약

**결론**
- Max workers 1 조건에서 개선 구조 1(plan0·plan1·plan2를 스레드 3개로 동시 실행)의 warm 응답 시간은 baseline(한 스레드 순차 실행)과 같은 수준
- Max workers 1 조건에서 처리 속도 개선이 관측되지 않았고, 스레드와 DB 연결 사용량만 증가
- 개선 구조 2(place-selection 동시 처리 한도 16, 초과 시 즉시 503): 처리되는 요청의 warm 응답 시간은 baseline과 같은 수준. 동시 18건에서 반복마다 16건은 처리(최대 42.62초), 2건은 0.02~0.04초에 503으로 거절
- 개선 구조 3(place-selection 요청을 줄 세워 한 번에 하나씩 처리, 줄 상한 9): 동시 요청을 도착 순서대로 한 번에 하나씩 처리하고, 줄이 가득 차면(9건) 즉시 503, 줄에서 55초를 넘게 기다리면 줄에서 빼고 503. 동시 12건 측정에서 반복마다 9건은 도착 순서대로 처리(첫 요청 2.51·2.91초, 9번째 요청 24.07·25.51초), 3건은 0.01초에 503으로 거절. 줄 상한은 지금까지 측정한 최대값(콜드 스타트 21.48초, 요청당 서비스 시간 3.65초) 기준으로 9로 설정(9번째 요청이 21.48 + 9 × 3.65 = 54.3초에 끝남, 계산)
- 개선 구조 4(개선 구조 3의 줄 상한을 9에서 15로 변경): 서비스 시간 최대값 3.65초만으로 계산한 상한(55 ÷ 3.65 = 15.07 → 15). 콜드 스타트는 계산에 넣지 않음. 동시 18건 측정에서 반복마다 15건은 도착 순서대로 처리(15번째 요청 41.17초와 46.34초), 3건은 0.01초에 503. 콜드 스타트와 겹칠 때는 뒤쪽 요청이 55초를 기다린 뒤 503이 될 것으로 계산(미측정)

**구조별 핵심 값**
- baseline: warm N=1 중앙값 2.66초, warm N=2 실행 단위 중앙값 5.65초. 첫 요청 12건 중 7건이 plan1의 RunPod 55초 read timeout으로 HTTP 500
- 개선 구조 1: warm N=1 중앙값 2.66초, warm N=2 실행 단위 중앙값 5.40초. 첫 요청 5건 모두 성공(7.78~12.40초). 55초를 넘는 대기가 없어 실패 동작은 비교하지 못함
- 개선 구조 2: warm N=1 중앙값 3.40초, warm N=2 실행 단위 중앙값 5.53초 (둘 다 한도 16 미만이라 한도 영향 없음). 한도 동작은 동시 18건 실행(측정 19)에서 확인
- 개선 구조 3: 줄 상한 9, 대기 상한 55초. 동시 12건에서 처리된 9건의 응답 시간은 2.51~25.51초(요청이 약 2.7~2.8초 간격으로 끝남), 503은 0.01초. 9번째 요청의 완료 시각은 평상시 계산(콜드 스타트 없음, 요청당 2.67초: 측정 13)의 24.0초와 맞고 최대값 기준 계산 54.3초보다 짧음. 콜드 스타트와 겹칠 때의 동작은 측정하지 않음
- 개선 구조 4: 줄 상한 15, 대기 상한 55초. 동시 18건에서 처리된 15건의 응답 시간은 2.66~46.34초(요청이 약 2.45~2.92초 간격으로 끝남), 503은 0.01초. 대기 상한 55초까지 여유 8.7초와 13.8초(15번째 요청 기준). 콜드 스타트와 겹칠 때의 동작은 측정하지 않음
- RunPod 실행 시간(Execution): 모든 측정에서 0.2~0.4초. 지연 구간은 모델 실행이 아니라 요청이 워커에 닿기까지의 대기(cold start, Throttled, 큐 대기)
- DB 연결 오류: 두 구조 모두 0건. 10/28 DB 풀 문제는 이번 측정으로 재현도 반박도 불가

**확인하지 못함**
- 호출 하나가 워커를 약 1.3초 점유하는데 Execution이 약 0.25초인 이유
- 첫 요청 대기가 9초에서 225초까지 변하는 이유
- 모든 측정에서 실행 직전 Worker states (기록 규칙 미이행)
- 콜드 스타트와 겹칠 때 줄의 실제 동작, 서버 로그의 줄 WARNING 횟수

## 2. 목적과 범위

- 목적: 가장 단순한 baseline에서 동시 요청 처리 방식을 측정하고, 개선 구조와 같은 방법으로 비교
- 범위: N=1과 N=2만 실행 (질문 12에서 5 이상 제외). 로컬 환경 측정이며 ECS 배포 환경과 BE 경유 흐름은 제외
- 가정: ECS Task 1개(0.5 vCPU, 메모리 1GB)에 해당하는 단일 uvicorn 프로세스 1개

## 3. 대상 구조와 측정 환경

**공통 구조** (코드 기준)
- DB: 커넥션 풀 없음. `get_connection()`이 호출마다 새 연결을 엶
- 실패 처리: 예외를 그대로 전파해 HTTP 500 반환. 폴백과 서킷 브레이커 없음. GPU 경로 실패 시 `InferenceUnavailable` 발생
- RunPod 호출 timeout: 55초 (코드 변경 없음)
- 서버: 이벤트 루프 → 스레드풀(anyio 기본 한도 40) → 요청당 스레드 1개. 핸들러는 동기 `def`
- 코드 검증: baseline·개선 구조 1은 `uv run pytest` 773건 통과·1건 건너뜀, 개선 구조 2는 775건 통과·1건 건너뜀, 개선 구조 3은 780건 통과·1건 건너뜀, `uv run ruff check` 통과. 개선 구조 4도 780건 통과·1건 건너뜀(줄 관련 21건 포함), `ruff` 통과 (사용자 실행)

**구조별 차이**
- baseline: 한 요청 안에서 plan0(규칙) → plan1(모델) → plan2(모델)를 한 스레드에서 차례로 실행. 요청 1건당 DB 연결 10회 열고 닫음 (로컬 계측)
- 개선 구조 1: plan0·plan1·plan2를 `ThreadPoolExecutor(max_workers=3)`로 스레드 3개에서 동시에 시작하고 셋이 모두 끝나면 응답. `async def` 전환 아님. 한 안이 실패해도 나머지 안은 이미 시작했으므로 끝날 때까지 기다린 뒤 예외 발생
- 개선 구조 2: baseline 코드에 place-selection 동시 처리 한도를 추가. `place_selection_max_concurrency`(기본 16, 계산 근거는 7.5절)를 넘는 요청은 기다리지 않고 즉시 HTTP 503(`동시 처리 한도를 넘었음`)을 반환하고 WARNING 로그를 남김. 슬롯은 성공·실패 모두 반환. plan 실행 구조는 baseline과 동일. 한도는 프로세스 단위(ECS Task 1개 가정). 이후 개선 구조 3으로 코드가 교체됨(개선 구조 2 코드는 커밋 `a1991e2`에 있음)
- 개선 구조 3: 개선 구조 2의 동시 처리 한도를 줄 세우기로 교체. `FifoGate`(`app/trips/fifo_gate.py`)가 요청을 도착한 순서대로 줄 세워 요청 전체(plan0~plan2)를 한 번에 하나씩 처리. 줄(처리 중 1건 + 대기 중)이 `place_selection_queue_capacity`(기본 9)에 차 있으면 기다리지 않고 즉시 HTTP 503(`줄이 가득 차서 처리할 수 없음`), 줄에서 `place_selection_queue_max_wait_seconds`(기본 55초)를 넘게 기다리면 줄에서 빼고 503(`줄에서 기다린 시간이 상한을 넘었음`). 처리가 끝나거나 실패하면 다음 요청에 차례를 넘김. 기다리는 요청도 스레드풀 스레드 1개를 점유(최대 9개, 상한 40 이내). 줄은 프로세스 단위(ECS Task 1개 가정)
- 개선 구조 4: 개선 구조 3의 줄 세우기 코드는 그대로 두고 `place_selection_queue_capacity` 기본값만 9에서 15로 변경(`app/core/config.py`). 대기 상한 55초와 503 동작은 동일. 개선 구조 3의 측정(측정 21)은 상한 9에서 했으므로 그 기록은 그대로 둠

**공통 측정 환경**
- 로컬 PC, 로컬 DB, 로컬 단일 uvicorn, RunPod Serverless 실호출
- 도구: k6. 가상 사용자 1명이 반복마다 `http.batch`로 CONC건을 동시에 보내고, 끝나면 바로 다음 반복 시작 (`k6/place_selection.js`). baseline 측정 1~3은 `per-vu-iterations`로 요청 1건씩. 3일 일정, k6 timeout 130초. 첫 반복(iter 0)은 예열
- 반복 측정 명령 (레포 안 `.grill/load-test-server-performance/k6` 폴더): `k6 run -e CONC=1 -e ITER=6 -e TOKEN="$TOKEN" place_selection.js`, N=2는 `CONC=2`, `ITER=7`
- 서버 실행 명령 (레포 루트): `.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000`. 배포 `Dockerfile` 20행과 같은 방식
- RunPod 엔드포인트 설정 (스크린샷 확인): Max workers 1, Active workers 0, GPU count 1, 선택 GPU 16GB 1종, Worker priority Availability, FlashBoot 꺼짐, Execution timeout 체크됨(초 값 미확인), Idle timeout 초 값 미확인 (RunPod 문서 기본값: 콘솔 5초, REST v2 10초)
- 측정 14부터 k6 스크립트는 `batch`·`batchPerHost`를 `CONC`로 올려 CONC건을 모두 동시에 보냄(커밋 `53e75f2`). k6 기본값(`batchPerHost` 6)에서는 `CONC` 20이어도 동시 요청이 6개였음. 이전 측정(CONC 1~2)은 6 이하라 영향 없음
- 측정 중 코드와 RunPod 설정 변경 없음

### 4.7 평가

- baseline
  - 워커가 떠 있을 때 N=1 약 2.7초, N=2 약 5.3~5.7초로 안정적으로 성공
  - 워커가 내려간 뒤 첫 요청은 대기 시간이 9초에서 225초까지 변동. 대기가 55초를 넘으면 요청 전체 실패 (7건 모두 plan1 RunPod ReadTimeout)
  - 이 실패는 워커 준비 대기가 사용자 실패로 직결되는 구조에서 발생
- 개선 구조 1
  - Max workers 1 조건에서 처리 속도 개선이 관측되지 않았고, 스레드와 DB 연결 사용량만 증가
- 개선 구조 2
  - 한도(16)를 넘는 요청은 기다리지 않고 즉시 503으로 거절. 동시 18건 실행에서 반복마다 2건을 0.02~0.04초에 거절하고 16건은 정상 처리(최대 42.62초)
  - 처리되는 요청의 warm 응답 시간은 baseline과 같은 수준 (N=2 실행 단위 5.53초 대 5.65초). N=1 3.40초는 baseline보다 높으나 원인 미확인
  - 용량을 늘리지 않음. 한도를 넘는 요청이 RunPod 호출 타임아웃(55초)까지 기다리다 실패하는 것을 막음
  - 한도 16은 사용자 결정 값 (계산 근거는 7.5절)
- 개선 구조 3
  - 동시 12건 실행(줄 상한 9)에서 반복마다 9건을 도착 순서대로 한 번에 하나씩 처리(요청이 약 2.7~2.8초 간격으로 끝남)하고 3건은 0.01초에 503으로 거절. 500과 대기 시간 초과 503은 없음. 9번째 요청이 24.07초와 25.51초에 끝나 최대값 기준 계산 54.3초보다 짧고 대기 상한 55초까지 약 29.5초의 여유
  - 용량을 늘리지 않음. 처리량은 RunPod 워커 1개가 정함
  - 줄 상한 9와 대기 상한 55초는 계산 값 (9 = floor((55 − 21.48) ÷ 3.65) = 9.18 → 9. 입력은 지금까지 측정한 최대값: 콜드 스타트 21.48초는 측정 1, 서비스 시간 3.65초는 측정 14의 단독 요청 응답 시간. 9번째 요청이 21.48 + 9 × 3.65 = 54.3초에 끝나고 10번째는 58.0초. 55 = 60 − 2.7 − 2)
  - 남은 위험: 측정한 최대값을 넘으면 줄 뒤쪽 요청이 55초를 기다린 뒤 503 (늦은 실패), 기다리던 요청의 클라이언트가 연결을 끊어도 서버가 처리할 가능성(미확인), ECS Task가 여러 개면 Task마다 줄이 따로 생김. 8.4절 참조
- 개선 구조 4
  - 동시 18건 실행(줄 상한 15)에서 반복마다 15건을 도착 순서대로 한 번에 하나씩 처리(요청이 약 2.45~2.92초 간격으로 끝남)하고 3건은 0.01초에 503으로 거절. 500과 대기 시간 초과 503은 없음. 15번째 요청이 41.17초와 46.34초에 끝나 대기 상한 55초까지 13.8초와 8.7초의 여유
  - 줄 상한 15는 계산 값 (15 = floor(55 ÷ 3.65) = 15.07 → 15. 입력은 서비스 시간 최대값 3.65초 하나. 15번째 요청 15 × 3.65 = 54.75초, 16번째 58.4초). 개선 구조 3과 달리 콜드 스타트 21.48초를 계산에 넣지 않음
  - warm일 때 처리 건수가 9건에서 15건으로 늘어남(15건은 측정 23에서 확인). 콜드 스타트와 겹치면 뒤쪽 요청이 줄에서 55초를 기다린 뒤 503이 됨 (계산, 미측정). 9장 참조

  - 개선 구조 1의 DB 연결: 요청당 최대 3개 (동시 N건이면 최대 3N개)
