# AI 서버 부하 테스트 보고서 (baseline과 개선 구조)

- 작성일: 2026-11-06, 개선 구조 1 추가와 구성 변경: 2026-11-07 (시각은 모두 KST)
- 대상: AI 서버 `POST /trips/place-selection`, 브랜치 `perf/load-test-server-tuning` (baseline은 커밋 `4fca88d`, 개선 구조 1은 커밋 `6150791`)
- 양식: IEEE 829 테스트 요약 보고서의 요약·편차·평가 구성을 참고한 내부 양식. 표준을 그대로 따르지 않음
- 용도: 구조별 측정 결과 기록과 비교. 구조 추가 시 6장 뒤에 같은 소제목의 장을 더하고 4장 표에 열을 추가
- 구성: 1~4장은 결론과 비교, 5장 이후는 구조별 상세. 비교 값만 볼 때는 1장과 4장 참조
- 관련 기록: grill 질문·답변은 `summary.md`, 구조 그림은 `architecture-baseline.png`·`architecture-improved.png`, 측정 도구는 `k6/`

## 1. 요약

**결론**
- Max workers 1 조건에서 개선 구조 1(plan0·plan1·plan2를 스레드 3개로 동시 실행)의 warm 응답 시간은 baseline(한 스레드 순차 실행)과 같은 수준
- Max workers 1 조건에서 처리 속도 개선이 관측되지 않았고, 스레드와 DB 연결 사용량만 증가

**구조별 핵심 값**
- baseline: warm N=1 중앙값 2.66초, warm N=2 실행 단위 중앙값 5.65초. 첫 요청 12건 중 7건이 plan1의 RunPod 55초 read timeout으로 HTTP 500
- 개선 구조 1: warm N=1 중앙값 2.66초, warm N=2 실행 단위 중앙값 5.40초. 첫 요청 5건 모두 성공(7.78~12.40초). 55초를 넘는 대기가 없어 실패 동작은 비교하지 못함
- RunPod 실행 시간(Execution): 모든 측정에서 0.2~0.4초. 지연 구간은 모델 실행이 아니라 요청이 워커에 닿기까지의 대기(cold start, Throttled, 큐 대기)
- DB 연결 오류: 두 구조 모두 0건. 10/28 DB 풀 문제는 이번 측정으로 재현도 반박도 불가

**확인하지 못함**
- 호출 하나가 워커를 약 1.3초 점유하는데 Execution이 약 0.25초인 이유
- 첫 요청 대기가 9초에서 225초까지 변하는 이유
- 모든 측정에서 실행 직전 Worker states (기록 규칙 미이행)

## 2. 목적과 범위

- 목적: 가장 단순한 baseline에서 동시 요청 처리 방식을 측정하고, 개선 구조와 같은 방법으로 비교
- 범위: N=1과 N=2만 실행 (질문 12에서 5 이상 제외). 로컬 환경 측정이며 ECS 배포 환경과 BE 경유 흐름은 제외
- 가정: ECS Task 1개(0.5 vCPU, 메모리 1GB)에 해당하는 단일 uvicorn 프로세스 1개

## 3. 대상 구조와 측정 환경

**공통 구조** (코드 기준)
- DB: 커넥션 풀 없음. `get_connection()`이 호출마다 새 연결을 엶
- 실패 처리: 오류를 그대로 올려 HTTP 500 반환. 폴백과 서킷 브레이커 없음. GPU 경로 실패 시 `InferenceUnavailable` 발생
- RunPod 호출 timeout: 55초 (코드 변경 없음)
- 서버: 이벤트 루프 → 스레드풀(anyio 기본 한도 40) → 요청당 스레드 1개. 핸들러는 동기 `def`
- 코드 검증 (두 구조 모두): `uv run pytest` 773건 통과·1건 건너뜀, `uv run ruff check` 통과

**구조별 차이**
- baseline: 한 요청 안에서 plan0(규칙) → plan1(모델) → plan2(모델)를 한 스레드에서 차례로 실행. 요청 1건당 DB 연결 10회 열고 닫음 (로컬 계측)
- 개선 구조 1: plan0·plan1·plan2를 `ThreadPoolExecutor(max_workers=3)`로 스레드 3개에서 동시에 시작하고 셋이 모두 끝나면 응답. `async def` 전환 아님. 한 안이 실패해도 나머지 안은 이미 시작했으므로 끝날 때까지 기다린 뒤 예외 발생

**공통 측정 환경**
- 로컬 PC, 로컬 DB, 로컬 단일 uvicorn, RunPod Serverless 실호출
- 도구: k6. 가상 사용자 1명이 반복마다 `http.batch`로 CONC건을 동시에 보내고, 끝나면 바로 다음 반복 시작 (`k6/place_selection.js`). baseline 측정 1~3은 `per-vu-iterations`로 요청 1건씩. 3일 일정, k6 timeout 130초. 첫 반복(iter 0)은 예열
- 반복 측정 명령 (레포 안 `.grill/load-test-server-performance/k6` 폴더): `k6 run -e CONC=1 -e ITER=6 -e TOKEN="$TOKEN" place_selection.js`, N=2는 `CONC=2`, `ITER=7`
- 서버 실행 명령 (레포 루트): `.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000`. 배포 `Dockerfile` 20행과 같은 방식
- RunPod 엔드포인트 설정 (스크린샷 확인): Max workers 1, Active workers 0, GPU count 1, 선택 GPU 16GB 1종, Worker priority Availability, FlashBoot 꺼짐, Execution timeout 체크됨(초 값 미확인), Idle timeout 초 값 미확인 (RunPod 문서 기본값: 콘솔 5초, REST v2 10초)
- 측정 중 코드와 RunPod 설정 변경 없음

## 4. 비교

값의 상세와 출처는 5장(baseline)과 6장(개선 구조 1) 참조. 집계 규칙은 공통: 성공한 응답 시간의 중앙값과 범위를 기록하고, 실패는 응답 시간에서 제외한 뒤 실패 지점을 집계

### 4.1 warm 응답 시간

| 항목 | baseline | 개선 구조 1 |
|---|---|---|
| N=1 성공 | 5/5 | 5/5 |
| N=1 중앙값(범위) | 2.66초 (2.58~2.79) | 2.66초 (2.56~2.83) |
| N=2 성공(요청 단위) | 10/10 | 10/10 |
| N=2 요청 단위 중앙값(범위) | 5.33초 (3.99~8.55) | 4.81초 (3.93~5.63) |
| N=2 실행 단위(느린 쪽) 중앙값(범위) | 5.65초 (5.30~8.55) | 5.40초 (5.28~5.63) |
| 참고: baseline 측정 7·8의 N=2 실행 단위 중앙값 | 5.34초, 5.395초 (예열 실패로 4회씩) | - |

- baseline 측정 9의 최댓값 8.55초가 개선 구조에서는 미발생. 각 1회 측정이라 구조 차이로 단정하지 않음

### 4.2 첫 요청 (워커가 내려간 뒤, cold 포함)

| 항목 | baseline | 개선 구조 1 |
|---|---|---|
| 첫 요청 수 | 12건 (실행 8번) | 5건 (실행 3번) |
| 성공 / 실패 | 5건 / 7건 | 5건 / 0건 |
| 성공한 첫 요청의 응답 시간 | 9.40~25.57초 | 7.78~12.40초 |
| 실패 지점 | 7건 모두 plan1의 RunPod 호출이 55초 read timeout → HTTP 500 | 없음 |
| 실행 직전 Worker states | 기록하지 못함 | 기록하지 못함 |

- 개선 구조는 55초를 넘는 대기가 없어 대기가 긴 경우의 동작 비교 불가
- 두 구조 모두 워커 상태가 통제되지 않아 같은 조건의 비교로 보기 어려움

### 4.3 RunPod 쪽 값

| 항목 | baseline | 개선 구조 1 |
|---|---|---|
| Execution | 0.2~0.4초 | 208~421ms |
| 워커 수 | Max workers 1 | 1개 (22:15~22:37에 1개 초과 없음) |
| 동시에 나간 호출의 Delay 변화 | 호출 묶음별로는 미확인. warm N=2의 Delay는 대부분 1.4~1.7초, 일부 93~722ms (일부 행만 확인) | 4건 묶음 안에서 앞 호출보다 약 1.0~1.4초씩 증가 (측정 12) |
| Throttled | 측정 2에서 관찰 (워커 상태 Throttled, "Waiting for GPU to become available") | 관찰하지 못함 (상태 미기록) |

### 4.4 평가

- baseline
  - 워커가 떠 있을 때 N=1 약 2.7초, N=2 약 5.3~5.7초로 안정적으로 성공
  - 워커가 내려간 뒤 첫 요청은 대기 시간이 9초에서 225초까지 변동. 대기가 55초를 넘으면 요청 전체 실패 (7건 모두 plan1 RunPod ReadTimeout)
  - 이 실패는 워커 준비 대기가 사용자 실패로 직결되는 구조에서 발생
- 개선 구조 1
  - Max workers 1 조건에서 처리 속도 개선이 관측되지 않았고, 스레드와 DB 연결 사용량만 증가
- 비용 측면 (코드 구조에서 읽은 값, 미측정)
  - DB 연결: 요청당 최대 3개 (동시 N건이면 최대 3N개)
  - 스레드: 요청당 최대 4개 (요청 처리 1 + plan 3)
  - 한 안이 실패해도 나머지 안의 RunPod 호출은 이미 발생
- 워커가 시작하지 못하는 대기(Throttled)는 서버 구조로 해결 불가. 서버 구조가 다룰 수 있는 범위는 대기 발생 시 사용자 응답 방식(타임아웃, 폴백, 실패 처리)과 warm 응답 시간

### 4.5 확인하지 못한 것

- Throttled가 baseline N=2 첫 요청 실패 3건 모두의 원인인지 여부 (측정 2 외에는 대기 구간의 Worker states 미확인)
- 호출 하나의 워커 점유 약 1.3초와 Execution 약 0.25초의 차이 원인
- 워커를 2개 이상으로 늘렸을 때 개선 구조의 효과 (미측정)
- 개선 구조에서 서버 쪽 시간(DB 조회, 계산)의 감소 여부 (별도 측정 없음)
- 로컬 환경 측정이라 클라우드 팀의 BE 경유 단일 흐름 15.48초와 직접 비교하지 않음

### 5.3 첫 요청 (cold 포함)

각 실행의 iter 0(예열)과 단발 측정의 응답 시간. 실행 직전 Worker states 미전달

- N=1: 25.57초 성공(측정 1, 00:30), 9.40초 성공(측정 3, 01:09), 55.93초 실패(측정 4, 13:13), 11.45초 성공(측정 6, 13:28) → 4번 중 성공 3번
- N=2: 55.56초 두 건 실패(측정 2, 00:33), 55.6초 두 건 실패(측정 7, 14:05), 55.61초 두 건 실패(측정 8, 17:31), 15.49초·16.84초 두 건 성공(측정 9, 17:54) → 4번 중 두 건 모두 실패 3번, 두 건 모두 성공 1번
- RunPod 대기(Delay, 대시보드 값)
  - 측정 2: 3분 45초, 3분 44초
  - 측정 7: 1분 28초, 1분 29초
  - 측정 9: 10.37초, 11.72초로 보이는 두 건 (요청 ID별 매핑 미확정)
  - 측정 1: cold start 21.48초 (Metrics 구간 값)
- 같은 실행의 두 요청은 항상 같은 결과 (같이 실패 또는 같이 성공)

### 5.4 실패 집계

- 로그로 확인한 500은 총 7건, 모두 같은 지점: plan1의 RunPod 호출이 read timeout 55초 초과 → `InferenceUnavailable("사용 가능한 추론 경로가 없음")` (`inference.py` 148행) → `model_trip(plan, "plan1", False)` (`trip_orchestrator.py` 91행)에서 올라와 HTTP 500 (줄 번호는 baseline 커밋 기준)
  - 측정 2: 2건, 측정 4: 1건, 측정 7: 2건, 측정 8: 2건
- plan0·plan2 실패와 DB 연결 오류(`TooManyConnectionsError` 등): 0건
- 7건 모두 각 실행의 첫 요청(예열). 워커가 떠 있는 동안 500 없음

### 5.5 분석

**관찰한 사실**
- RunPod 실행 시간(Execution): 모든 측정에서 0.2~0.4초
- warm 구간의 N=2 RunPod 요청 대부분은 Delay 1.4~1.7초, 일부 93~722ms (측정 7, 9의 Requests 탭, 일부 행만 확인)
- 측정 2의 워커 상태: 00:33 Throttled, 00:36 Running. 요청이 없던 00:43과 00:45~00:48에도 Throttled. 워커 설정 화면에 "Waiting for GPU to become available" 표시
- 서버 로그: 측정 4~9의 요청이 k6 결과와 같은 건수로 기록

**계산** (실측 아님)
- 측정 2: 225초 − cold start 6.25초 = 약 218.8초가 cold start 앞의 대기. 이 구간에서 워커는 Throttled
- 측정 3: 9.40초 − RunPod 구간 합 7.53초 = 약 1.87초가 RunPod 밖에서 소요
- warm N=1의 2.66초는 RunPod 밖 약 1.87초(측정 3 값)와 RunPod 구간 약 0.8초의 합과 규모가 맞음. 서로 다른 측정 값을 섞은 추정

**추정** (근거는 있으나 미확인)
- 첫 요청의 긴 대기는 워커 시작 불가가 원인. RunPod 문서의 Throttled 정의: 호스트의 GPU가 다른 워크로드에 쓰여 워커가 지금 시작하지 못하는 상태, 과금 없음 (부록 B). 측정 2의 약 219초 대기가 해당한다고 판단

**확인하지 못한 것**

### 6.5 분석

**관찰한 사실**
- warm 응답 시간: N=1은 baseline과 동일, N=2는 같은 수준
- RunPod 호출 4개(요청 2건 × plan1·plan2)가 거의 동시에 나갔을 때 워커는 1개, 묶음 안 Delay가 호출마다 증가
- N=2의 같은 반복에서 두 요청이 4.05초와 5.40초처럼 따로 종료. 차이 1.35초는 Delay 증가분 약 1.3초와 규모 일치. 먼저 끝나는 요청은 반복마다 달랐음

**계산**
- Delay 증가분(앞 호출 대비): iter 0 1.35, 1.34, 1.25초 / iter 1 1.28, 1.23, 1.37초 / iter 2 1.34, 1.14, 1.01초
- 호출 하나의 워커 점유 시간 약 1.3초, 그 중 Execution 약 0.25초

**추정** (근거는 있으나 미확인)
- RunPod 워커 1개가 호출을 한 번에 하나씩 처리(직렬 처리)하여 plan1·plan2를 동시에 보내도 큐 대기 시간이 호출마다 누적. 이로 인해 서버의 스레드 동시 실행이 응답 시간을 줄이지 못한 것으로 판단
- `serving/runpod/handler.py`에 `concurrency_modifier` 설정 없음. 이 경우 워커 1개가 동시에 작업 1개를 처리하는 것이 일반 지식이나 이 환경에서 미확인

**확인하지 못한 것**
- 측정 12 예열의 첫 호출 Delay 5.14초와 Cold start time(회당 6.8~8.5초)의 불일치 이유

## 부록 B. Worker states

상태 정의 (RunPod 문서, 사용자가 문서에서 옮겨 전달):

- Initializing: 내려간 상태에서 호스트가 이미지나 캐시 모델을 받는 중 (과금 없음)
- Idle: 내려간 상태에서 시작 준비 완료, 이미지와 캐시 모델이 호스트에 있음 (과금 없음)
- Running: 시작된 상태. cold start, 작업 처리, Idle timeout 대기를 모두 포함 (과금)
- Throttled: 내려간 상태에서 호스트의 GPU가 다른 워크로드에 쓰여 워커가 지금 시작하지 못함 (과금 없음)
- Unhealthy: 워커가 죽었거나 초기화에 실패해 최대 7일까지 늘어나는 간격으로 재시도 (과금 없음)
