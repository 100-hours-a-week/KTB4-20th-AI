- 작성일: 2026-11-06, 개선 구조 1 추가와 구성 변경, 개선 구조 2 추가: 2026-11-07, 개선 구조 3 추가: 2026-11-08 (시각은 모두 KST)
- 대상: AI 서버 `POST /trips/place-selection`, 브랜치 `perf/load-test-server-tuning` (baseline은 커밋 `4fca88d`, 개선 구조 1은 커밋 `6150791`, 개선 구조 2는 커밋 `a1991e2`, 개선 구조 3은 커밋 `d9b14df`)
- 양식: IEEE 829 테스트 요약 보고서의 요약·편차·평가 구성을 참고한 내부 양식. 표준을 그대로 따르지 않음
- 용도: 구조별 측정 결과 기록과 비교. 구조 추가 시 마지막 구조 장 뒤에 같은 소제목의 장을 더하고 4장 표에 열을 추가
- 구성: 1~4장은 결론과 비교, 5~8장은 구조별 상세, 9장은 다음 단계. 비교 값만 볼 때는 1장과 4장 참조
- 관련 기록: grill 질문·답변은 `summary.md`, 구조 그림은 `architecture-baseline.png`(baseline), `architecture-improved.png`(개선 구조 1), `architecture-improved2.png`(개선 구조 2), `architecture-improved3.png`(개선 구조 3), 측정 도구는 `k6/`

## 1. 요약

**결론**
- Max workers 1 조건에서 개선 구조 1(plan0·plan1·plan2를 스레드 3개로 동시 실행)의 warm 응답 시간은 baseline(한 스레드 순차 실행)과 같은 수준
- Max workers 1 조건에서 처리 속도 개선이 관측되지 않았고, 스레드와 DB 연결 사용량만 증가
- 개선 구조 2(place-selection 동시 처리 한도 16, 초과 시 즉시 503): 처리되는 요청의 warm 응답 시간은 baseline과 같은 수준. 동시 18건에서 반복마다 16건은 처리(최대 42.62초), 2건은 0.02~0.04초에 503으로 거절
- 개선 구조 3(place-selection 요청을 줄 세워 한 번에 하나씩 처리, 줄 상한 19): 동시 22건에서 반복마다 19건은 도착 순서대로 처리(k번째 약 2.74 × k초, 첫 요청 2.60·2.80초, 마지막 51.88·52.35초), 3건은 0.01~0.03초에 503으로 거절. 처리량은 개선 구조 2와 같음(0.365건/초 대 0.375건/초)

**구조별 핵심 값**
- baseline: warm N=1 중앙값 2.66초, warm N=2 실행 단위 중앙값 5.65초. 첫 요청 12건 중 7건이 plan1의 RunPod 55초 read timeout으로 HTTP 500
- 개선 구조 1: warm N=1 중앙값 2.66초, warm N=2 실행 단위 중앙값 5.40초. 첫 요청 5건 모두 성공(7.78~12.40초). 55초를 넘는 대기가 없어 실패 동작은 비교하지 못함
- 개선 구조 2: warm N=1 중앙값 3.40초, warm N=2 실행 단위 중앙값 5.53초 (둘 다 한도 16 미만이라 한도 영향 없음). 한도 동작은 동시 18건 실행(측정 19)에서 확인
- 개선 구조 3: 줄 상한 19, 대기 상한 55초. 처리된 19건의 응답 시간 중앙값 약 27.8초(개선 구조 2의 16건은 약 33초), 가장 빠른 요청 2.60초(개선 구조 2는 21.64초), 가장 느린 요청 52.35초. 콜드 스타트가 겹치면 18번째부터 대기 55초를 넘어 55초 뒤 503이 날 것으로 계산됨 (측정 21은 예열 후 실행이라 미발생)
- RunPod 실행 시간(Execution): 모든 측정에서 0.2~0.4초. 지연 구간은 모델 실행이 아니라 요청이 워커에 닿기까지의 대기(cold start, Throttled, 큐 대기)
- DB 연결 오류: 두 구조 모두 0건. 10/28 DB 풀 문제는 이번 측정으로 재현도 반박도 불가

**확인하지 못함**
- 호출 하나가 워커를 약 1.3초 점유하는데 Execution이 약 0.25초인 이유
- 첫 요청 대기가 9초에서 225초까지 변하는 이유
- 모든 측정에서 실행 직전 Worker states (기록 규칙 미이행)
- 콜드 스타트와 겹칠 때 줄 뒤쪽 요청의 실제 동작, 서버 로그의 줄 WARNING 횟수

## 2. 목적과 범위

- 목적: 가장 단순한 baseline에서 동시 요청 처리 방식을 측정하고, 개선 구조와 같은 방법으로 비교
- 범위: N=1과 N=2만 실행 (질문 12에서 5 이상 제외). 로컬 환경 측정이며 ECS 배포 환경과 BE 경유 흐름은 제외
- 가정: ECS Task 1개(0.5 vCPU, 메모리 1GB)에 해당하는 단일 uvicorn 프로세스 1개

## 3. 대상 구조와 측정 환경

**공통 구조** (코드 기준)
- DB: 커넥션 풀 없음. `get_connection()`이 호출마다 새 연결을 엶
- 실패 처리: 예외를 그대로 전파해 HTTP 500 반환. 폴백과 서킷 브레이커 없음. GPU 경로 실패 시 `InferenceUnavailable` 발생
- RunPod 호출 timeout: 55초 (코드 변경 없음)
- 서버: 이벤트 루프 → 스레드풀(anyio 기본 한도 40) → 요청당 스레드 1개. 핸들러는 동기 `def`
- 코드 검증: baseline·개선 구조 1은 `uv run pytest` 773건 통과·1건 건너뜀, 개선 구조 2는 775건 통과·1건 건너뜀, 개선 구조 3은 780건 통과·1건 건너뜀, `uv run ruff check` 통과

**구조별 차이**
- baseline: 한 요청 안에서 plan0(규칙) → plan1(모델) → plan2(모델)를 한 스레드에서 차례로 실행. 요청 1건당 DB 연결 10회 열고 닫음 (로컬 계측)
- 개선 구조 1: plan0·plan1·plan2를 `ThreadPoolExecutor(max_workers=3)`로 스레드 3개에서 동시에 시작하고 셋이 모두 끝나면 응답. `async def` 전환 아님. 한 안이 실패해도 나머지 안은 이미 시작했으므로 끝날 때까지 기다린 뒤 예외 발생
- 개선 구조 2: baseline 코드에 place-selection 동시 처리 한도를 추가. `place_selection_max_concurrency`(기본 16, 계산 근거는 7.5절)를 넘는 요청은 기다리지 않고 즉시 HTTP 503(`동시 처리 한도를 넘었음`)을 반환하고 WARNING 로그를 남김. 슬롯은 성공·실패 모두 반환. plan 실행 구조는 baseline과 동일. 한도는 프로세스 단위(ECS Task 1개 가정). 이후 개선 구조 3으로 코드가 교체됨(개선 구조 2 코드는 커밋 `a1991e2`에 있음)
- 개선 구조 3: 개선 구조 2의 동시 처리 한도를 줄 세우기로 교체. `FifoGate`(`app/trips/fifo_gate.py`)가 요청을 도착한 순서대로 줄 세워 요청 전체(plan0~plan2)를 한 번에 하나씩 처리. 줄(처리 중 1건 + 대기 중)이 `place_selection_queue_capacity`(기본 19)에 차 있으면 기다리지 않고 즉시 HTTP 503(`줄이 가득 차서 처리할 수 없음`), 줄에서 `place_selection_queue_max_wait_seconds`(기본 55초)를 넘게 기다리면 줄에서 빼고 503(`줄에서 기다린 시간이 상한을 넘었음`). 처리가 끝나거나 실패하면 다음 요청에 차례를 넘김. 기다리는 요청도 스레드풀 스레드 1개를 점유(최대 19개, 상한 40 이내). 줄은 프로세스 단위(ECS Task 1개 가정)

**공통 측정 환경**
- 로컬 PC, 로컬 DB, 로컬 단일 uvicorn, RunPod Serverless 실호출
- 도구: k6. 가상 사용자 1명이 반복마다 `http.batch`로 CONC건을 동시에 보내고, 끝나면 바로 다음 반복 시작 (`k6/place_selection.js`). baseline 측정 1~3은 `per-vu-iterations`로 요청 1건씩. 3일 일정, k6 timeout 130초. 첫 반복(iter 0)은 예열
- 반복 측정 명령 (레포 안 `.grill/load-test-server-performance/k6` 폴더): `k6 run -e CONC=1 -e ITER=6 -e TOKEN="$TOKEN" place_selection.js`, N=2는 `CONC=2`, `ITER=7`
- 서버 실행 명령 (레포 루트): `.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000`. 배포 `Dockerfile` 20행과 같은 방식
- RunPod 엔드포인트 설정 (스크린샷 확인): Max workers 1, Active workers 0, GPU count 1, 선택 GPU 16GB 1종, Worker priority Availability, FlashBoot 꺼짐, Execution timeout 체크됨(초 값 미확인), Idle timeout 초 값 미확인 (RunPod 문서 기본값: 콘솔 5초, REST v2 10초)
- 측정 14부터 k6 스크립트는 `batch`·`batchPerHost`를 `CONC`로 올려 CONC건을 모두 동시에 보냄(커밋 `53e75f2`). k6 기본값(`batchPerHost` 6)에서는 `CONC` 20이어도 동시 요청이 6개였음. 이전 측정(CONC 1~2)은 6 이하라 영향 없음
- 측정 중 코드와 RunPod 설정 변경 없음

### 4.6 평가

- baseline
  - 워커가 떠 있을 때 N=1 약 2.7초, N=2 약 5.3~5.7초로 안정적으로 성공
  - 워커가 내려간 뒤 첫 요청은 대기 시간이 9초에서 225초까지 변동. 대기가 55초를 넘으면 요청 전체 실패 (7건 모두 plan1 RunPod ReadTimeout)
  - 이 실패는 워커 준비 대기가 사용자 실패로 직결되는 구조에서 발생
- 개선 구조 1
  - Max workers 1 조건에서 처리 속도 개선이 관측되지 않았고, 스레드와 DB 연결 사용량만 증가
- 개선 구조 2
  - 한도(16)를 넘는 요청은 기다리지 않고 즉시 503으로 거절. 동시 18건 실행에서 반복마다 2건을 0.02~0.04초에 거절하고 16건은 정상 처리(최대 42.62초)
  - 처리되는 요청의 warm 응답 시간은 baseline과 같은 수준 (N=2 실행 단위 5.53초 대 5.65초). N=1 3.40초는 baseline보다 높으나 원인 미확인
  - 용량을 늘리지 않음. 한도를 넘는 요청이 RunPod 호출 타임아웃(55초)까지 기다리다 실패하는 것을 막음
  - 한도 16은 사용자 결정 값 (계산 근거는 7.5절)
- 개선 구조 3
  - 동시 22건 실행에서 줄에 19건을 세워 도착 순서대로 한 번에 하나씩 처리(k번째 약 2.74 × k초). 3건은 0.01~0.03초에 503으로 거절
  - 처리량은 개선 구조 2와 같음(0.365건/초 대 0.375건/초). 중앙값은 약 33초에서 약 27.8초로, 가장 빠른 요청은 21.64초에서 2.60초로 줄었고, 가장 느린 요청은 42.62초에서 52.35초로 늘어남(3건을 더 처리한 만큼)
  - 용량을 늘리지 않음. 처리량은 RunPod 워커 1개가 정함
  - 줄 상한 19와 대기 상한 55초는 계산 값 (19 = (60 − 8.5) ÷ 2.67, 55 = 60 − 2.7 − 2)
  - 남은 위험: 콜드 스타트(8.5초)가 겹치면 18번째 요청이 시작하는 시각이 8.5 + 17 × 2.74 = 55.1초라 대기 상한 55초를 넘어, 18·19번째 요청이 55초를 기다린 뒤 503을 반환할 것으로 계산됨. 줄이 가득 찬 즉시 거절(0.01~0.03초)과 달리 늦은 실패. 측정 21은 예열 후 실행이라 미발생
- 비용 측면 (코드 구조에서 읽은 값)
  - 개선 구조 1의 DB 연결: 요청당 최대 3개 (동시 N건이면 최대 3N개)
  - 개선 구조 1의 스레드: 요청당 최대 4개 (요청 처리 1 + plan 3)
  - 개선 구조 1에서 한 안이 실패해도 나머지 안의 RunPod 호출은 이미 발생
  - 개선 구조 3의 DB 연결: 한 번에 한 요청만 처리하므로 최대 1개
  - 개선 구조 3의 스레드: 줄에 선 요청마다 1개씩 최대 19개 (대기 중에도 점유, 스레드풀 상한 40 이내)
- 워커가 시작하지 못하는 대기(Throttled)는 서버 구조로 해결 불가. 서버 구조가 다룰 수 있는 범위는 대기 발생 시 사용자 응답 방식(타임아웃, 폴백, 실패 처리)과 warm 응답 시간

### 4.7 확인하지 못한 것

- Throttled가 baseline N=2 첫 요청 실패 3건 모두의 원인인지 여부 (측정 2 외에는 대기 구간의 Worker states 미확인)
- 호출 하나의 워커 점유 약 1.3초와 Execution 약 0.25초의 차이 원인
- 워커를 2개 이상으로 늘렸을 때 개선 구조의 효과 (미측정)
- 개선 구조에서 서버 쪽 시간(DB 조회, 계산)의 감소 여부 (별도 측정 없음)
- 콜드 스타트와 겹칠 때 한도 16의 동작 (측정 19는 예열 후 실행). 계산상 마지막 요청 약 51.1초로 55초까지 여유 3.9초
- BE가 AI 서버의 503을 프론트에 어떻게 전달하는지 (클라우드 팀 확인 필요)
- ECS Task가 여러 개일 때 한도(개선 구조 2)와 줄(개선 구조 3)이 Task별로 적용되어 RunPod 워커 1개를 공유하는 전체 요청 수가 달라지는 영향
- 콜드 스타트와 겹칠 때 줄(개선 구조 3)의 실제 동작 (측정 21은 예열 후 실행)
- 서비스 시간이 3.4초(측정 14의 N=1 중앙값)로 늘면 18번째 요청이 시작하는 시각이 17 × 3.4 = 57.8초라 대기 상한 55초를 넘는지 여부 (계산, 미발생)
- 줄에서 기다리는 요청의 클라이언트(BE)가 60초에 연결을 끊어도 서버가 그 요청을 계속 처리하는지 (일반 지식으로는 동기 핸들러가 중단되지 않음, 이 환경에서 확인하지 못함)
- 서버 로그의 줄 WARNING 횟수 (측정 21에서 전달받지 못함)
- 로컬 환경 측정이라 클라우드 팀의 BE 경유 단일 흐름 15.48초와 직접 비교하지 않음

## 부록 B. Worker states

상태 정의 (RunPod 문서, 사용자가 문서에서 옮겨 전달):

- Initializing: 내려간 상태에서 호스트가 이미지나 캐시 모델을 받는 중 (과금 없음)
