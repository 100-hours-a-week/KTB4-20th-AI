# ADR-0016: place-selection 요청을 FIFO 줄로 한 번에 하나씩 처리하고 줄 초과와 모델 경로 실패를 폴백 없이 HTTP 503(또는 500) 에러로 반환

## Status

Proposed

1. Proposed: 2026-11-09

ADR-0010의 결정 중 "모델 호출이 실패하거나 결과가 유효하지 않으면 그 안만 규칙 변형으로 채우는 폴백을 유지한다"는 부분만 대체한다. 2·3안을 항상 모델 경로로 만들고 `PLACE_SELECTION_MODE`를 제거한 부분은 그대로다.

## Context

- 부하 테스트(PR #122, k6로 로컬 서버에 요청을 보내고 RunPod Serverless를 실호출)로 baseline과 개선 구조를 같은 방법으로 비교했다. RunPod 워커가 Max workers 1이라 호출을 한 번에 하나씩 처리하고, 호출당 점유 시간은 약 1.33초다(Execution 약 0.25초, 나머지 약 1.05초는 원인 확인하지 못함).
- 이 때문에 plan 3개를 스레드로 동시에 실행한 개선 구조 1과 동시 처리 한도 16을 둔 개선 구조 2는 처리량을 늘리지 못했다(N=2 실행 단위 중앙값: baseline 5.65초, 구조 1 5.40초, 구조 2 5.53초). 구조 2는 첫 요청이 21.64초였다.
- 측정값: 요청 1건의 서비스 시간(plan0 + RunPod 호출 2번)은 단독 요청 최대 3.65초, 포화 시 평균 2.67초이고, 콜드 스타트는 6.25~21.48초다. BE→AI 읽기 타임아웃은 60초, RunPod `/runsync` 타임아웃은 55초다.
- 개선 구조 3은 줄 상한을 콜드 스타트 최대값을 넣어 9(= floor((55 − 21.48) ÷ 3.65))로 정했으나, 서버는 워커의 콜드 여부를 알 수 없어 warm일 때도 10번째 요청부터 즉시 503이 났다.
- 이 구조를 만드는 과정에서 baseline을 단순화하면서 아래 폴백을 제거했다(커밋 `4fca88d`, `5ede392`). 폴백이 있으면 RunPod 호출 실패가 200 응답으로 가려져 처리량과 실패 지점을 측정할 수 없었다.
  - 모델 경로 실패 시 그 안을 규칙 변형으로 채우는 폴백(ADR-0010)
  - GPU 실패 후 CPU 추론
  - 모델 호출 서킷 브레이커(연속 3회 실패 시 60초 차단)
- PR 리뷰에서 "폴백이 없는데 괜찮은가"라는 질문이 나왔고, 사용자가 폴백 제거를 운영에도 반영하기로 했다(2026-11-09). 사용자가 든 근거는 사용자에게 에러가 반환되고 다시 실행하면 된다는 것이다.
- 재시도로 풀리는 실패는 일시적인 것이다: 줄 가득 참(줄이 비면 처리됨), 콜드 스타트 지연, 타임아웃. 재시도로 풀리지 않는 실패도 있다: 엔드포인트 일시 정지(Max Workers 0)이면 모든 요청이 `409 ENDPOINT_PAUSED`로 거절되고(ADR-0010 Context), 모델 서버 설정이 없거나 잘못된 경우도 같다.
- 확인하지 못한 것: BE가 AI의 503(또는 500)을 사용자에게 어떻게 전달하는지, 사용자 화면에 재시도 수단이 있는지, 운영 ECS Task 수, 운영 RunPod 실패 빈도.

## Decision

우리는 place-selection 요청을 도착 순서대로 FIFO 줄(`FifoGate`)에 세워 한 번에 하나씩 처리한다.

- 줄(처리 중 1건 + 대기 중)의 상한은 15, 줄에서 기다리는 시간의 상한은 55초다. 상한이 차 있으면 기다리지 않고 바로 503, 대기 상한을 넘으면 줄에서 빼고 503 에러를 반환한다.
- 줄 상한 15 = floor(대기 상한 55초 ÷ 서비스 시간 측정 최대값 3.65초) = 15.07이고, 15번째 요청이 54.75초에 끝난다(16번째는 58.4초). 대기 상한 55초 = BE 읽기 타임아웃 60초 − 요청 처리 약 2.7초 − 여유 2초다. 콜드 스타트는 계산에 넣지 않는다.
- 줄 초과와 모델 경로 실패를 규칙 안으로 대신 응답하지 않고 예외를 전파하여 HTTP 503(또는 500) 에러를 반환한다. 일시적인 실패는 사용자가 에러를 받고 다시 실행하면 모델 결과를 받는다. 폴백은 모델 경로 실패, GPU 실패 후 CPU 추론, 모델 호출 서킷 브레이커 세 곳 모두 두지 않는다.

## Alternative / Considered Options

### 1. plan을 스레드로 동시에 실행 (개선 구조 1)

- (장점) 요청 하나 안에서 plan들이 겹쳐 실행된다.
- (단점) RunPod 워커 1개가 직렬 처리해서 처리량이 늘지 않았다(N=2 실행 단위 5.40초 대 baseline 5.65초).
- (소결) 구현해 측정한 뒤 되돌렸다.

### 2. 동시 처리 한도 16, 초과 요청은 즉시 503 (개선 구조 2)

- (장점) 구현이 단순하다.
- (단점) 처리량이 늘지 않았고, 동시에 처리하는 요청이 늘수록 첫 요청 응답이 21.64초로 느렸다. 요청이 도착 순서대로 처리되지 않는다.
- (소결) 선택하지 않았다. 줄 세우기로 교체했다.

### 3. 줄 상한 9 (개선 구조 3, 콜드 스타트 최대값 포함)

- (장점) 콜드 스타트 21.48초가 겹쳐도 9번째 요청이 54.3초에 끝난다.
- (단점) warm일 때도 10번째 요청부터 즉시 503이다. 서버가 워커의 콜드 여부를 알 수 없다.
- (소결) 선택하지 않았다. 사용자가 서비스 시간 최대값만 입력으로 15로 정했다.

### 4. ADR-0010의 폴백 유지

- (장점) GPU 장애, 콜드 스타트, 타임아웃에도 3개 안이 항상 나온다.
- (단점) 실패가 200으로 가려져 로그(WARNING)를 찾아야만 드러나고, 처리량과 실패 지점을 측정할 수 없다.
- (소결) 선택하지 않았다. 일시적인 실패는 에러를 받고 다시 실행하면 되고, 그때 규칙 안이 아니라 모델 결과를 받는다는 것이 사용자 판단이다.

## Consequences

### Positive (Gain)

- 요청이 도착 순서대로 처리되고, 줄 상한 15 안의 요청은 대기 상한 안에 끝난다. 동시 18건 측정에서 반복마다 15건이 도착 순서대로 200(15번째 41.17초와 46.34초), 3건이 0.01초에 503이었다.
- 모델 경로 실패가 응답 코드로 드러나고, 규칙 결과가 모델 결과로 오인되지 않는다.
- 측정한 구조와 운영 구조가 같아, 부하 테스트 수치(줄 상한 15, 대기 55초)가 운영에 적용된다.
- 코드가 단순해진다(폴백, CPU 경로 호출, 서킷 브레이커 제거).

### Negative (Loss)

- 콜드 스타트가 겹치면 줄 뒤쪽 요청이 55초를 기다린 뒤 503을 받는다. 계산: 콜드 21.48초 + k × 3.65초이면 9번째가 54.3초, 10번째가 58.0초에 끝나고 11~15번째는 55초 뒤 503이다(미측정).
- RunPod 장애, 콜드 스타트 겹침, 타임아웃이 곧 일정 생성 실패(HTTP 503 또는 500)가 된다. ADR-0010이 우려했던 결과를 감수한다. 3개 안이 항상 나오는 성질도 사라진다.
- 재시도로 풀리지 않는 실패(엔드포인트 일시 정지, 모델 서버 설정 오류)는 사용자가 다시 실행해도 계속 에러다. 폴백이 있었다면 규칙 안이라도 받았다.
- 서킷 브레이커가 없어 RunPod가 계속 실패해도 요청마다 호출한다. 실패 중 재시도가 몰리면 줄이 가득 차 즉시 503이 늘 수 있고, 55초를 기다린 뒤 503을 받은 사용자의 재시도는 그 시간을 한 번 더 쓴다.
- 줄은 프로세스 단위다. ECS Task가 여러 개면 Task마다 줄이 생겨 RunPod 워커를 공유하는 전체 요청 수가 15를 넘을 수 있다. Task를 늘릴 때는 상한을 15 ÷ Task 수로 나눠야 한다.
- 줄에서 기다리는 요청의 클라이언트가 연결을 끊어도 서버가 그 요청을 처리할 수 있다(일반 지식, 확인하지 못함).
- BE가 AI의 503(또는 500)을 사용자에게 어떻게 전달하는지 확인하지 못했다.
- 이 PR 외에 폴백을 전제하는 문서가 남아 있다(`docs/trips/place-selection-evolution.md`, ADR-0010 본문). ADR은 수정하지 않으므로 이 ADR이 최신 결정이다.
