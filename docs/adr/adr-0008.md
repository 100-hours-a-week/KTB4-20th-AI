# ADR-0008: place-selection 응답을 안·일자·장소의 3차원 배열로 확장하고 안마다 규칙 경로 1번과 모델 경로 2번으로 구성

## Context

- 현재 `POST /trips/place-selection`은 하루 일정 하나(`places: list[Place]`, 5~6곳)만 돌려준다. `Place`에는 일자·시간대 필드가 없다. 요청의 `start_date`, `end_date`는 검증에만 쓰이고 선정 로직은 읽지 않는다.
- 기획이 바뀌어 최대 8박 9일(BE와 합의)을 3가지 안으로 제공해야 한다. 응답 모양(`places[안][일자][장소]`)과 안의 순서는 BE와 협의됐다. BE의 응답 대기 시간은 30초이고 변경 가능하다.
- 하루 슬롯 계획(`build_slot_plan`)은 5슬롯(MORNING, LUNCH, AFTERNOON_FIRST, AFTERNOON_SECOND, DINNER)이고 야간 점수가 3.0을 넘으면 EVENING을 더해 6슬롯이다. 반복 호출하면 매일 같은 카테고리 배치, 매일 같은 장소, 첫날·마지막 날 구분 없음, 매일 저녁 이후 슬롯이 생긴다(`router.py` TODO).
- 서버리스 핸들러는 한 호출에 슬롯을 1~8개만 받고(`handler.py:40`), 한 호출 안에서만 중복 장소를 막는다. 모델은 하루의 앞 6곳까지만 학습했다(`MAX_VISITS = 6`). 하루치 호출은 따뜻한 상태에서 약 1.3초, 유휴 후 첫 요청은 10~13초, 호출 제한은 20초였다(ADR-0004). 9일치 한 호출의 지연은 측정하지 않았다.
- 운영 기본값은 아직 `PLACE_SELECTION_MODE=rule`이고, 모델 경로 실패 때도 규칙 경로로 되돌아간다. 규칙 경로는 시드가 없고 조회 한도가 하루 분량(`슬롯 수 + 5`)이다.
- 시드는 요청 본문 전체의 해시(`router.py:64`, ADR-0007)라서, 외부 요인을 요청에 넣으면 그 값이 바뀔 때마다 같은 여행 조건에도 다른 일정이 나온다.
- 로컬 DB에서 품질 하한을 적용한 야간 후보는 서울 63, 부산 36, 제주 14, 전주 6, 경주 2곳이다.
- 외부 요인(현재 날씨)은 별도 precheck 엔드포인트가 5개 지역의 단기·중기 예보를 판정해 `generated_at`과 `forecasts[날짜].regions[지역]`(`has_issue`, `reasons`)으로 돌려줄 예정이다. precheck는 아직 구현되지 않았고 이 ADR의 범위가 아니다.

## Decision

우리는 place-selection 응답을 `places[안][일자][장소]`의 3차원 배열로 바꾸고, 안마다 다른 경로로 만든다. 일자 수는 항상 `종료일 − 시작일 + 1`이다.

- 안: `[0]` 규칙 경로(평점순, Spring이 재정렬해 최단 거리 안으로 쓰는 원본), `[1]` 모델 경로의 취향 안, `[2]` 모델 경로에 3위·4위 카테고리를 주간 후보에 추가한 다양성 안. `[0]`, `[1]`은 매일 취향 상위 2개 카테고리를 쓴다. 모델 경로를 쓸 수 없으면(운영 기본값 `rule` 포함) 규칙 경로로 `[1]`(후보 상위 K곳에서 시드로 고른 조합)과 `[2]`(3위·4위 카테고리 추가)를 채워 항상 3개 안을 준다.
- 일자별 슬롯: 첫날과 중간 날짜는 현재 하루 템플릿(5~6곳), 마지막 날만 MORNING·LUNCH 2곳이다. 당일치기(시작일 = 종료일)는 현재 템플릿을 유지한다. 저녁 이후 슬롯은 야간 점수 조건을 만족하면 마지막 날을 뺀 날마다 시도하고 후보가 소진되면 제거한다.
- GPU 호출: 안마다 한 번(`[1]`, `[2]` 총 2번)이고, 호출 하나에 일자별 슬롯 후보(`days`)를 담는다. 핸들러가 일자마다 문맥을 초기화하고 중복 방지 집합은 여행 전체에서 공유한다. 호출 제한은 20초를 유지한다. 규칙 `[0]`의 DB 조회와 `[1]`, `[2]`의 후보 조회·GPU 호출은 처음부터 동시에 시작한다.
- 중복: 한 안 안에서 여행 전체에 걸쳐 제거하고, 안 사이는 제거하지 않는다. 안 사이 차이 기준은 일자당 주간·식사 슬롯 기준 최소 2곳 이상 다름이고(`[0]`과 `[1]` 비교) 구현 뒤 측정한다.
- 외부 요인: 요청에 `external_factors`를 precheck 응답과 같은 모양으로 받고, 요청의 지역과 여행 날짜에 해당하는 것만 고른다. `has_issue`가 true인 날짜는 모든 안에서 `OUTDOOR_ACTIVITY` 제외 목록을 후보에 적용한다. 값이 없거나 날짜·지역이 빠지면 신호 없음이다.
- 시드: `region`, 날짜, `members`, 이 여행에 해당하는 `has_issue` 신호로만 계산한다. `generated_at`과 다른 지역의 신호는 뺀다.
- 입력 검증: 종료일 − 시작일이 8일을 넘는 요청은 422로 거부한다.

## Alternative / Considered Options

### 1. 세 안 모두 모델 경로에서 시드만 다르게 만들고 규칙은 폴백으로만 사용

- (장점) 안 사이 구현이 하나의 경로로 통일된다.
- (단점) 지난주 계획(1안 규칙 + Spring 거리, 2안 모델, 3안 다양성)과 다르고, 운영 기본값이 규칙인 동안 모델이 꺼져 있으면 3개 안을 만들 수 없다.
- (소결) 선택하지 않았다. 내가 처음 이렇게 해석했다가 사용자가 바로잡았다.

### 2. 안·일자마다 GPU 호출 (최대 27회)

- (장점) 모델 입력이 하루 단위로 학습 분포와 같고 핸들러 변경이 없다.
- (단점) 일자 사이 중복을 막으려면 일자별 호출이 직렬이 되어 지연이 늘어난다. 총 지연을 측정하지 않았다.
- (소결) 선택하지 않았다. 9일치 한 호출의 p95가 15초를 넘으면 이 방식으로 재설계한다.

### 3. 안마다 45~54슬롯을 일자 구분 없이 한 번에 생성

- (장점) 호출이 가장 단순하다.
- (단점) 학습하지 않은 길이이고 핸들러 상한 8을 크게 늘려야 한다.
- (소결) 선택하지 않았다.

### 4. 안 사이 중복을 순차 호출로 제거

- (장점) 안 사이 겹침이 없어진다.
- (단점) 호출이 직렬이 되어 지연이 늘어난다.
- (소결) 보류했다. 겹침 기준(일자당 2곳 이상 다름)을 못 채우면 도입한다.

### 5. 첫날과 마지막 날 모두 부분 템플릿(도착일 오후, 출발일 오전)

- (장점) 도착·출발 시간 가정에 가깝다.
- (단점) 사용자가 첫날은 하루 전체로 정했다.
- (소결) 선택하지 않았다.

### 6. 요청 본문 전체 해시를 시드로 유지

- (장점) 코드 변경이 없다.
- (단점) 외부 요인이 바뀌면 같은 조건에도 일정이 달라진다.
- (소결) 선택하지 않았다.

## Consequences

### Positive (Gain)

- 최대 9일 일정을 3개 안으로 한 번에 받을 수 있다. 가능한 장소 수는 `8 × (5~6) + 2` = 42~50곳이다.
- 모델 경로가 꺼져 있어도 응답 모양이 같다.
- 한 안 안에서 여행 전체 중복이 없다.
- 날씨 신호로 같은 여행 조건의 일정이 외부 값 변화에 흔들리지 않는다(시드 입력 제한).
- GPU 호출이 최대 2번으로 제한되어 일수 증가에 비례해 늘지 않는다.

### Negative (Loss)

- 응답 형식이 바뀌어 BE가 `places`를 새 구조로 읽어야 한다. BE가 현재 장소 수 5~6에 의존하는지는 확인하지 못했다.
- 9일치 한 호출의 지연을 아직 모른다. 호출 제한 20초에 규칙 변형 시간을 더하면 30초(BE 제한)를 넘을 수 있다.
- 모델은 하루 6곳까지만 학습했다. 일자마다 문맥을 초기화해 분포는 유지하지만 9일치 호출의 계산량과 3위·4위 카테고리 후보(`[2]`)의 품질은 측정하지 않았다.
- 안 사이 겹침을 허용하므로 `[1]`이 `[0]`과 비슷할 수 있다. EVENING 슬롯은 야간 후보(경주 2곳 등)가 모자라 안 사이에 겹칠 수밖에 없다.
- 규칙 경로에 시드 기반 변형과 9일치 후보 조회를 새로 만들어야 한다. 병렬 실행을 위해 동기 라우터에 스레드풀 등을 도입한다.
- 핸들러 이미지가 바뀌어(`days` 구조, 슬롯 상한) 새 이미지 빌드와 7,680건 불변식 재검증이 필요하다.
- ADR-0007의 시드 정의가 바뀐다.

- [x] 자동: 8일을 넘는 요청이 422이고, 같은 요청은 같은 응답이며, `generated_at`과 다른 지역의 신호가 바뀌어도 응답이 같다. `tests/test_place_selection_route.py`가 확인한다.
- [x] 자동: `has_issue`가 true인 날짜의 모든 안에 `OUTDOOR_ACTIVITY` 제외 type이 없고, 모델 경로 실패와 `rule` 모드에서도 3개 안이 나온다. `tests/test_trip_selection.py`, `tests/test_place_selection_route.py`가 확인하고, GPU 측정(요청 20건, 3·4일째 신호)에서도 신호일 야외 장소가 세 안 모두 0곳이었다.
- [x] 수동: 대표 설문 × 지역 5곳 × 여행 길이로 안 사이 겹침(일자당 저녁 이후를 뺀 슬롯에서 2곳 이상 다름)을 측정한다. `scripts/measure_trip_plans.py`로 RunPod v3에서 쟀다(2026-10-19, 신호 없음·경주·날씨 신호 각 20건). `[1]` 대 `[0]` 418/420일, `[2]` 대 `[0]` 419/420일 충족이고 미충족 3일은 모두 후보가 적거나 슬롯이 2개인 날에 1곳만 달랐다. "모든 일자" 기준에는 못 미친다.
- [x] 수동: 9일치 모델 호출의 p95와 전체 응답 최악 시간을 측정한다. 모델 호출 p95는 최대 2.91초, 전체 응답은 최대 3.02초였고, 워커가 내려간 뒤 첫 요청은 10.3초였다(n=1, 요청 직전 워커 0개를 확인하지 못한 추정).

**결정사항 반영 여부 측정 목록**

- [x] 9일치 모델 호출 p95가 15초를 넘으면 호출 단위(대안 2)를 재검토한다. 넘지 않아(최대 2.91초) 재검토하지 않는다.

- [x] 전체 응답 최악이 BE 제한 30초를 넘으면 GPU 호출 제한이나 병렬 구조를 재검토한다. 넘지 않아(최대 3.02초, 콜드 추정 10.3초) 재검토하지 않는다. 표본이 작고(요청 60건) 콜드 스타트는 1건뿐이다.
- [ ] `[2]`의 3위·4위 카테고리 비율과 규칙 변형의 상위 후보 수 K는 구현 때 정하고 이 ADR이 아니라 설계 문서에 기록한다. 모델 다양성 안 `[2]`의 3위·4위 비율은 측정에서 41.4%, 49.0%, 43.2%였고 K=10은 잠정값이다. 정하지 않아 미결로 둔다.
