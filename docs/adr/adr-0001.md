# ADR-0001: 장소 후보를 hex grid로 사전 수집한 자체 DB에서 조회

## Status

Accepted

1. Proposed: 2026-09-22 (PR #19 생성)
2. Accepted: 2026-09-24 (PR #22 머지)

## Context

**문제**

- 초기 설계(2026-09-18 핸드오프 기준)는 요청마다 Google Places Nearby Search를 실시간 호출하고, AI 서버는 자체 캐싱과 DB 접근을 하지 않는 구조였다.
- Nearby Search는 한 좌표에서 필터링된 결과가 최대 20개이고 페이지네이션을 쓰지 않아, 같은 지역과 필터로 호출하면 항상 같은 20개만 반환된다. 21번째 장소는 호출할 수 없다. (PR #19)
- 장소 추천은 20개 중 하나를 고르는 구조가 되어 선택 폭이 좁았다.
- 응답이 정형 데이터라 RDS에 적재해 조회할 수 있었다. (사용자 진술)

**조건과 규모 (확인된 사실)**

- 서비스 지역은 5개(서울, 부산, 제주, 경주, 전주)이며, 수집 지역은 6개(제주를 제주시권과 서귀포권으로 분리), hex grid 중심점은 180개, 반경은 2,883m다.
- 2026-10-01 재수집(PR #54) 기준 적재량은 장소 10,719건, type 연결 46,894건, 카테고리 연결 11,069건, 리뷰 39,772건이다.
- 서비스는 MVP 단계이며 총 사용자는 100명 내외로 가정했다. (사용자 진술)
- 백엔드와 같은 RDS 인스턴스를 사용한다. 백엔드 ERD의 테이블명과 충돌해 Flyway 마이그레이션이 실패해서 `ai_` 접두사를 붙였다. (PR #32)

**범위와 책임 경계**

- 범위: trips 장소 후보의 수집, 저장, 조회.
- 범위 밖: 후보 정렬과 슬롯 규칙(ADR-0000), v2 이후의 수집 소스 변경.

**가정 (확인되지 않음)**

- 초기 설계에서 Google 정책상 `place_id` 외 필드의 장기 캐싱이 금지된다고 인식했다. v1 DB는 전체 필드와 리뷰를 저장하며, 당시 접근 가능한 데이터의 범위를 제대로 판단하지 못했다. 정책 부합 여부는 확인되지 않았다. (사용자 진술)
- RDS 인스턴스 사양과 `max_connections` 값은 저장소에서 확인되지 않았다.

## Decision

우리는 v1 trips의 장소 후보를 요청 시 Google Places 실시간 호출이 아니라, hex grid 좌표로 사전 수집해 RDS에 적재한 자체 DB(`ai_places` 등)에서 조회한다.

- 수집: 지역별 hex grid 중심점마다 카테고리 type 조합으로 Nearby Search를 호출해 저장한다(`collect_places.py`). 호출 실패는 최대 3회 재시도하고, 연속 5회 실패하면 수집을 중단한다.
- 저장: 장소 정보를 정규화해 5개 테이블(`ai_places`, `ai_place_categories`, `ai_place_types`, `ai_place_regions`, `ai_place_reviews`)에 적재한다.
- 조회: `place-selection`이 지역, 카테고리, 제외·포함 type 조건으로 SQL을 실행한다. 커넥션 풀은 최대 5개 연결을 사용한다.

## Alternative / Considered Options

### 1. 요청 시 Google Places 실시간 호출 (초기 설계)

- (장점) 항상 최신 데이터를 사용하고, AI 서버가 DB를 갖지 않아 구조가 단순하며, 캐싱 정책 문제가 없다.
- (단점) 한 좌표당 최대 20개이고 같은 조건이면 같은 20개가 반환되어 후보의 폭과 다양성을 확보할 수 없다.
- (소결) 기각.

### 2. 지역당 하나의 중심 좌표로 수집

- (장점) 구현이 단순하고 호출 수가 적다.
- (단점) 조합당 최대 20개만 확보되어, DB를 구축해도 다양성이 확보되지 않는다.
- (소결) 기각. 지역을 세부 좌표로 나누고 탐색 범위를 좁혀 겹치지 않게 호출하는 방식(hex grid)으로 변경했다.

## Consequences

### Positive (Gain)

- 지역과 카테고리별 후보를 충분히 확보해 한 좌표 20개의 한계를 해소한다.
- 요청 경로에서 외부 API 호출 없이 DB만 조회하므로, 요청 처리가 Google Places API의 호출 비용·지연·가용성에 의존하지 않는다.
- 평점·평가 수 정렬과 type 포함·제외 필터를 SQL로 일관되게 적용할 수 있다.

### Negative (Loss)

- 데이터가 수집 시점에 고정되며 자동 갱신 절차가 없다. 재수집은 수동이고, PR #54에서는 기존 테이블을 삭제 후 재적재해 `ai_places.id`가 바뀌었으며 백업하지 않았다.
- Google 정책 부합 여부가 확인되지 않은 상태로 전체 필드와 리뷰를 저장하고 있다. 공공데이터 접근 가능성을 검토해 수집 소스를 변경할지 결정해야 한다.
- 백엔드와 같은 RDS를 공유하므로 테이블명 충돌과 마이그레이션 영향, 연결 한도를 함께 부담한다.
- 커넥션 풀 크기(최대 5)는 MVP 단계에서 작게 시작한다는 판단에 따른 초기값이며 부하 측정으로 검증하지 않았다. `blocking=False` 기본값이라 한도에 도달하면 대기하지 않고 `TooManyConnectionsError`가 발생한다.
- 지역 필터가 중심점마다 `ST_Distance_Sphere` 조건을 `OR`로 잇는 구조(서울 최대 43개)이며, 쿼리 비용은 측정하지 않았다.

## Compliance / Reconsideration Conditions

**결정사항 반영 여부 검증 기준**

- [ ] 자동(기존): CI가 MySQL 8.0 서비스 컨테이너에 테스트 DB 덤프를 적재한 뒤 `pytest`로 `/trips/place-selection`의 DB 조회 경로를 실행한다.
- [ ] 수동(기존): 재수집 후 장소·type·카테고리·지역 건수와 연결 누락(0건) 여부를 검증 쿼리로 확인한다. (PR #54에서 수행한 방식)
- [ ] 수동: 요청 경로(`place-selection`)에 Google Places 실시간 호출을 추가하는 변경은 이 ADR을 대체하는 새 ADR을 먼저 작성한다.

**결정사항 반영 여부 측정 목록**

- [ ] 동시 요청 증가 시 풀 고갈 오류 발생 여부 (현재 측정 없음)
- [ ] 지역 필터 쿼리의 응답 시간 (현재 측정 없음)
- [ ] 공공데이터 접근 가능성 검토 결과 (수집 소스 변경 시 이 결정의 재검토 조건)
