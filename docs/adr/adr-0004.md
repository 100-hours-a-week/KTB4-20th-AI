# ADR-0004: 모델 서빙을 RunPod 서버리스 GPU와 컨테이너 CPU 폴백의 두 경로로 구성

## Status

Accepted

1. Proposed: 2026-10-14
2. Accepted: 2026-10-18 (RunPod 벤치마크를 마치고 기본 경로를 GPU 우선으로 정함)

## Context

**문제**

- ADR-0003의 모델을 서비스에서 실행할 위치와 방식을 정해야 한다. 서비스는 사용자 100명 내외로 시작하지만 중견·대기업 수준의 트래픽까지 단계적으로 확장하는 계획을 전제로 한다.
- 개발자는 GPU 서빙 경험이 없고, 이 프로젝트는 AI 개발자 취업 준비를 겸한다.

**조건과 규모 (확인된 사실)**

- AI 서버는 python:3.12-slim 컨테이너의 FastAPI(uvicorn) 단일 프로세스이고, AWS SSM + Docker Compose로 배포한다. 호스트는 2 vCPU, 메모리 3.8GB(여유 약 2.5GB)다.
- 컨테이너 메모리 제한은 백엔드 1g, 프론트 128m이고 AI 서버에는 없다. 백엔드 → AI 서버 타임아웃은 연결 3초, 읽기 30초다.
- 현재 규칙 파이프라인의 요청당 평균 처리 시간은 약 0.18초(로컬 DB, 테스트 오버헤드 포함)이고 DB 커넥션 풀은 최대 5개다.
- 모델은 약 1,000만 파라미터대로 추정한다(실측 전). 요청은 한 번에 하나이고 생성 단계는 20~24단계다.
- GPU는 RunPod를 쓰고 비용은 지원된다. 학습은 Pod를 일시적으로 켜고, 서빙은 Serverless다. VLM(`Qwen/Qwen2.5-VL-7B-Instruct`, bf16 가중치 약 15GB 계산 값)이 별도로 서빙된다.
- RunPod Serverless는 워커가 없을 때 콜드 스타트가 있고(컨테이너 시작과 모델 적재), 상시 워커를 두면 없어지지만 상시 요금이 든다.

**벤치마크 결과 (2026-10-17~18, 모델 A 3.37M, ONNX, 엔드포인트 `place-model-bench`, 이미지 `whale2200d/place-model-runpod:v1`)**

- 엔드포인트 설정: Active 워커 0, Max 2, Idle timeout 5초, FlashBoot 꺼짐, 컨테이너 디스크 20GB, 실행 제한 120초. 호출은 `/runsync`.
- GPU별 첫 실행: 같은 이미지에서 PRO 6000 MIG 24GB(최신 세대로 추정)는 첫 요청의 executionTime이 35~39초(총 43~48초)였고 RTX A4500는 0.33초(총 8.8초)였다. 최신 세대에는 CUDA 12.4와 `onnxruntime-gpu 1.20.2`로 미리 컴파일된 커널이 없어 첫 사용 때 컴파일된 것으로 추정한다(GPU만 바꿔 재현했으나 원인은 직접 확인하지 못했다).
- 아래 측정은 16GB 그룹(RTX 2000 Ada, RTX 4000 Ada, RTX A4000, RTX A4500)만 선택한 상태이고, 측정한 워커 `tt40h35275o36e`는 RTX A4500(12 vCPUs, 62GB RAM)임을 콘솔에서 확인했다.
- 90초 유휴 후 첫 요청(서울 요청 138KB, 3회): 총 13.1 / 10.0 / 12.2초, delayTime 9.2~12.2초, executionTime 0.33~0.38초. 3회 모두 같은 워커 ID가 다시 쓰여서 새 컨테이너가 처음부터 뜬 시간인지는 확인하지 못했다.
- 따뜻한 상태(20회, 서울·제주 번갈아): 총 평균 1.335초, p50 1.336초, p95 1.429초. delayTime 평균 0.81초, executionTime 평균 0.19초(p95 0.25초). 실패 없음.
- 동시 요청(4개 × 3라운드): 총 평균 3.35초, p95 5.46초. 서로 다른 워커는 1개였고 두 번째 워커는 뜨지 않았다.
- 요청 크기: 0.5 / 1 / 5 / 10 / 15MB 모두 성공(총 1.26 → 5.95초, 1MB당 약 0.4초 증가). 한도는 15MB 이상이며 찾지 못했다. 서비스의 실제 요청은 약 138KB(서울, 슬롯 5개, 후보 770~1,055개)다.
- 같은 요청의 CPU 경로 추론(이 Mac, ONNX Runtime 1 스레드): 서울 평균 276ms, 제주 366ms. 서버(2 vCPU 공유)의 CPU 경로는 측정하지 못했다.
- 로컬 DB를 포함한 모델 경로 전체(CPU)는 평균 약 480ms, 최대 상주 메모리 120MB였다.
- 서버 경유 확인(2026-10-18): 로컬에서 uvicorn으로 AI 서버를 띄우고(`PLACE_SELECTION_MODE=model`, `MODEL_DIR` 없음, 실제 엔드포인트) `/trips/place-selection`에 요청 3건을 보냈다. 모두 HTTP 200, 장소 5곳이었고 응답은 6.69초 / 1.29초 / 1.38초였다(첫 요청은 요청 전에 워커가 이미 initializing 상태였다). `/health`의 완료 요청 수가 49에서 52로 3 늘어 GPU 경로 사용을 확인했고, 서버 로그에 경고나 오류는 없었다. GPU 경로가 낸 장소 5곳은 CPU 경로 결과와 같았다.
- GPU 호출 실패 시험: 잘못된 엔드포인트 주소로 같은 서버에 요청 4건을 보냈다(CPU 경로 없는 구성). 모두 HTTP 200, 장소 5곳이 규칙 경로 결과로 응답했고 서버 로그에 `모델 경로 실패, 규칙 경로로 되돌림`(ERROR) 4건, `GPU 경로 실패`(WARNING) 3건이 남았다. 3번 연속 실패 뒤 서킷 브레이커가 GPU 호출을 막았다. CPU 경로가 있는 구성(5건)에서는 같은 실패에 CPU 경로로 응답했고 같은 방식으로 브레이커가 동작했다.
- 관측: 정상 요청의 경로 로그(`route=gpu/cpu`)는 INFO라 uvicorn 기본 설정에서 서버 로그에 나오지 않는다(앱에 로깅 설정이 없음, 코드로 확인). 오류와 GPU 실패 경고는 보인다. 정상 요청의 gpu/cpu 비율은 운영에서 셀 수 없다. 응답에 영향이 없고 출시에 치명적이지 않다고 판단해 후순위로 미뤘다. GPU 경로 사용은 RunPod `/health`의 완료 요청 수로 확인할 수 있다.
- 신뢰성: 엔드포인트 상태 조회(`/health`)에서 지금까지 보낸 49건이 모두 완료(실패 0, 재시도 0, 대기·진행 0)였다.
- 운영: Idle timeout을 5초로 두었는데 요청이 끝난 뒤에도 idle 워커 2개가 남아 있어 콘솔에서 Terminate해야 했고 이유는 확인하지 못했다. 시험이 끝난 뒤 Max 워커를 0으로 낮춰 일시 정지했다(`/health`의 workers가 모두 0). 크레딧은 두 확인 사이에 $78.08에서 $78.03으로 줄었으나 사이의 시간을 알지 못해 비용 단가 판단에는 쓰지 않는다.

**가정 (확인되지 않음)**

- 서버의 CPU 아키텍처, 서버에서의 CPU 경로 지연과 메모리는 측정하지 못했다. 사용자가 AWS 서버에는 CPU 경로를 배포하지 않는다고 가정하기로 해서(2026-10-18) 측정하지 않는다.
- 비용은 기록하지 못했다(GPU 단가: 16GB 그룹 시간당 $0.59로 화면에 표시됨).
- 자동 확장이 일어나는 조건과 FlashBoot의 효과는 확인하지 못했다.

## Decision

우리는 모델을 RunPod Serverless GPU 경로와 AI 서버 컨테이너 내 CPU 경로의 두 가지로 모두 구현하고, 측정 결과로 서비스 기본 경로를 정한다.

- 두 경로는 같은 모델 산출물(ONNX)을 쓴다. 후보 목록과 슬롯 제약을 요청에 실어 GPU 쪽이 빔 서치 전체를 수행한다.
- 내 모델은 VLM과 다른 엔드포인트로 서빙한다.
- GPU 호출에 타임아웃을 두고 초과하거나 실패하면 CPU 경로로 폴백한다. 연속 실패 시 일정 시간 GPU 호출을 차단하는 서킷 브레이커를 둔다.
- 코드 사전의 키는 `google_place_id`이고 재수집 후 갱신은 수동 절차다. 요청 경로에서 외부 임베딩 API를 호출하지 않는다.
- 서비스 기본 경로는 GPU 우선이다(GPU 호출 20초 제한, 실패 시 CPU, 그다음 규칙 경로). 단 AWS 서버에는 CPU 경로를 배포하지 않기로 했으므로(`MODEL_DIR`을 두지 않음) 실제 운영의 폴백 순서는 GPU → 규칙 경로다. CPU 경로 코드는 남겨 두고, 서버 사양이 확인되면 `MODEL_DIR`만 설정해 켤 수 있다. 이 결정의 근거는 성능이 아니라 GPU 서빙 경험이라는 프로젝트 목표다. 위 측정에서 CPU 경로가 지연이 더 짧았음(따뜻한 GPU 1.3초 대 CPU 추론 0.28초)을 알고 정한 것이다.
- 엔드포인트의 GPU는 Ada·Ampere 세대의 16GB 그룹으로 고정한다. 최신 세대가 배정되면 첫 요청이 약 45초 걸려 AI 서버의 20초 제한을 넘는다. 이미지는 CUDA 12.4와 `onnxruntime-gpu 1.20.2` 조합이다.
- 서빙은 모델 학습과 평가를 끝낸 뒤 진행한다(진행 완료).
- 트래픽 확장은 단계적으로 한다: 요청 경로의 DB 제거와 결과 캐시, AI 서버 수평 확장, GPU 서빙의 동적 배칭과 워커 조정, 모니터링·부하 테스트, 모델 버전 롤아웃.

## Alternative / Considered Options

### 1. 컨테이너 내 CPU 추론만 사용

- (장점) 구조가 단순하고 장애 지점이 늘지 않으며 현재 배포 파이프라인을 그대로 쓴다.
- (단점) 메모리 여유가 크지 않고 2 vCPU를 다른 컨테이너와 나눠 쓴다. GPU 서빙 경험을 얻지 못하고 트래픽 증가에 수평 확장 비용이 크다.
- (소결) 단독으로는 선택하지 않았다. 폴백과 비교 기준으로 구현한다.

### 2. RunPod GPU 서버리스만 사용 (폴백 없음)

- (장점) AI 서버 컨테이너의 메모리 부담이 줄고 동적 배칭, 워커 확장을 쓸 수 있다.
- (단점) 요청 경로에 네트워크 호출이 늘고, 콜드 스타트와 GPU 서버 장애가 서비스 전체에 영향을 준다.
- (소결) 선택하지 않았다.

### 3. VLM과 내 모델을 하나의 서버리스 워커에 함께 서빙

- (장점) GPU 메모리에는 둘 다 들어간다(내 모델은 수십 MB 수준).
- (단점) 콜드 스타트가 결합되어 내 모델 요청도 VLM 적재를 기다리고, 긴 VLM 추론이 같은 워커의 요청을 막으며 장애가 함께 번진다.
- (소결) 선택하지 않았다. 엔드포인트를 분리한다.

### 4. CPU 경로를 기본으로 하고 GPU는 CPU 동시 실행 상한을 넘을 때만 사용

- (장점) 벤치마크에서 지연이 가장 짧고(CPU 추론 0.28초, GPU는 따뜻할 때도 1.3초), GPU 비용이 줄고, 콜드 스타트가 사용자에게 보이지 않는다.
- (단점) GPU 서빙 경로를 평상시 운영하며 얻는 경험이 줄고, GPU 경로 이상이 평소에는 드러나지 않는다.
- (소결) 선택하지 않았다. GPU 서빙 경험이라는 프로젝트 목표를 우선해 GPU 우선을 기본으로 정했다. 서버 CPU 측정이 끝나고 지연이 문제가 되면 이 안으로 바꾼다.

## Consequences

### Positive (Gain)

- 측정으로 기본 경로를 정해서, 필요성이 없으면 없다고 기록할 수 있다.
- GPU 경로가 실패해도 CPU 경로로 서비스를 유지한다.
- 같은 모델 파일로 두 경로를 비교하고, 트래픽 확장 단계를 하나씩 추가할 수 있다.

### Negative (Loss)

- 두 경로를 구현하고 유지해야 해서 코드와 테스트가 늘어난다.
- GPU 경로가 지연되면 모든 요청이 CPU 경로로 몰려 과부하가 날 수 있다. 서킷 브레이커와 폴백 용량 산정이 필요하다.
- AWS 서버에 CPU 경로를 두지 않으면 GPU가 실패하거나 20초를 넘길 때 모델이 아니라 규칙이 장소를 고르므로, 장애 시 추천 품질이 규칙 수준으로 돌아간다. 응답 자체는 항상 5곳 이상이다(시험으로 확인).
- GPU 우선은 측정상 CPU 우선보다 느리다. 따뜻한 상태 총 1.3초(CPU 경로 추론 0.28초), 유휴 후 첫 요청 10~13초, 사용자는 이 지연을 그대로 겪는다. GPU 비용이 추가로 든다.
- 콜드 스타트는 구세대 GPU에서 약 10~13초로 20초 제한 안이지만, 최신 세대에 배정되면 약 45초가 되어 CPU 폴백으로 넘어간다. 엔드포인트를 16GB 그룹으로 고정해도 그 그룹의 재고가 부족하면(화면에서 Medium으로 표시됨) 워커 시작이 늦어질 수 있다.
- 요청 사이가 5초만 넘어도 워커가 내려가서, 사용자 100명 안팎의 드문 트래픽에서는 요청 대부분이 콜드 스타트 지연을 겪을 가능성이 크다(트래픽 가정에 기반한 추정). 상시 워커 1개를 두면 없어지지만 상시 요금이 든다.
- 동시 요청이 몰려도(4개 동시) 워커가 늘지 않아 마지막 요청이 5초 가까이 기다렸다.
- 유휴 시간 설정과 달리 idle 워커가 남을 수 있어서 비용이 새지 않도록 시험 뒤 `/health`로 워커 수를 확인하고 필요하면 Max 워커를 0으로 낮추는 운영 절차가 필요하다.
- ONNX 변환 과정에서 지원하지 않는 연산이 있으면 변환이 어렵고 디버깅이 불편하다.
- 모델 버전, 코드 사전, DB 버전의 정합성을 함께 관리해야 한다.

## Compliance / Reconsideration Conditions

**결정사항 반영 여부 검증 기준**

- [x] 자동: GPU 경로 실패와 타임아웃을 모의했을 때 CPU 경로로 응답하는 테스트(`tests/test_model_serving.py`: 폴백, 서킷 브레이커, RunPod 응답 검증)
- [ ] 자동: 같은 입력에 두 경로의 결과가 같은 장소를 내는지 확인하는 테스트. 수동으로는 같은 요청에서 RunPod(GPU)와 로컬 CPU가 같은 장소 2곳을 냈다.
- [x] 수동: 벤치마크(콜드 스타트 포함 첫 요청 지연, 따뜻한 지연, 동시 요청, 요청 크기)를 마치고 기본 경로를 정했다. 서버 CPU 경로의 지연과 메모리는 측정하지 못했다.
