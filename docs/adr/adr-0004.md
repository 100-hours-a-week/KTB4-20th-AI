# ADR-0004: 모델 서빙을 RunPod 서버리스 GPU와 컨테이너 CPU 폴백의 두 경로로 구성

## Status

Proposed

1. Proposed: 2026-10-14

## Context

**문제**

- ADR-0003의 모델을 서비스에서 실행할 위치와 방식을 정해야 한다. 서비스는 사용자 100명 내외로 시작하지만 중견·대기업 수준의 트래픽까지 단계적으로 확장하는 계획을 전제로 한다.
- 개발자는 GPU 서빙 경험이 없고, 이 프로젝트는 AI 개발자 취업 준비를 겸한다.

**조건과 규모 (확인된 사실)**

- AI 서버는 python:3.12-slim 컨테이너의 FastAPI(uvicorn) 단일 프로세스이고, AWS SSM + Docker Compose로 배포한다. 호스트는 2 vCPU, 메모리 3.8GB(여유 약 2.5GB)다.
- 컨테이너 메모리 제한은 백엔드 1g, 프론트 128m이고 AI 서버에는 없다. 백엔드 → AI 서버 타임아웃은 연결 3초, 읽기 30초다.
- 현재 규칙 파이프라인의 요청당 평균 처리 시간은 약 0.18초(로컬 DB, 테스트 오버헤드 포함)이고 DB 커넥션 풀은 최대 5개다.
- 모델은 약 1,000만 파라미터대로 추정한다(실측 전). 요청은 한 번에 하나이고 생성 단계는 20~24단계다.
- GPU는 RunPod를 쓰고 비용은 지원된다. 학습은 Pod를 일시적으로 켜고, 서빙은 Serverless다. VLM(`Qwen/Qwen2.5-VL-7B-Instruct`, bf16 가중치 약 15GB 계산 값)이 별도로 서빙된다.
- RunPod Serverless는 워커가 없을 때 콜드 스타트가 있고(컨테이너 시작과 모델 적재), 상시 워커를 두면 없어지지만 상시 요금이 든다.

**가정 (확인되지 않음)**

- 이 크기의 모델은 배치 1 요청에서 GPU의 성능 이점이 작을 수 있다(일반적 성질 기반, 미측정).
- RunPod의 payload 크기 제한과 호출 방식은 확인하지 못했다.

## Decision

우리는 모델을 RunPod Serverless GPU 경로와 AI 서버 컨테이너 내 CPU 경로의 두 가지로 모두 구현하고, 측정 결과로 서비스 기본 경로를 정한다.

- 두 경로는 같은 모델 산출물(ONNX)을 쓴다. 후보 목록과 슬롯 제약을 요청에 실어 GPU 쪽이 빔 서치 전체를 수행한다.
- 내 모델은 VLM과 다른 엔드포인트로 서빙한다.
- GPU 호출에 타임아웃을 두고 초과하거나 실패하면 CPU 경로로 폴백한다. 연속 실패 시 일정 시간 GPU 호출을 차단하는 서킷 브레이커를 둔다.
- 코드 사전의 키는 `google_place_id`이고 재수집 후 갱신은 수동 절차다. 요청 경로에서 외부 임베딩 API를 호출하지 않는다.
- 서빙은 모델 학습과 평가를 끝낸 뒤 진행한다.
- 트래픽 확장은 단계적으로 한다: 요청 경로의 DB 제거와 결과 캐시, AI 서버 수평 확장, GPU 서빙의 동적 배칭과 워커 조정, 모니터링·부하 테스트, 모델 버전 롤아웃.

## Alternative / Considered Options

### 1. 컨테이너 내 CPU 추론만 사용

- (장점) 구조가 단순하고 장애 지점이 늘지 않으며 현재 배포 파이프라인을 그대로 쓴다.
- (단점) 메모리 여유가 크지 않고 2 vCPU를 다른 컨테이너와 나눠 쓴다. GPU 서빙 경험을 얻지 못하고 트래픽 증가에 수평 확장 비용이 크다.
- (소결) 단독으로는 선택하지 않았다. 폴백과 비교 기준으로 구현한다.

### 2. RunPod GPU 서버리스만 사용 (폴백 없음)

- (장점) AI 서버 컨테이너의 메모리 부담이 줄고 동적 배칭, 워커 확장을 쓸 수 있다.
- (단점) 요청 경로에 네트워크 호출이 늘고, 콜드 스타트와 GPU 서버 장애가 서비스 전체에 영향을 준다.
- (소결) 선택하지 않았다.

### 3. VLM과 내 모델을 하나의 서버리스 워커에 함께 서빙

- (장점) GPU 메모리에는 둘 다 들어간다(내 모델은 수십 MB 수준).
- (단점) 콜드 스타트가 결합되어 내 모델 요청도 VLM 적재를 기다리고, 긴 VLM 추론이 같은 워커의 요청을 막으며 장애가 함께 번진다.
- (소결) 선택하지 않았다. 엔드포인트를 분리한다.

## Consequences

### Positive (Gain)

- 측정으로 기본 경로를 정해서, 필요성이 없으면 없다고 기록할 수 있다.
- GPU 경로가 실패해도 CPU 경로로 서비스를 유지한다.
- 같은 모델 파일로 두 경로를 비교하고, 트래픽 확장 단계를 하나씩 추가할 수 있다.

### Negative (Loss)

- 두 경로를 구현하고 유지해야 해서 코드와 테스트가 늘어난다.
- GPU 경로가 지연되면 모든 요청이 CPU 경로로 몰려 과부하가 날 수 있다. 서킷 브레이커와 폴백 용량 산정이 필요하다.
- 콜드 스타트(워커가 내려간 뒤 첫 요청)가 읽기 타임아웃 30초를 넘길 위험이 있어 상시 워커 운용이 필요할 수 있다.
- ONNX 변환 과정에서 지원하지 않는 연산이 있으면 변환이 어렵고 디버깅이 불편하다.
- 모델 버전, 코드 사전, DB 버전의 정합성을 함께 관리해야 한다.

## Compliance / Reconsideration Conditions

**결정사항 반영 여부 검증 기준**

- [ ] 자동: GPU 경로 실패와 타임아웃을 모의했을 때 CPU 경로로 응답하는 테스트
- [ ] 자동: 같은 입력에 두 경로의 결과가 같은 장소를 내는지 확인하는 테스트(수치 오차 허용 범위 내)
- [ ] 수동: 벤치마크 보고서(평균·상위 95% 지연, 콜드 스타트 포함 첫 요청 지연, 메모리, 처리량)에 따라 기본 경로를 정한 뒤 Accepted로 전환한다.

**결정사항 반영 여부 측정 목록**

- [ ] 폴백 비율과 폴백 시 CPU 경로의 지연
- [ ] 콜드 스타트 발생 빈도와 상시 워커 필요 여부
- [ ] RunPod payload 제한과 호출 방식(동기/비동기) 확인 결과
