# ADR-0012: place-selection 응답을 1안 places와 2·3안 routes로 나누고 routes에 낮 활동 장소의 취향 반영도를 담음

## Status

Proposed

1. Proposed: 2026-10-21

ADR-0008의 결정 중 응답 모양(`places[안][일자][장소]`)만 바꾼다. 안의 구성(1안 규칙, 2안 취향, 3안 다양성), 일자 구조, 시드, 날씨 제외는 그대로다. 백엔드가 새 구조를 읽을 준비가 되기 전에는 배포하지 않는다.

## Context

- 현재 `POST /trips/place-selection`은 `data.places`가 `places[안][일자][장소]`의 3차원 배열이다(ADR-0008). 안 이름이 없고 인덱스 순서(0 규칙, 1 취향, 2 다양성)로만 구분한다.
- 기획은 여행자 화면에 2·3안이 취향을 얼마나 반영했는지 "내 취향 카테고리 N곳 / 새로 발견한 곳 M곳"으로 보여 주는 것이다. 사용자 결정으로 백엔드와 합의한 응답 계약은 1안을 `places`(2차원), 2·3안을 `routes`에 담고 안마다 `strategy`와 취향 반영도를 두는 형태다. 합의안과 달라진 곳이 두 군데 있다. 반영도는 정수 점수 하나(`preference_score`)였으나 N·M 두 값(`preference_count`, `discovery_count`)으로 바꾸기로 했고, 3안의 `strategy` 이름은 `BALANCED`였으나 `DIVERSITY`로 바꾸기로 했다. 두 변경을 백엔드가 전달받았는지는 확인하지 못했다.
- 응답의 장소는 이미 `matched_preferences`(그 장소를 고를 때 쓴 카테고리)와 `selected_for`(그 카테고리에 맞는 구성원)를 갖고 있고, 규칙 경로와 모델 경로가 같은 필드를 채운다. 그래서 N·M은 모델 내부 값 없이 완성된 일정만으로 센다.
- 하루 5곳은 식당 2곳과 낮 활동 3곳이고, 야간 조건을 만족하면 저녁 이후 1곳이 더해져 6곳이다. 마지막 날은 오전과 점심 2곳이다. 설문에는 식당 차원이 없다(ADR-0003).
- 3안은 규칙 경로에서 하루의 오후2 슬롯을 3위·4위 카테고리로 번갈아 바꾸고, 모델 경로에서는 낮 활동 후보에 3위·4위를 더해 모델이 고르게 한다(측정에서 3위·4위 비율 41.4~49.0%). 회피 조건으로 취향 상위 2개 카테고리의 후보가 모자라면 1·2안도 다음 순위로 보충한다(ADR-0006).
- 취향 반영의 대부분은 후보 제한이 하고, 학습 데이터에서 방문이 미션 기반 취향을 따르는 정도(lift)는 1.06이다. 모델이 취향에 더 맞게 골랐는지는 이 지표로 알 수 없다.
- 후보 조회는 저녁 이후 풀에 야간 type을 요구하고 낮 ACTIVITY 풀에서는 야간 type을 제외한다(규칙·모델 경로 모두). 장소 객체에는 저녁 이후 슬롯 표시가 없다.
- 확인하지 못한 것: 백엔드가 현재 `places`를 어떻게 읽는지, 새 구조를 읽을 준비가 된 시점, 화면 문구.

## Decision

우리는 응답을 다음 모양으로 바꾼다.

- `data.places`: 1안의 `[일자][장소]`(2차원).
- `data.routes`: 길이 2의 배열. `routes[0]`은 2안(`strategy: "PREFERENCE"`), `routes[1]`은 3안(`strategy: "DIVERSITY"`)이다. 각 항목은 `strategy`, `preference_count`, `discovery_count`, `days`(`[일자][장소]`, 배열 순서가 방문 순서)를 갖는다. 1안에는 반영도를 담지 않는다.
- `preference_count`와 `discovery_count`는 안 하나의 낮 활동 장소만 센다. 식당(FOOD)과 저녁 이후 장소는 어느 쪽에도 넣지 않는다. 매칭 카테고리가 그룹 취향 상위 2개에 속하면 `preference_count`, 속하지 않으면 `discovery_count`이며, 3안이 섞은 3·4위 카테고리와 회피 조건으로 보충한 다음 순위 카테고리가 모두 `discovery_count`에 들어간다.
- 저녁 이후 장소는 매칭 카테고리가 ACTIVITY이고 야간 type을 가진 장소로 알아본다.
- 안 단위 합계만 담고 일자별 값은 담지 않는다. `strategy` 값은 대문자 문자열이고 이 응답 전용 열거형으로 정의한다.

## Alternative / Considered Options

### 1. 기존 3차원 `places[안][일자][장소]`를 유지하고 반영도 배열을 따로 추가

- (장점) 응답 변경이 가장 작고 백엔드의 기존 읽기가 깨지지 않는다.
- (단점) 안 이름 없이 인덱스 순서에 의존하는 구조가 이어지고, 합의한 계약(1안 `places` + 2·3안 `routes`)과 다르다.
- (소결) 선택하지 않았다. 사용자가 합의한 계약을 따른다.

### 2. 반영도를 정수 점수 하나(`preference_score`)로 표현

- (장점) 필드가 하나고, N/(N+M)을 백분율로 정의하면 화면에서 한 숫자로 보여 줄 수 있다.
- (단점) 3안의 점수가 낮은 이유("일부러 취향 밖을 섞음")를 사용자에게 설명하기 어렵고, 기획 문구 "취향 N곳 / 새로 발견 M곳"과 맞지 않는다.
- (소결) 선택하지 않았다.

### 3. 일자별 N·M을 함께 담음

- (장점) 화면이 일자별 숫자를 보여 줄 수 있다.
- (단점) 일자마다 낮 활동 슬롯 수가 달라(마지막 날 1곳 등) 비교하기 어렵고 응답이 커진다.
- (소결) 선택하지 않았다. 필요해지면 필드를 추가한다.

### 4. 식당을 `preference_count`에 포함하거나 모든 장소를 셈

- (장점) 숫자가 크고 단순해진다.
- (단점) 식당은 취향 카테고리가 아니라서 취향 반영이 부풀려지고, 저녁 이후 슬롯은 일자마다 있고 없어 비교가 흔들린다.
- (소결) 선택하지 않았다.

### 5. 3안이 의도해서 섞은 3·4위 카테고리만 `discovery_count`로 셈

- (장점) "새로 발견한 곳"의 의미가 설계 의도와 정확히 맞는다.
- (단점) 장소마다 의도 표시 필드를 새로 달아야 하고, 설계가 바뀔 때마다 표시를 고쳐야 한다. 규칙·모델 경로와 모델 실패 폴백에 모두 적용해야 한다.
- (소결) 선택하지 않았다. 결과 기준으로 세므로 2안에도 보충 때문에 `discovery_count`가 0보다 클 수 있다.

## Consequences

### Positive (Gain)

- 안 이름(`strategy`)이 생겨 백엔드와 화면이 인덱스에 의존하지 않고 2·3안을 구분한다.
- 반영도가 완성된 일정만으로 계산되어, 안을 만든 경로(모델 또는 규칙 변형 폴백)와 무관하게 같은 정의가 적용된다.
- 3안의 `preference_count`가 2안보다 낮은 이유를 같은 화면에서 설명할 수 있다.

### Negative (Loss)

- 응답 형식이 바뀌어 백엔드가 `places`(2차원)와 `routes`를 읽도록 바꿔야 하고, 호환 단계 없이 한 번에 교체한다. 백엔드가 준비되기 전에 배포하면 읽기가 깨진다.
- `discovery_count`에 회피 조건으로 보충한 곳이 들어가므로 회피 조건이 많은 여행에서는 2안에도 0보다 클 수 있다. 화면 문구는 "내 상위 취향 밖의 곳"에 가까워야 정확하다.
- 모델 경로의 3안은 모델이 후보 중에서 고르므로 `discovery_count`가 규칙 경로(오후2 슬롯을 3·4위로 고정)보다 작아질 수 있다. 분포는 측정하지 않았다.
- 저녁 이후 장소를 type으로 알아보는 것은 후보 조회의 불변식(저녁 풀은 야간 type 필수, 낮 ACTIVITY 풀은 야간 type 제외)에 의존한다. 이 조회 규칙이 바뀌면 N·M이 틀어진다.
- 낮 활동 슬롯 수가 일자와 안마다 달라(마지막 날 1곳, 후보 부족으로 건너뛴 슬롯) N + M은 고정값이 아니다.
- 1안에는 반영도가 없어서 1안이 취향을 얼마나 반영했는지는 이 응답으로 알 수 없다.

## Compliance / Reconsideration Conditions

**결정사항 반영 여부 검증 기준**

- [x] 자동: 응답이 `places`(2차원)와 `routes`(`PREFERENCE`, `DIVERSITY` 순서, 안마다 `strategy`·`preference_count`·`discovery_count`·`days`)를 갖고, 두 값이 낮 활동 장소만 센다. 후보가 충분하면 2안의 `discovery_count`는 0이고 3안은 1 이상이다. `tests/test_place_selection_route.py`, `tests/test_taste_share.py`가 확인한다(2026-10-21).
- [ ] 수동: 합의안과 달라진 두 곳(`preference_score` → `preference_count`/`discovery_count`, `BALANCED` → `DIVERSITY`)을 백엔드에 전달했다. 확인하지 못함.
- [ ] 수동: 백엔드가 새 응답 구조를 읽을 준비가 된 뒤에 배포한다. 확인하지 못함.
- [ ] 수동: 화면 문구가 `discovery_count`에 보충한 곳이 포함됨을 반영한다.

**결정사항 반영 여부 측정 목록**

- [ ] 후보 조회 규칙(저녁 풀의 야간 type 요구, 낮 ACTIVITY 풀의 야간 type 제외)이 바뀌면 저녁 이후 장소 식별을 다시 검토한다.
