# ADR-0010: 2·3안을 항상 모델 경로로 만들고 장소 선정 모드 전환을 제거하되 실패한 안은 규칙 변형으로 채움

## Status

Proposed

1. Proposed: 2026-10-21

ADR-0008의 결정 중 "`PLACE_SELECTION_MODE`로 모델 경로를 켜고 끄며 기본값이 `rule`"인 부분만 바꾼다. 안의 구성(`[0]` 규칙, `[1]` 취향, `[2]` 다양성), 일자 구조, 시드, 날씨 제외는 그대로다. 1안의 선택 방식 변경은 별도 ADR로 다룬다.

## Context

- 현재 코드는 `settings.place_selection_mode`(`rule` 기본, `model`)로 2·3안을 만드는 방법을 가른다(`trip_orchestrator.py`). `rule`이면 2·3안은 모델 없이 평점 가중 정렬 상위 K=10곳 중 시드로 고른 규칙 변형이고, 이 모드에서는 RunPod을 부르지 않는다. `model`이면 안마다 GPU를 한 번씩(총 2번) 부르고, 실패하거나 결과가 유효하지 않으면 그 안만 규칙 변형으로 채운다.
- 운영 기본값이 `rule`이라 사용자가 받는 2·3안은 모델 결과가 아니다(2026-10-19 핸드오프 기준). 모델 경로는 측정만 했다: 전체 응답 최대 3.02초, 워커가 내려간 뒤 첫 요청 10.3초(n=1, 요청 직전 워커 0개를 확인하지 못한 추정), 유효 측정 요청 60건.
- 모델 평가: 최종용(free 조건, 한 번만 열음) 모델 13.8%, 인기순 5.9%, 규칙 2.5%. 서비스 조건(top2-slots, 개발용) 모델 5.9%, 규칙 2.4%, 인기순 5.5%로 인기순 대비 차이가 없다(ADR-0003, 0005, 0006). 취향 반영의 대부분은 후보 제한(ADR-0006)이 하고, 학습 데이터에서 방문이 미션 기반 취향을 따르는 정도는 lift 1.06이다.
- 기획은 2·3안의 취향 반영도(내 취향 카테고리 N곳, 새로 발견한 곳 M곳)를 응답에 담아 여행자 화면에 보여 주는 것이다. 반영도는 완성된 일정과 취향 입력만으로 계산하므로 어떤 경로가 안을 만들었든 같은 정의가 적용되어야 하지만, 2·3안이 규칙인지 모델인지에 따라 안의 내용이 달라진다.
- 엔드포인트가 일시 정지(Max Workers 0)이면 모든 요청이 `409 ENDPOINT_PAUSED`로 거절되고, 이때 모델이 한 번도 응답하지 못한 측정이 있었다. BE 응답 대기는 30초, GPU 호출 제한은 20초이며 서킷 브레이커는 연속 3회 실패 시 60초 차단한다.
- 가정: AWS 서버에는 CPU 경로(`model_dir`)를 배포하지 않아 폴백 순서는 GPU → 규칙 변형이다. 서버 환경변수와 RunPod 콘솔 값(Max Workers, Idle Timeout)은 확인하지 못했다.

## Decision

우리는 2·3안을 항상 모델 경로로 만든다. `PLACE_SELECTION_MODE`와 그 분기(`use_model`)를 제거하고, 모델 호출이 실패하거나 결과가 유효하지 않으면 그 안만 규칙 변형(K=10)으로 채우는 현재의 폴백은 유지한다. 모델 경로의 첫 장소 K=30(ADR-0007)과 안별 독립 폴백, 3개 안이 항상 나오는 성질은 그대로 둔다.

## Alternative / Considered Options

### 1. 현재 구조 유지 (`rule` 기본, 서버 환경변수로만 `model` 전환)

- (장점) 코드 변경이 없고, 모델 비용과 장애가 운영에 영향을 주지 않는다.
- (단점) 사용자가 받는 2·3안이 모델 결과가 아니고, 반영도를 보여 줄 안이 환경변수에 따라 달라진다.
- (소결) 선택하지 않았다. 사용자가 2·3안을 모델로만 구성하기로 했다.

### 2. 서버 환경변수만 `model`로 바꾸고 코드 기본값과 모드 분기는 유지

- (장점) 코드 변경이 가장 작고 되돌리기 쉽다.
- (단점) 모드 분기와 `rule` 경로의 2·3안 분기가 코드에 남고, 테스트가 환경변수에 의존하는 구조가 이어진다.
- (소결) 선택하지 않았다. 모드 스위치를 없애는 것이 사용자 결정이다.

### 3. 폴백까지 제거하고 모델 실패 시 오류(503)를 돌려줌

- (장점) 모든 안이 모델 결과라는 보장이 생긴다.
- (단점) GPU 장애(엔드포인트 일시 정지, 콜드 스타트 10.3초, 서킷 차단)가 곧 여행 일정 생성 실패가 된다. BE 제한 30초 안에 오류를 돌려주는 경우도 생긴다.
- (소결) 선택하지 않았다.

### 4. 실패한 안을 빈 배열로 둠

- (장점) 응답 모양이 유지되고 규칙 결과가 모델 결과로 오인되지 않는다.
- (단점) 사용자 화면에 안이 비어 보인다.
- (소결) 선택하지 않았다.

## Consequences

### Positive (Gain)

- 2·3안의 생성 경로가 하나가 되어 반영도 정의와 측정이 모드에 따라 달라지지 않는다.
- 모델 평가에서 규칙보다 앞선 최종용 결과(13.8% 대 2.5%)가 사용자 화면에 반영된다.
- 환경변수 하나(`PLACE_SELECTION_MODE`)와 `rule`/`model` 이중 테스트 구성이 사라진다.

### Negative (Loss)

- 서비스 조건(개발용)에서는 모델이 인기순 대비 차이가 없으므로(5.9% 대 5.5%) 모델 전환의 이득이 확인된 것은 최종용 한 조건뿐이다.
- 모든 place-selection 요청이 RunPod을 부르므로 요청마다 GPU 비용과 지연(전체 응답 최대 3.02초, 콜드 스타트 추정 10.3초)이 생긴다. 20초 타임아웃 직전에 실패해 규칙 변형을 돌린 최악의 경우가 BE 30초 안에 드는지는 측정하지 못했다.
- 모델 서버 설정이 잘못되어 있으면 매 요청에서 "모델 경로 실패, 규칙 변형으로 채움" 예외 로그가 남고 사용자는 규칙 변형 결과를 받는다. 장애가 겉으로 드러나지 않는다.
- `RUNPOD_MODEL_URL`이 없는 개발·테스트 환경에서도 모델 경로를 먼저 시도하므로, 테스트가 실제 RunPod을 부르지 않게 막는 장치(`tests/conftest.py`의 `no_real_model_route`)가 필요하다.
- `Settings`가 `.env`의 알 수 없는 키를 거부하므로(`extra_forbidden`), `PLACE_SELECTION_MODE`가 남아 있는 `.env`는 앱을 시작하지 못한다. OS 환경변수(ECS 태스크 정의)의 같은 이름은 영향이 없다.

## Compliance / Reconsideration Conditions

**결정사항 반영 여부 검증 기준**

- [x] 자동: 모델 경로가 실패하거나 결과가 유효하지 않으면 그 안만 규칙 변형으로 채워지고 3개 안이 항상 나온다. `tests/test_place_selection_route.py`가 확인한다(2026-10-21, 일반 테스트 755건 통과).
- [x] 자동: 테스트가 `runtime.get_router`를 직접 바꾸지 않으면 RunPod을 부르지 않는다. `tests/conftest.py`의 `no_real_model_route`가 막는다(전체 조합 테스트 실행 중 프로세스의 네트워크 연결이 로컬 MySQL뿐임을 확인).
- [ ] 수동: 서버 환경변수에 `RUNPOD_MODEL_URL`, `RUNPOD_MODEL_API_KEY`가 있고 `/trips/place-selection` 호출 로그에 "모델 경로 실패, 규칙 변형으로 채움"이 없다.
- [ ] 수동: 서버 환경변수와 `.env`에서 `PLACE_SELECTION_MODE`를 제거한다.

**결정사항 반영 여부 측정 목록**

- [ ] 서버 로그의 `route=gpu` 비율과 "모델 경로 실패" 횟수로 폴백 비율을 보고, 모델 경로가 대부분의 요청에서 쓰이지 않으면 이 결정을 재검토한다.
- [ ] place-selection 전체 응답이 BE 제한 30초를 넘는 요청이 있으면 GPU 호출 제한(20초)이나 병렬 구조를 재검토한다.
- [ ] 서비스 조건(개발용)에서 모델이 인기순 대비 차이가 없다는 평가가 운영 반응(재생성 요청 비율 등)으로도 이어지면 모델 경로의 가치를 다시 판단한다.
