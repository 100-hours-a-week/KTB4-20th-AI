# ADR-0000: 장소 선정을 LLM 없이 설문 점수 기반 결정론 규칙과 DB 조회로 구현

## Status

Accepted

1. Proposed: 2026-09-14
2. Accepted: 2026-09-21 (PR #14 머지)

## Context

**문제**

- 서비스는 그룹 여행자에게 AI로 일정(장소+동선)을 생성한다. 그룹원 각자가 15문항 5점 리커트 설문으로 취향을 입력한다.
- 장소 선정 단계의 입력은 전부 숫자다: 취향 점수, `rating`, `userRatingCount`.
- 초기에 팀은 AI 적용 프로젝트라는 이유로, 구체적 근거 없이 추천에 LLM을 적용하려 했다. 추천의 정의, 추천과 탐색의 차이, 추천에 LLM을 도입해야 할 근거를 설명하지 못했다.
- 프롬프트 기반 추천은 모델의 사전 지식과 지시문에 의존하므로 같은 입력에도 출력이 달라질 수 있고, 관리 비용이 높다. 근본적인 장소 추천이라 보기 어렵다는 점은 인지했으나 AI를 접목할 다른 대안을 파악하기 어려웠다.
- 설계 논의 중 "순위·필터는 규칙으로 만들 수 있는 영역인데 LLM 사용 근거가 부족하다"는 문제가 제기됐고, 역검증 결과 LLM 채택 근거가 "처음에 그렇게 선택했다"는 것 외에 확인되지 않았다.

**조건과 규모 (확인된 사실)**

- 결정 시점에 이미 고정된 사항: 그룹 점수 `평균 - 표준편차 × w`, 하루 5슬롯 구조, 카테고리별 후보 8~20개.
- 추천 정확도 수치 없음. 평점과 평가 수 기반으로 가장 높은 점수의 장소를 필터링해 제공한다.

**범위와 책임 경계**

- 범위: `POST /trips/place-selection`의 장소 선정.
- 범위 밖: photomissions, `course-recommendation`과 `precheck`(v1 미구현), v2 이후의 추천 모델 검토.

**가정 (확인되지 않음)**

- Proposed 날짜(2026-09-14)는 개발 착수일에 대한 사용자 진술이며, 채팅 기록과 git 이력에서 날짜를 확인하지 못했다.
- 결정 자체는 첫 소스 코드(2026-09-20, PR #14) 이전의 설계 단계에서 이루어졌다.

## Decision

우리는 v1 trips 장소 선정을 LLM 없이, 설문 점수 기반 결정론 규칙과 DB 조회로 구현한다. 설계 단계에서 LLM 도입 근거를 확인하지 못해, 첫 소스 코드(PR #14)부터 결정론으로 작성했다.

v1.0.3 기준 구성은 다음과 같다.

- 그룹 점수(공식은 ADR-0002)로 주간 카테고리 순위를 정하고, 이를 바탕으로 하루 슬롯 구조(오전, 점심, 오후 2칸, 저녁, 조건 충족 시 저녁 이후)를 결정한다.
- 후보는 사전 수집한 자체 DB에서 조회한다(ADR-0001).
- 회피조건은 type 제외 맵으로 DB 조회 단계에서 후보에서 제외한다.
- 카테고리 후보가 부족하면 다음 순위 카테고리에서 순차 보충하고, 저녁 이후 슬롯은 야간형 후보가 없으면 제거한다.
- 후보는 평점과 평가 수 기반 점수로 정렬한다.

## Alternative / Considered Options

### 1. LLM이 후보 중 장소를 직접 추천·선정

- (장점) 프롬프트만으로 구현이 빠르고, AI 적용 프로젝트 취지에 부합한다.
- (단점) 같은 입력에 다른 결과가 나올 수 있어 재현과 검증이 어렵고 관리 비용이 높다. 입력이 전부 숫자라 가중합으로 대체할 수 있어 LLM이 필요한 이유가 없었다.
- (소결) 기각.

### 2. 규칙으로 정하되 LLM이 비선형 판단(슬롯 간 균형, 그룹 맥락, 장소 성격)을 보완

- (장점) 규칙이 표현하지 못하는 판단을 추가할 수 있다.
- (단점) 세 가지 모두 규칙(types 재매핑 등)으로 구현 가능해 LLM이 필요한 지점이 확인되지 않았다.
- (소결) 기각.

### 3. 선정된 장소의 설명 문구를 LLM+RAG로 생성

- (장점) 장소별 설명을 자연스러운 문장으로 제공할 수 있다.
- (단점) 취향 기반 추천이라는 서비스 본래 취지와 관계가 없어 AI 도입 근거가 약하다.
- (소결) 기각. 설계 단계에서 한때 유지로 논의됐으나 이후 제외됐다.

## Consequences

### Positive (Gain)

- 카테고리 점수에 동점이 없는 입력은 항상 같은 결과를 반환해, 결과를 재현하고 검증할 수 있다.
- LLM의 확률적 출력에 따른 관리 비용과 LLM 호출 의존성이 trips 장소 선정에서 제거된다.
- 규칙을 테스트로 검증할 수 있다(슬롯 구성, 회피 type 제외, 장소 중복 없음).

### Negative (Loss)

- 같은 카테고리 안에서 그룹 취향이 장소 순위에 직접 반영되지 않고, 슬롯의 카테고리 배치에만 간접 반영된다. 카테고리 점수에 동점이 없고 지역, 카테고리 구성, 회피조건이 같으면 그룹이 달라도 같은 장소가 선정되며, 규칙 기반 추천은 조건이 같으면 같은 장소를 추천할 수밖에 없다.
- 결정론은 LLM의 확률적 생성을 배제한다는 의미이며, 카테고리 점수가 동점일 때의 순서는 무작위로 결정된다(`slot_plan.py`).
- 카테고리와 회피조건 규칙을 사람이 직접 분류하고 유지해야 한다. Google Places type을 전수 검토해 분류했고, 회피조건 제외 매핑도 수동으로 관리한다.
- 추천 품질을 판단할 정량 평가 기준이 없다.

## Compliance / Reconsideration Conditions

**결정사항 반영 여부 검증 기준**

- [ ] 자동(기존): CI의 `pytest`가 `/trips/place-selection`의 요청 검증(422)과 정상 응답(200)을 확인한다.
- [ ] 수동(기존): 릴리스 전 `pytest -m exhaustive`로 슬롯 구성, 점심·저녁 슬롯의 FOOD 배치, 회피 type 제외, 장소 중복 없음을 확인한다.
- [ ] 자동(제안, 미구현): `app/trips`에서 LLM SDK import를 금지하는 검사를 CI에 추가한다.
- [ ] 수동: trips 장소 선정에 LLM 호출을 추가하는 PR은 이 ADR을 대체하는 새 ADR을 먼저 작성한다.

**결정사항 반영 여부 측정 목록**

- [ ] 동점이 없는 입력에서 반복 호출 시 응답이 동일한지 (현재 자동화된 테스트 없음)
- [ ] 추천 품질 정량 지표 (현재 없음. 평가 기준이 생기면 이 결정의 재검토 조건으로 사용)
