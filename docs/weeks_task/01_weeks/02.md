# 설계

## 주요 키워드

전체 파이프라인 설계를 이해하려면 크게 5개 영역의 키워드가 필요함. 지금은 정의만 짧게 나열하고, 각 키워드가 왜 필요한지는 실제 설계 논의 단계에서 하나씩 짚는 게 순서에 맞음.

**표 142. 모델 서빙(model serving) 관련**
| 키워드 | 정의 |
|---|---|
| inference (추론) | 학습된 모델(또는 API로 호출하는 LLM)이 입력을 받아 결과를 산출하는 실행 단계 |
| endpoint (엔드포인트) | 클라이언트가 특정 기능을 호출하기 위해 접근하는 URL 단위 |
| latency (지연시간) | 요청을 보낸 시점부터 응답을 받는 시점까지 걸리는 시간 |
| throughput (처리량) | 단위 시간당 처리 가능한 요청 수 |
| synchronous / asynchronous (동기/비동기) | 요청을 순서대로 하나씩 처리할지, 여러 요청을 동시에 처리할지의 구분 |
| batching (배치 처리) | 여러 요청을 모아서 한 번에 처리하는 방식 |
| caching (캐싱) | 이전에 계산한 결과를 저장해뒀다가 동일 요청 시 재사용하는 방식 |
| cold start (콜드 스타트) | 서버가 요청을 처음 받을 때 초기화(모델 로딩 등)로 인해 발생하는 추가 지연 |

**표 143. 아키텍처(architecture) 관련**
| 키워드 | 정의 |
|---|---|
| monolith / microservice (모놀리식/마이크로서비스) | 모든 기능을 하나의 애플리케이션에 넣을지, 기능별로 독립된 서비스로 나눌지의 구분 |
| decoupling (디커플링) | 모듈 간 의존성을 낮춰서, 한쪽을 변경해도 다른 쪽에 영향이 적게 만드는 것 |
| service boundary (서비스 경계) | 어떤 기능까지를 하나의 모듈/서비스로 묶을지 정하는 기준선 |
| coupling / cohesion (결합도/응집도) | 모듈 간 서로 얼마나 의존하는지(결합도), 모듈 내부 요소가 얼마나 관련 있는지(응집도) |
| statelessness (무상태성) | 서버가 이전 요청의 상태를 기억하지 않고, 매 요청을 독립적으로 처리하는 성질 |

**표 144. 인프라·비용(cost) 관련 (예산 제약 반영)**
| 키워드 | 정의 |
|---|---|
| pay-per-use (사용량 기반 과금) | 실제 호출·사용한 만큼만 비용이 발생하는 과금 방식(LLM API, 서버리스 등) |
| serverless (서버리스) | 서버를 직접 상시 운영하지 않고, 요청이 있을 때만 실행되는 컴퓨팅 모델 |
| always-on server (상시 운영 서버) | EC2처럼 요청 유무와 관계없이 계속 켜져 있어 고정 비용이 드는 서버 |
| rate limit (요청 제한) | 일정 시간 내 허용되는 요청 수 상한(초과 시 과금 급증 또는 차단) |
| managed service / self-hosted (관리형 서비스/자체 호스팅) | 인프라 운영을 외부에 맡길지, 직접 서버를 구축·운영할지의 구분 |

**표 145. 성능 최적화(optimization) 관련**
| 키워드 | 정의 |
|---|---|
| profiling (프로파일링) | 코드 실행 중 어느 구간이 시간을 많이 쓰는지 측정하는 작업 |
| bottleneck (병목) | 전체 처리 속도를 가장 크게 제한하는 구간 |
| I/O bound / CPU bound | 지연의 원인이 입출력 대기(네트워크, 디스크)인지, 연산 자체의 부하인지의 구분 |
| concurrency / parallelism (동시성/병렬성) | 여러 작업을 번갈아 처리하는 것(동시성)과 실제로 동시에 실행하는 것(병렬성)의 구분 |
| connection pooling (커넥션 풀링) | 매번 새로 연결을 맺지 않고, 미리 만들어둔 연결을 재사용하는 방식 |

**표 146. 프레임워크·외부 API 관련**
| 키워드 | 정의 |
|---|---|
| ASGI / WSGI | 파이썬 웹 프레임워크가 비동기(ASGI) 요청을 처리할 수 있는지, 동기(WSGI)만 가능한지의 표준 규격 구분 |
| Pydantic | FastAPI에서 요청·응답 데이터의 타입과 형식을 검증하는 라이브러리 |
| OpenAPI (Swagger) | API 명세를 자동으로 문서화해주는 표준 규격 |
| third-party API dependency (외부 API 의존성) | 자체 구현 대신 외부 서비스(TourAPI, Google Maps 등) 호출로 기능을 구현할 때 생기는 의존 관계 |
| prompt caching | LLM API 호출 시 반복되는 프롬프트 앞부분을 캐싱해 비용·지연을 줄이는 기법 |

이 키워드들을 바탕으로 다음 단계에서 "우리 팀·우리 서비스" 관점의 워크플로우(사용자 요청 → AI 서버 처리 → 응답)를 그려보면서, 각 지점에 어떤 키워드가 왜 적용되는지 하나씩 짚어가는 방식으로 진행하면 될 것 같음.

## 예상 워크플로우 (사용자 요청 -> AI 서버 처리 -> 응답 순)

**표 147. 예상 워크플로우 (사용자 요청 → AI 서버 처리 → 응답)**
| 단계 | 주체 | 동작 | 관련 키워드 |
|---|---|---|---|
| 1. 요청 발생 | 프론트엔드 | 그룹장이 버튼 클릭 → 백엔드(Spring)로 "일정 생성 요청" 전송 | endpoint |
| 2. 요청 위임 | 백엔드 | 그룹 취향 벡터, 여행 조건(지역·날짜·인원)을 모아서 AI 서버로 전달 | service boundary, decoupling |
| 3. 외부 데이터 조회 | AI 서버 | TourAPI/Google Places에 장소 후보 조회 요청 | I/O bound, third-party API dependency |
| 4. 대기 처리 방식 | AI 서버 | 외부 API 응답을 기다리는 동안 다른 요청을 막지 않고 처리할지 결정 | synchronous/asynchronous, concurrency |
| 5. 3안 계산 | AI 서버 | 최단거리/취향우선/균형 3개 코스를 동시에 계산 | parallelism, batching |
| 6. 반복 요청 대비 | AI 서버 | 같은 지역·날짜 조합이 이미 조회된 적 있는지 확인 | caching |
| 7. 다수 그룹 처리 | AI 서버 | 여러 그룹이 동시에 요청을 보내는 상황을 감당 | throughput, connection pooling |
| 8. 응답 반환 | AI 서버 → 백엔드 → 프론트 | 3안 결과를 구조화된 형식으로 반환 | Pydantic, OpenAPI |
| 9. 상태 저장 여부 | 백엔드 | 계산된 3안을 누가, 어디에 저장하는지(AI 서버는 상태를 기억하는지) | statelessness |
| 10. 서버 유휴 시간 | 인프라 | 요청이 없는 시간에도 서버가 계속 켜져 있을지 | always-on server, serverless, pay-per-use |

여행방 상세 페이지에서 "AI 일정 생성하기"를 누르는 순간부터 경로 추천 페이지에 3개 카드가 뜨기까지의 흐름을 단계별로 나눔.

**흐름도 (텍스트)**

```
[프론트: AI 일정 생성하기 클릭]
        ↓ (1 endpoint)
[백엔드: 그룹 취향 벡터 + 여행 조건 취합]
        ↓ (2 service boundary)
[AI 서버: 요청 수신]
        ↓ (3 I/O bound)
[외부 API 호출: TourAPI / Google Places]
        ↓ (4 sync/async, 6 caching)
[장소 후보 확보]
        ↓ (5 parallelism, batching)
[3안 동시 계산: 최단거리 / 취향우선 / 균형]
        ↓ (8 Pydantic 응답 구조화)
[백엔드로 결과 반환]
        ↓ (9 statelessness: 결과를 어디에 저장할지)
[프론트: 경로 추천 페이지에 3개 카드 표시]
```

## 사용한 기술 및 근거

### 장소 추천

- 잘 분석, GCP 기준 186만 원
- 유저가 되고 싶은 상태
- 퀄리티
- 최적화 방향도 속도 vs 퀄리티
- 서비스 관점으로 설명할 필요
  - 포트폴리오를 단단하게 만들 수 있는 원리가 됨

### 여행 일정 생성

- FastAPI
  - ASGI 기반이라 asyncio.gather로 TourAPI·Google Places·Google Maps 호출을 동시에 보낼 수 있음. 독립적인 I/O bound 작업이기 때문임(장소 조회가 경로 계산 결과를 기다릴 필요 없음). 만약 프레임워크가 WSGI 기반(Flask 기본 등)이었다면 이 동시 처리를 프레임워크 차원에서 지원하지 않아 별도 스레드풀이 필요함.

- 캐시
  - 대상 1: 이름, 좌표, 카테고리 등 장소 메타데이터
    - 변동 빈도: 잘 변경되지 않음
    - 근거: TourAPI/Google Places 응답의 "실체"가 정적 정보이기 때문
    - TTL: 24시간
  - 대상 2: 혼잡도, 리뷰 수 등 동적지표
    - 변동 빈도: 매일 또는 실시간 변동
    - 근거: 혼잡도 예측 API 자체가 일일 단위 갱신임
    - TTL: 1시간 이내 또는 캐시 미사용
