# 단계 2: 모델 추론 성능 최적화

## 로컬 모델로 변경이 필요한 지점 우선순위 선정 및 이유

표 167. 로컬 모델 전환 우선순위
우선순위 | 엔드포인트 | 실시간 제약 | GPU 부하 요인 | 선택
-- | -- | -- | -- | --
1 | `photomissions/verify` | 상 | 상 | ✅
2 | `trips/place-selection`, `trips/course-recommendation` | 상 | 중 | ✅
3 | `photomissions/generate` | 하 | 중 | (후순위)
4 | `itineraries/revalidate` | 하 | 하 | (후순위)

**선정 이유**

1순위 — `photomissions/verify`
  - 실시간 제약: 사용자가 여행 중 사진을 찍고 결과를 기다려야 함.
  - GPU 부하 요인: 이미지 인코딩이 텍스트 모델보다 연산량이 큼. VLM(Vision-Language Model)은 양자화해도 정확도 유지가 까다로움.

2순위 — `trips/place-selection`, `trips/course-recommendation` (동일 모델 호출 예정)
  - 실시간 제약: 사용자가 버튼을 누르고 화면에서 대기해야 함.
  - GPU 부하 요인: 입력값이 수치화된 취향 벡터이므로 프롬프트 길이는 짧지만, 매번 실시간으로 돌아야 함.

## 제출 항목 1: 기존 모델의 추론 성능 지표

### 사용할 LLM/VLM API

v1에서는 **Gemini 3.1 Pro**를 채택했다.

선정 이유:
- 실측 비교: 동일한 그룹 취향 벡터 입력에 동일 프롬프트로 Gemini 3.1 Pro Preview와 Claude Sonnet 5를
  여러 차례 비교 테스트한 결과, 수치 기반 추론 정확도는 동등했고, 멤버 간 제약이 충돌하는
  케이스(한 멤버의 deal_breaker가 다른 멤버의 최우선 취향과 겹치는 경우)를 짚어내는 정확도는
  Gemini 쪽이 앞선 경우가 있었음. 단, 출력 형식을 강제하지 않으면 지정한 스키마를 벗어나는
  경향이 관찰되어, 구조화 출력을 반드시 함께 적용해야 함.
- 속도: 스트리밍 기준 초당 생성 토큰 수가 Sonnet 대비 약 5배 빠름(약 340 vs 69 tokens/sec).¹
  `photomissions/verify`처럼 사용자가 화면 앞에서 즉시 결과를 기다리는 엔드포인트,
  `trips/place-selection`, `trips/course-recommendation`의 로딩 체감 시간 단축에 직접 기여할 수 있을 것이라고 판단함.
- 비용: 입력 단가는 Sonnet과 동일($2/M 토큰), 출력 단가는 Sonnet이 근소하게 저렴($10 vs $12/M)하나,¹
  실제 프롬프트 크기(수백 토큰 수준)에서는 그 차이가 크지 않다고 판단함.
- 하나의 구독 안에서 Gemini 3.1 Pro(추론이 중요한 `trips/place-selection`, `trips/course-recommendation`)와 Flash 계열
  (가벼운 `photomissions` 엔드포인트)을 작업별로 나눠 쓸 수 있어, 단일 구독 제약 안에서도
  작업 난이도별 티어링이 가능함.

VLM(`photomissions/verify`)도 동일 provider 계열 사용한다.

> ¹ 속도·단가는 2026년 9월 조회 기준의 공개 벤치마크·공식 가격표 값이다. 벤치마크는 provider가 공개한 최대 성능 조건 기준이므로 우리 워크로드에서의 실제 값과는 다를 수 있고, 단가는 변경될 수 있다. 실제 값은 구현 후 아래 baseline 측정으로 확인한다.

아래 기준선(baseline)은 이 API를 대상으로 측정한다. 다만 구현 전이라 두 엔드포인트 모두
아직 실측 전이며, 여기서는 "무엇을 어떤 조건으로 측정할지"를 정의한다.

**photomissions/verify**
- 최적화 전 구성: EXIF 필터 없음, 원본 해상도 그대로 인코딩, 프롬프트 캐싱 없음, 순차 처리(배치 없음)
- 측정 조건: 평시(동시 요청 1건), 성수기(동시 요청 30~50건). 원본 해상도 / 리사이즈 적용을 나눠서 측정
- 측정 지표: 평균 latency, p95 latency, throughput, 랜드마크 인식 정확도

**trips/place-selection, trips/course-recommendation**
- 최적화 전 구성: 후보 장소 사전 필터링 없음, 캐싱 없음, 순차 처리(배치 없음), few-shot 예시 없음
- 측정 조건: 평시(동시 요청 1건), 특정 시간대 집중(동시 요청 20~30건)
- 측정 지표: 평균 latency, p95 latency, throughput, 구조화 출력 1차 성공률

두 엔드포인트 모두 실측값은 TBD 상태이며, 프로파일링 코드(제출 항목 2 참고)를 이 기준선 구성에 적용해 실제 수치 작성 계획

## 제출 항목 2: 식별된 성능 병목 요소와 그 원인에 대한 분석

**측정 구간 정의**

| 엔드포인트 | 측정 구간 |
|---|---|
| photomissions/verify | S3 이미지 다운로드 → EXIF 확인 → 이미지 전처리(리사이즈·인코딩) → 모델 추론(prefill+decode) → 응답 반환 |
| trips/place-selection, trips/course-recommendation | 후보 장소 조회 → 프롬프트 구성 → 모델 추론(prefill+decode) → 구조화 출력 파싱 → 응답 반환 |

측정 방법은 두 엔드포인트 공통으로, 각 구간 전후에 `time.perf_counter()`를 삽입해 로그로 수집함.

**예상 병목과 원인**

| 엔드포인트 | 예상 병목 | 원인 |
|---|---|---|
| photomissions/verify | 이미지 전처리(인코딩, prefill) | 원본 해상도가 클수록 인코더가 처리할 픽셀 수·이미지 토큰 수가 늘어남. 이미지는 텍스트보다 토큰 수가 훨씬 많아 prefill 비중이 큼 |
| photomissions/verify | 모델 추론(decode) | 응답 텍스트가 순차 생성되는 구조적 특성. 다만 출력이 짧아 텍스트 생성 엔드포인트보다 비중은 작을 것으로 예상 |
| photomissions/verify | S3 이미지 다운로드 | 서버 간 통신이라 빠를 것으로 예상되나, 원본 해상도가 크면 무시할 수 없을 수 있어 실측으로 확인 |
| trips/place-selection, trips/course-recommendation | 모델 추론(decode) 또는 구조화 출력 파싱 | decode: 장소 목록(키워드 위주, 반영 카테고리·사용자 ID 등)을 생성하나, 후보 수가 많으면 항목 수에 비례해 여전히 토큰 수 증가 가능 |

> **사용자 업로드는 이 측정 구간 밖이다.** AI 서버는 이미지 파일이 아니라 백엔드가 만들어 준 presigned URL을 받아 S3에서 내려받으므로, 사용자가 사진을 업로드하는 시간은 AI 서버가 대기하는 시간이 아니다. 다만 "사진을 찍고 결과를 볼 때까지"의 사용자 체감 시간에는 포함되므로, 업로드 전 리사이즈(제출 항목 3)는 AI 서버 성능과 별개로 체감 시간 개선에 기여한다.

두 엔드포인트 공통으로, 외부 요인(TourAPI/Google Places 응답 지연, 프롬프트 길이)과 모델 내부 요인(decode 속도)이 병목 후보로 겹치며, 실측 후 어느 쪽이 실제 지배적인 병목인지 확정할 예정임.

## 제출 항목 3: 적용할 최적화 기법의 구체적 계획

**공통 적용 기법**

| 기법 | photomissions/verify | trips/place-selection, trips/course-recommendation |
|---|---|---|
| 로컬 모델 | Qwen2.5-VL-7B-Instruct (GGUF Q4_K_M) | Qwen2.5-7B-Instruct (GGUF Q4_K_M) |
| 파인튜닝 | 보류 — 사용자 데이터 부재로 zero-shot 우선, 데이터 축적 후 착수 | 보류 — 동일 사유 |
| 동적 배치 | 대기창 50~200ms, 성수기 저녁 시간대 집중 대응 | 대기창 50~200ms, 특정 요일·시간대(평일 저녁, 주말) 집중 대응 |

**엔드포인트별 고유 기법**

**photomissions/verify**

| 기법 | 대응 병목 | 내용 |
|---|---|---|
| 이미지 리사이즈 (클라이언트 측, 업로드 전) | 인코딩(prefill) + S3 다운로드 | 앱에서 업로드 전에 리사이즈하면 이후 모든 단계의 입력 크기가 함께 줄어든다. 왜냐하면 AI 서버의 S3 다운로드, 이미지 인코딩(prefill)이 모두 파일 크기에 비례하기 때문이다. 추가로 사용자의 업로드 시간도 줄어 체감 시간이 개선된다. |
| EXIF GPS 우선 필터 | 모델 추론 (호출 자체 제거) | GPS가 있고 목표 좌표와 명백히 불일치하면 VLM 호출 없이 조기 반려한다. 단, EXIF는 자주 없다(메신저 전달 시 삭제, 위치 권한 거부, 스크린샷). 절감되는 것은 명백한 오답 케이스뿐이라 비중은 크지 않을 수 있어, 실측으로 조기 반려 비중을 확인한다 |
| 프롬프트 캐싱 (System Prompt) | prefill | 매 요청 동일한 시스템 프롬프트의 prefill 반복을 제거 |
| 출력 형식 강제 | decode | 생성 토큰 수 최소화 |

**trips/place-selection, trips/course-recommendation**

| 기법 | 내용 |
|---|---|
| 후보 장소 캐싱 (지역+카테고리) | 외부 API 응답 지연 대응 |
| 후보군 사전 필터링 (카테고리 상위 N개) | 프롬프트 길이 축소 |
| 구조화 출력 | LangChain/LangGraph `with_structured_output` 사용, 필요 시 GBNF로 전환 |
| Few-shot 예시 추가 | 구조화 출력 1차 성공률 개선 |
