## 배경

- AI 모델이 서비스에 통합하려면 안정적으로 호출할 수 있는 인터페이스 필요
- 안정적인 호출이란?
  - 서비스 간 구성 요소 간 경계를 명확히 구분
  - 모델을 다른 부분과 분리(decouple)하여 개별 및 배포에 용이
  - 모델 호출 로직이 뒤섞이지 않고 유지보수가 쉬움
  - 다른 서비스나 클라이언트가 모델 기능 활용하기 용이
  - 표준화된 API 형태로 확장성과 협업하기 쉬움.

## 과제

- 서비스 요구사항에 맞는 API 설계 및 구현
- RESTful API로 엔드포인트 정의
- 입출력를 구조적으로 문서화
- 오류 처리 방안
- 인증/권한 관리 고려

## ✅ 설계한 API의 엔드포인트 목록과 각 엔드포인트의 기능 설명

### 엔드포인트 목록

엔드포인트 목록
| 엔드포인트 | 기능 |
|---|---|
| `POST /trips/generate` | 그룹 멤버들의 취향 데이터를 받아, AI가 장소를 추천하고 최적 동선을 생성해 반환. 핵심 엔드포인트 |
| `POST /trips/{trips_id}/regenerate` | 장소 추가/삭제, 또는 멤버 나감·탈퇴 후 그룹 취향 반영률을 유지한 채 동선을 재조정 |
| `POST /trips/{trips_id}/precheck` | 출발 전날(D-1) 외부 요인의 이상 유무를 판정 (날씨 API 등 활용) |
| `POST /photomissions/generate` | 확정된 동선과 그룹 취향을 바탕으로 포토미션 목록 생성 |
| `POST /photomissions/{mission_id}/verify` | 제출된 사진을 Vision 기반으로 판정(성공/재시도유도/실패) |

가장 자주 호출되는 `/trips/generate`를 기준으로 상세 스펙을 정리한다.

## ✅ API의 입력(JSON 혹은 Proto 메시지 등)과 출력 형식에 대한 명세서 (스키마, 예시 포함)

### 설계 원칙: 정적 데이터 vs 동적 데이터

입력 스키마를 짤 때 필드마다 "이 값이 요청마다 바뀌는 값(동적)인지, 한 번 정해지면 안 바뀌는 값(정적)인지"를 먼저 구분했다. 정적인 값은 이미 그 값을 소유한 쪽(프론트엔드, 설문 정의 등)이 들고 있으면 되고, AI 서버는 계산에 실제로 쓰이는 동적인 값만 받는다.

설계 원칙
| 항목 | 정적/동적 | 판단 |
|---|---|---|
| 설문 문항 텍스트, 문항이 몇 개인지 | 정적 (최초 설정 후 고정) | AI에 안 보냄 — 프론트가 소유 |
| 카테고리 이름·순서 | 정적 (고정) | AI에 안 보냄 — 인덱스 순서로 고정, 코드 상수로만 공유 |
| 리커트 응답 점수 | 동적 (사용자마다 다름) | AI에 보냄 — `survey_result`가 이 값만 담는 이유 |

이 원칙에 따라 `survey_result`는 문항 텍스트나 카테고리 이름 없이 숫자 값(리커트 점수)만 담은 배열로 확정했다.

같은 기준을 다른 필드에도 적용해보면: `members[].nickname`도 사실 정적 데이터다(유저 프로필 정보라 요청마다 바뀌는 값이 아님). 원칙대로면 AI는 `user_id`만 받고, 결과의 `reason` 문구도 "지영님의 취향이 반영됐어요" 같은 완성된 문장 대신 `selected_for`(유저 ID)와 `matched_preferences`(취향 태그)만 주고, 닉네임을 채워 넣는 건 그 값을 소유한 백엔드가 하는 게 원칙적으로는 더 맞다. 다만 지금 설계는 LLM이 "지영님과 채령님의 취향이 겹쳐서 골랐어요"처럼 상황마다 다르게 서술하는 문장까지 한 번에 생성하는 걸 의도했어서, 이 경우엔 닉네임을 예외적으로 유지했다.

### 입력 (`POST /trips/generate`)

```json
{
  "room_id": "room_20260826_001",
  "region": "경주",
  "date_range": { "start": "2026-08-26", "end": "2026-08-26" },
  "members": [
    {
      "user_id": "u_daniel",
      "nickname": "Daniel",
      "survey_result": [4, 3, 5, 2, 2, 3, 5, 4, 5, 1, 1, 2, 3, 3, 4],
      "deal_breakers": ["시끄러운_곳", "실내_활동"],
      "must_visit": [{ "place_query": "황리단길" }]
    },
    {
      "user_id": "u_jiyoung",
      "nickname": "지영",
      "survey_result": [5, 5, 4, 3, 2, 3, 2, 2, 1, 1, 1, 1, 2, 2, 3],
      "deal_breakers": [],
      "must_visit": []
    }
  ]
}
```

### 타입 정의 (Pydantic)

```python
from pydantic import BaseModel, Field

class MustVisit(BaseModel):
    place_query: str

class Member(BaseModel):
    user_id: str
    nickname: str
    survey_result: list[int] = Field(min_length=15, max_length=15)
    deal_breakers: list[str]   # 필수 필드. 값 자체는 빈 리스트[] 허용
    must_visit: list[MustVisit]  # 필수 필드. 값 자체는 빈 리스트[] 허용

class DateRange(BaseModel):
    start: str  # YYYY-MM-DD
    end: str    # YYYY-MM-DD

class GenerateRequest(BaseModel):
    room_id: str
    region: str
    date_range: DateRange
    members: list[Member] = Field(min_length=1)
```

- `survey_result`: 카테고리 5개×문항 3개 리커트 척도 원본 응답을 고정된 순서의 정수 배열(15개, 항상 이 길이)로 담는다. 문항 텍스트나 카테고리 이름 같은 정적 메타데이터는 프론트엔드가 이미 갖고 있으므로 백엔드·AI 서버는 계산에 필요한 숫자 값만 주고받는다(백엔드 ERD 복잡도를 늘리지 않기 위한 결정). 인덱스 0~2=문화·역사, 3~5=자연·힐링, 6~8=미식, 9~11=액티비티, 12~14=편의·쇼핑 순서로 고정하며, 이 순서 자체가 프론트·백엔드·AI 세 팀이 공유하는 계약이므로 코드에 상수로 박아두고 어느 한쪽에서 임의로 바꾸지 않는다. (2026-09-02 팀 논의로 확정, 백엔드와 세부 필드명은 추후 재확인 예정)

### 출력 (`POST /trips/generate`)

```json
{
  "success": true,
  "request_id": "a3f9e21c-4b8e-4a2b-9e7a-1d6f8b2c0e91",
  "trips_id": "it_20260826_001",
  "places": [
    {
      "order": 1,
      "place_id": "kko_38211",
      "name": "경주역",
      "category": "관광명소",
      "distance_to_next_m": 7700,
      "selected_for": [],
      "matched_preferences": []
    },
    {
      "order": 2,
      "place_id": "kko_90142",
      "name": "황리단길",
      "category": "관광명소",
      "distance_to_next_m": 40,
      "selected_for": ["u_jiyoung"],
      "matched_preferences": ["문화_역사"]
    }
  ],
  "meta": {
    "model": "<llm-provider-tbd>",
    "prompt_version": "preference-synthesis-v1",
    "generation_time_ms": 4820,
    "validation": { "schema_passed": true },
    "retry_count": 0
  }
}
```

```python
class Place(BaseModel):
    order: int
    place_id: str
    name: str
    category: str
    distance_to_next_m: int # 마지막 장소는 다음이 없으므로 0
    selected_for: list[str] # 빈 리스트[] 가능 — 전체 공통 선택이면 빈 배열
    matched_preferences: list[str] # 빈 리스트[] 가능

class Validation(BaseModel):
    schema_passed: bool

class Meta(BaseModel):
    model: str
    prompt_version: str
    generation_time_ms: int
    validation: Validation
    retry_count: int

class GenerateResponse(BaseModel):
    success: bool
    request_id: str
    trips_id: str
    places: list[Place]
    preference_scores: dict[str, float]  # key=user_id, value=0~1
    meta: Meta
```

- `success` / `request_id`: 모든 응답 공통 봉투(envelope). `request_id`는 로그 추적과 실패 재현에 쓴다.
- `selected_for` / `matched_preferences` / `reason`: 각 장소가 누구의 어떤 취향으로 선정됐는지를 명시한다. 결과 화면의 추천 근거 카드("지영님의 '전시' 취향이 반영됐어요")가 이 필드를 그대로 렌더링한다.
- (참고) 장소 영업시간 데이터의 `confidence`는 AI 서버 내부에서 하드/소프트 제약 판단에만 쓰고, 이 응답엔 노출하지 않는다.
- `preference_scores`: 멤버별 취향 반영률. 그룹 내 편차를 감지하고, 이후 `/regenerate` 호출이나 동선 투표 동률 발생 시 판단 근거로 재사용된다.
- `meta`: 처리 과정 정보(모델·프롬프트 버전·소요시간·검증 통과 여부·재시도 횟수). 2단계(추론 성능 최적화) 과제에서 프롬프트 버전별 성능을 비교할 때 이 필드를 근거로 쓴다.

### 입력 (`POST /trips/precheck`)

```json
{
  "trip_id": "trip_20260826_001",
  "region": "경주",
  "today": "2026-08-25",
  "place_ids": ["kko_38211", "kko_90142", "kko_60193"]
}
```

```python
class PrecheckInput(BaseModel):
    trip_id: str
    region: str
    today: str  # YYYY-MM-DD, Spring이 관찰한 원본 현재 날짜
    place_ids: list[str]
```

- `today`: Spring이 자체 시계(Asia/Seoul 기준, 표279 정책)로 판단한 오늘 날짜. 가공 없이 그대로 전달. AI 서버는 `today + 1일`을 D-day(출발일)로 간주해 판정 대상 날씨를 계산함.
- `place_ids`: 현재 확정된 동선에 포함된 장소 ID 목록, 날씨 캐시(지역+시간대) 조회 시, 이 장소들이 실외/실내인지 등 판정 대상 범위를 좁히는데 사용

### 출력 (`POST /trips/precheck`)

```json
{
  "has_issue": true,
  "affected_place_ids": ["kko_38211"],
  "reasons": ["weather_risk", "closure_risk"]
}
```

```python
class PrecheckReason(str, Enum):
    WEATHER_RISK = "weather_risk" # 이상 날씨
    CLOSURE_RISK = "closure_risk" # 정기 휴무/임시휴업 등 운영 중단
    CONGESTION_RISK = "congestion_risk" # TODO: 혼잡도 예측

class PrecheckOutput(BaseModel):
    has_issue: bool
    affected_place_ids: list[str]
    reasons: list[PrecheckReason]
```

- `has_issue`: 문제 여부. false면 affected_place_ids, reasons 모두 빈 배열
- `affected_place_ids`: 문제로 판정된 장소만 나열(전체 동선이 아님). 이 단계에서 대체 장소는 계산하지 않음
- `reasons`: 문제로 판정된 원인 전체를 나열(하나의 장소가 여러 사유에 동시 해당될 수 있음). has_issue가 false면 빈 배열

### 그 외 엔드포인트 요약 명세

핵심 엔드포인트만큼 상세하진 않지만, 나머지 4개도 요청/응답 필드는 아래처럼 정의한다.

**`POST /trips/{trips_id}/regenerate`**

```json
// 요청 — 멤버 이탈로 재조정하는 경우
{
  "trigger": "member_left",
  "member_id": "u_jiyoung"
}
```

```json
// 요청 — 장소 추가로 재조정하는 경우
{
  "trigger": "place_added",
  "place_query": "동궁과 월지"
}
```

```json
// 요청 — 장소 삭제로 재조정하는 경우
{
  "trigger": "place_removed",
  "place_id": "kko_90142"
}
```

```json
// 응답 — generate와 완전히 동일한 shape
{
  "trips_id": "it_20260826_001",
  "places": ["..."],
  "preference_scores": { "...": "..." }
}
```

"트리거별로 필수 필드가 달라진다"는 규칙은 표보다 discriminated union(태그된 유니온)으로 표현하는 게 더 정확하다. `trigger` 값(태그)마다 별도 타입을 두면, 잘못된 조합(예: `place_added`인데 `member_id`가 옴)은 애초에 타입 검증에서 걸러진다.

```python
from typing import Literal

class PlaceAdded(BaseModel):
    trigger: Literal["place_added"]
    place_query: str

class PlaceRemoved(BaseModel):
    trigger: Literal["place_removed"]
    place_id: str

class MemberLeft(BaseModel):
    trigger: Literal["member_left"]
    member_id: str

class MemberRemoved(BaseModel):
    trigger: Literal["member_removed"]
    member_id: str

RegenerateRequest = PlaceAdded | PlaceRemoved | MemberLeft | MemberRemoved
RegenerateResponse = GenerateResponse  # generate와 완전히 동일한 shape
```

- `place_id` / `place_query`가 없으면 어떤 장소가 추가·삭제됐는지 AI가 알 방법이 없어서, 트리거별로 필수 필드를 다르게 뒀다.
- 응답이 `generate`와 완전히 같은 이유: 재조정도 결국 바뀐 조건으로 동선을 다시 만드는 것이라 새 스키마를 따로 만들 이유가 없다.

**`POST /photomissions/generate`**

```json
// 요청
{ "trips_id": "it_20260826_001" }
```

```json
// 응답
{
  "missions": [
    {
      "mission_id": "ms_001",
      "place_id": "kko_90142",
      "description": "함께 그룹 사진 찍기",
      "scope": "group"
    },
    {
      "mission_id": "ms_002",
      "place_id": "kko_38211",
      "description": "지역 대표 음식 촬영하기",
      "scope": "individual"
    }
  ]
}
```

```python
class Mission(BaseModel):
    mission_id: str
    place_id: str
    description: str
    scope: Literal["group", "individual"]

class PhotoMissionGenerateRequest(BaseModel):
    trips_id: str

class PhotoMissionGenerateResponse(BaseModel):
    missions: list[Mission]
```

- `scope`가 `group`이면 멤버 1명만 완료해도 전체 완료 처리, `individual`이면 각자 완료해야 한다.
- `description`엔 의도적으로 인원수를 넣지 않는다. 등록 인원과 실제 참여 인원이 다를 수 있어서(예: 일정 겹침으로 일부만 참여), 인원수를 박아넣으면 문구 자체가 틀린 말이 될 수 있다.

**`POST /photomissions/{mission_id}/verify`**

```json
// 요청
{ "image_url": "https://cdn.planit.internal/uploads/xyz.jpg" }
```

```json
// 응답
{
  "result": "success",
  "match_score": 0.92,
  "landmark": { "name": "첨성대", "fact": "신라시대 천문관측대로 알려진..." },
  "message": "사진에서 유적지가 확인됐어요"
}
```

```python
class Landmark(BaseModel):
    name: str
    fact: str

class VerifyRequest(BaseModel):
    image_url: str

class VerifyResponse(BaseModel):
    result: Literal["success", "retry", "fail"]
    match_score: float  # 0~1
    landmark: Landmark | None  # 랜드마크 인식 성공 시에만 채워짐
    message: str
```

- `result`: `success` | `retry` | `fail` 3단계. 이분법(성공/실패)이 아니라 애매한 신뢰도 구간을 `retry`로 따로 둔다.
- `landmark`: 랜드마크 인식에 성공했을 때만 채워지는 nullable 필드.

**`POST /trips/{trips_id}/precheck`**

```json
// 요청
{ "check_date": "2026-08-25" }
```

```json
// 응답
{
  "has_changes": true,
  "changes": [
    {
      "original_place_id": "kko_38211",
      "reason": "폭우 예보로 실외 장소 방문이 어려움",
      "replacement_place_id": "kko_55201"
    }
  ]
}
```

```python
class Change(BaseModel):
    original_place_id: str
    reason: str
    replacement_place_id: str

class precheckRequest(BaseModel):
    check_date: str  # YYYY-MM-DD

class precheckResponse(BaseModel):
    has_changes: bool
    changes: list[Change]  # 필수 필드, has_changes가 False면 빈 리스트
```

- 출발 전날(D-1) 배치가 이 엔드포인트를 호출해 날씨 문제로 대체가 필요한 장소만 뽑아 돌려준다. `has_changes`가 `false`면 원래 동선 그대로 진행한다.

## ✅ 해당 API가 서비스 전체 구조에서 차지하는 역할과 연동 관계에 대한 설명

### 서비스 구조에서의 역할

```
[프론트엔드] → [백엔드 서버]  --(내부 API, 위 엔드포인트)-->  [AI 서버]
                    ▲                                    │
                    │ (2) 영업시간 배치 조회                 │
                    │  Phase 4: /internal/places/       ▼
                    │  opening-hours:batchGet         [LLM Provider]
                    └──────────────────────────────   [지도/장소 API] (1) 후보 검색
```

백엔드는 여행방·설문 데이터를 모아 위 입력 스키마로 변환해 AI 서버를 호출하고, 응답을 그대로 저장했다가 프론트엔드에 전달한다. AI 서버는 사용자에게 직접 노출되지 않는 내부 서비스이며, 백엔드-AI 서버 간 통신은 Bearer 토큰으로 인증한다.

**호출 방향이 한 곳에서 뒤집힌다.** `/trips/generate` 처리 중 AI 서버는 (1) 지도 API로 후보 장소를 실시간 검색한 뒤, (2) 후보들의 영업시간을 확인하려고 백엔드가 제공하는 Phase 4 조회 API(`/internal/places/opening-hours:batchGet`, 장소 영업시간 데이터 파이프라인 문서 참고)를 호출한다. 이 지점만 AI→백엔드 방향이라, 백엔드가 API를 설계할 때 "우리도 AI 서버로부터 호출을 받는 엔드포인트가 하나 있다"는 걸 알고 있어야 한다.

### 오류 처리 / 인증

- 인증: 서비스 간 호출이므로 사용자 로그인 토큰이 아닌 별도 내부 서비스 토큰(Bearer)을 사용한다.
- 입력 검증: Pydantic 스키마로 검증, 실패 시 422 + 필드별 에러 메시지
- LLM 응답 파싱 실패: 내부적으로 재시도(최대 N회) 후에도 실패하면 500 + 재시도 안내
