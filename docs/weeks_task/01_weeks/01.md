## 배경

- AI 모델이 서비스에 통합하려면 안정적으로 호출할 수 있는 인터페이스 필요
- 안정적인 호출이란?
  - 서비스 간 구성 요소 간 경계를 명확히 구분
  - 모델을 다른 부분과 분리(decouple)하여 개별 및 배포에 용이
  - 모델 호출 로직이 뒤섞이지 않고 유지보수가 쉬움
  - 다른 서비스나 클라이언트가 모델 기능 활용하기 용이
  - 표준화된 API 형태로 확장성과 협업하기 쉬움.

## 과제

- 서비스 요구사항에 맞는 API 설계 및 구현
- RESTful API로 엔드포인트 정의
- 입출력를 구조적으로 문서화
- 오류 처리 방안
- 인증/권한 관리 고려

## ✅ 설계한 API의 엔드포인트 목록과 각 엔드포인트의 기능 설명

### 엔드포인트 목록

엔드포인트 목록
| 엔드포인트 | 기능 |
|---|---|
| `POST /trips/generate` | 그룹 멤버들의 취향 데이터를 받아, AI가 장소를 추천하고 최적 동선을 생성해 반환. 핵심 엔드포인트 |
| `POST /trips/course-recommendation` | 장소 추가/삭제, 또는 멤버 나감·탈퇴 후 그룹 취향 반영률을 유지한 채 동선을 재조정 |
| `POST /trips/{trips_id}/precheck` | 출발 전날(D-1) 외부 요인의 이상 유무를 판정 (날씨 API 등 활용) |
| `POST /photomissions/generate` | 확정된 동선과 그룹 취향을 바탕으로 포토미션 목록 생성 |
| `POST /photomissions/{mission_id}/verify` | 제출된 사진을 Vision 기반으로 판정(성공/재시도유도/실패) |

가장 자주 호출되는 `/trips/generate`를 기준으로 상세 스펙을 정리한다.

### 설계 원칙: 정적 데이터 vs 동적 데이터

입력 스키마를 짤 때 필드마다 "이 값이 요청마다 바뀌는 값(동적)인지, 한 번 정해지면 안 바뀌는 값(정적)인지"를 먼저 구분했다. 정적인 값은 이미 그 값을 소유한 쪽(프론트엔드, 설문 정의 등)이 들고 있으면 되고, AI 서버는 계산에 실제로 쓰이는 동적인 값만 받는다.

설계 원칙
| 항목 | 정적/동적 | 판단 |
|---|---|---|
| 설문 문항 텍스트, 문항이 몇 개인지 | 정적 (최초 설정 후 고정) | AI에 안 보냄 — 프론트가 소유 |
| 카테고리 이름·순서 | 정적 (고정) | AI에 안 보냄 — 인덱스 순서로 고정, 코드 상수로만 공유 |
| 리커트 응답 점수 | 동적 (사용자마다 다름) | AI에 보냄 — `survey_result`가 이 값만 담는 이유 |

이 원칙에 따라 `survey_result`는 문항 텍스트나 카테고리 이름 없이 숫자 값(리커트 점수)만 담은 배열로 확정했다.

같은 기준을 다른 필드에도 적용해보면: `members[].nickname`도 사실 정적 데이터다(유저 프로필 정보라 요청마다 바뀌는 값이 아님). 원칙대로면 AI는 `user_id`만 받고, 결과의 `reason` 문구도 "지영님의 취향이 반영됐어요" 같은 완성된 문장 대신 `selected_for`(유저 ID)와 `matched_preferences`(취향 태그)만 주고, 닉네임을 채워 넣는 건 그 값을 소유한 백엔드가 하는 게 원칙적으로는 더 맞다. 다만 지금 설계는 LLM이 "지영님과 채령님의 취향이 겹쳐서 골랐어요"처럼 상황마다 다르게 서술하는 문장까지 한 번에 생성하는 걸 의도했어서, 이 경우엔 닉네임을 예외적으로 유지했다.

- `survey_result`: 카테고리 5개×문항 3개 리커트 척도 원본 응답을 고정된 순서의 정수 배열(15개, 항상 이 길이)로 담는다. 문항 텍스트나 카테고리 이름 같은 정적 메타데이터는 프론트엔드가 이미 갖고 있으므로 백엔드·AI 서버는 계산에 필요한 숫자 값만 주고받는다(백엔드 ERD 복잡도를 늘리지 않기 위한 결정). 인덱스 0~2=문화·역사, 3~5=자연·힐링, 6~8=미식, 9~11=액티비티, 12~14=편의·쇼핑 순서로 고정하며, 이 순서 자체가 프론트·백엔드·AI 세 팀이 공유하는 계약이므로 코드에 상수로 박아두고 어느 한쪽에서 임의로 바꾸지 않는다.
```python
class ResponseStatus(str, Enum):
    OK = "OK"
    INVALID_INPUT = "INVALID_INPUT"
    SERVER_ERROR = "SERVER_ERROR"

    @property
    def code(self) -> int:
        return {
            ResponseStatus.OK: 200,
            ResponseStatus.INVALID_INPUT: 422,
            ResponseStatus.SERVER_ERROR: 500,
        }[self]

    @property
    def message(self) -> str:
        return {
            ResponseStatus.OK: "select_success",
            ResponseStatus.INVALID_INPUT: "select_failed",
            ResponseStatus.SERVER_ERROR: "internal_error",
        }[self]

class ResponseData(BaseModel):
    places: list[Place]

class GenerateResponse(BaseModel):
    status_data: ResponseStatus
    data: ResponseData
```

- `status_data`: 모든 응답 공통 상태 값(ResponseStatus). 상태 코드(`.code`)와 메시지(`.message`)가 1:1로 묶여 있어, 응답 상태가 항상 일관되게 표현된다.
- `selected_for` / `matched_preferences`: 각 장소가 누구의 어떤 취향으로 선정됐는지를 키워드(user_id, 카테고리)로만 명시한다. 결과 화면의 추천 근거 카드("지영님의 '전시' 취향이 반영됐어요")는 이 키워드를 고정 문장 템플릿에 대입해 Spring/프론트가 조립하며, AI 서버는 자연어 문구를 생성하지 않는다.
- (참고) 장소 영업시간 데이터의 `confidence`는 AI 서버 내부에서 하드/소프트 제약 판단에만 쓰고, 이 응답엔 노출하지 않는다.
- 처리 과정 정보(모델·프롬프트 버전·소요시간·검증 통과 여부·재시도 횟수)는 AI 서버 자체 로그로만 기록되며, 이 응답에는 포함하지 않는다.

```python
class ExternalFactor(BaseModel):
    place_id: str
    weather_risk: bool
    congestion_level: Literal["low", "medium", "high"]

class CourseRecommendationRequest(BaseModel):
    region: E_Region
    start_date: str
    end_date: str
    members: list[Member_Survey]        # 그룹장 편집으로 추가된 장소는 그룹장의 must_visit에 포함됨
    external_factors: list[ExternalFactor]  # 신규
```

- `external_factors`: 날씨·혼잡도 등 외부 변수 데이터를 장소 단위로 전달한다. 외부요인우선 코스 계산 시에만 사용되며, 취향우선 코스 계산에는 관여하지 않는다.
- 동선 편집(장소 추가)으로 발생하는 고정 방문지는 별도 필드 없이, `members[]` 중 그룹장의 `must_visit`에 포함되어 전달된다.

```python
class E_CourseType(str, Enum):
    PREFERENCE = "preference"
    EXTERNAL = "external"


class Course(BaseModel):
    course_type: E_CourseType
    places: list[Place]


class CourseRecommendationData(BaseModel):
    courses: list[Course]


class CourseRecommendationResponse(BaseModel):
    status_data: ResponseStatus
    data: CourseRecommendationData
```

- `courses`: 취향우선(`preference`)과 외부요인우선(`external`) 두 코스가 배열로 함께 반환된다. 최단거리 코스(1안)는 Spring이 별도로 계산하므로 이 응답에 포함되지 않는다.
- `course_type`: 어느 기준으로 생성된 코스인지 식별하는 값이다. 프론트는 경로 추천 페이지의 카드 중 이 값을 기준으로 취향우선/외부요인 카드를 매핑한다.

```python
class PrecheckInput(BaseModel):
    trip_id: str
    region: str
    today: str  # YYYY-MM-DD, Spring이 관찰한 원본 현재 날짜
    place_ids: list[str]
```

- `today`: Spring이 자체 시계(Asia/Seoul 기준, 표279 정책)로 판단한 오늘 날짜. 가공 없이 그대로 전달. AI 서버는 `today + 1일`을 D-day(출발일)로 간주해 판정 대상 날씨를 계산함.
- `place_ids`: 현재 확정된 동선에 포함된 장소 ID 목록, 날씨 캐시(지역+시간대) 조회 시, 이 장소들이 실외/실내인지 등 판정 대상 범위를 좁히는데 사용

```json
        "displayName": { "text": "경주역", "languageCode": "ko" },
        "location": { "latitude": 35.8382, "longitude": 129.2039 },
        "types": ["tourist_attraction"],
        "selected_for": [],
        "matched_preferences": []

    "reasons": [
      { "category": "weather_risk", "detail": "heavy_rain" },
      { "category": "closure_risk", "detail": "temporary_closure" }
```

```python
class PrecheckReason(str, Enum):
    WEATHER_RISK = "weather_risk" # 이상 날씨
    CLOSURE_RISK = "closure_risk" # 정기 휴무/임시휴업 등 운영 중단
    CONGESTION_RISK = "congestion_risk" # TODO: 혼잡도 예측

class E_Weather_Detail(str, Enum):
    HEAVY_RAIN = "heavy_rain"
    HEAVY_SNOW = "heavy_snow"

class E_Closure_Detail(str, Enum):
    TEMPORARY_CLOSURE = "temporary_closure"
    REGULAR_HOLIDAY = "regular_holiday"

class Precheck_Reason(BaseModel):
    category: PrecheckReason
    detail: E_Weather_Detail | E_Closure_Detail  # E_Weather_Detail 또는 E_Closure_Detail 등 카테고리별 상세값, 추후 외부요인 추가될 수 있음.

class PrecheckData(BaseModel):
    has_issue: bool
    affected_place_ids: list[Place]
    reasons: list[PrecheckReason]

class PrecheckResponse(BaseModel):
    status_code: E_Response_Status_Code
    data: PrecheckData
```

- `has_issue`: 문제 여부. false면 affected_place_ids, reasons 모두 빈 배열
- `affected_place_ids`: 문제로 판정된 장소만 나열(전체 동선이 아님). 이 단계에서 대체 장소는 계산하지 않음
- `reasons`: 문제로 판정된 원인 전체를 나열(하나의 장소가 여러 사유에 동시 해당될 수 있음). has_issue가 false면 빈 배열

**타입 정의**

```python
class DisplayName(BaseModel):
    text: str
    languageCode: str


class MissionPlace(BaseModel):
    id: str                                  # place-selection 응답의 Place.id 그대로
    displayName: DisplayName                 # place-selection 응답의 Place.displayName 그대로
    selected_for: list[str]                  # 빈 배열 허용
    matched_preferences: list[T_Preference]  # 빈 배열 허용


class PhotoMissionGenerateRequest(BaseModel):
    itinerary_id: str

```

- `places`가 필요한 이유: 엔드포인트 설명("확정된 동선과 **그룹 취향**을 바탕으로 미션 생성")대로면 그룹 취향 정보가 있어야 하는데, `itinerary_id` 하나만으로는 AI 서버가 그걸 알 방법이 없다. 대신 `place-selection` 응답에 이미 나왔던 `matched_preferences`를 백엔드가 그대로 다시 넣어준다. 설문 원본(`survey_result`)을 다시 보낼 필요 없이, 이미 계산해둔 결과를 재사용하는 것이다.
- 멤버 정보(닉네임 등)는 받지 않는다. 미션 문구에 사람 이름을 넣지 않기 때문이다.
- `selected_for`는 현재 미션 생성에 쓰이지 않는다. `place-selection` 응답 구조를 그대로 받는다는 원칙 때문에 필드는 유지한다.
- `id`/`displayName`과 취향 정보만 받고 좌표·`types` 같은 나머지 필드는 안 받는다. 미션 생성엔 "어느 장소에서 어떤 취향이 반영됐는지"만 필요하기 때문이다.
- 필드명과 구조는 `place-selection` 응답을 그대로 쓴다.

```python
class Mission(BaseModel):
    mission_id: str                        # "ms_" + 12자리 16진수
    place_id: str
    description: str
    scope: Literal["PERSONAL", "GROUP"]
    primary_category: T_Preference | None  # 대표 카테고리. matched_preferences가 비어 있으면 null


class PhotoMissionGenerateResponse(BaseModel):
    missions: list[Mission]
```

- `scope`: `GROUP`이면 대표 사진 한 장으로 전원 완료 처리되고, `PERSONAL`이면 각자 자기 사진을 따로 제출해야 완료된다. 모델이 미션 문구와 함께 정하며, 기준은 "한 사람이 낸 사진이 다른 사람 몫을 대신할 수 있는가" 하나다(건물·풍경처럼 누가 찍어도 같은 대상이면 `GROUP`, 사람마다 답이 달라야 하면 `PERSONAL`).
- `primary_category`가 필요한 이유: verify 응답에서 `message`를 없애면서, 등급별 안내 문구("사진에서 유적지가 확인됐어요" 등)를 프론트엔드가 조립하게 됐다. 그 문구는 미션의 카테고리에 따라 달라진다.
- `primary_category`를 정하는 방법: `places[].matched_preferences[0]`에서 코드로 직접 뽑는다(비어 있으면 `null`). 미션 생성 프롬프트에도 "여러 개면 첫 번째를 주 소재로 삼는다"는 지시가 있어 모델 출력과 대체로 일치하지만, `primary_category`는 그 출력과 무관하게 항상 규칙으로 결정한다.
- `description`엔 의도적으로 인원수를 넣지 않는다. 등록 인원과 실제 참여 인원이 다를 수 있기 때문이다(예: 일정 겹침으로 일부만 참여).
- `description`은 수행할 행동만 담은 담백한 문구다. "지영님이 좋아하는 문화·역사 감성 살려 인증샷 찍기"처럼 선정 근거를 문장에 녹이지 않는다. "그룹 취향 '역사·유적'에서 만들어졌어요" 같은 근거 표시는 화면에서 별도 요소로 붙이며, 그 문구는 해당 장소의 `matched_preferences`를 프론트엔드가 한글 라벨로 변환해 조립한다.
- `matched_preferences`는 문구에 직접 등장하지 않고 **미션의 소재를 정하는 데** 쓰인다(`FOOD`면 음식 사진, `HISTORY_CULTURE`면 건축물·유적 사진 등).

### 입력 (`POST /photomissions/{mission_id}/verify`)

**요청 예시**

```json
{
  "image_url": "https://planit-photos.s3.ap-northeast-2.amazonaws.com/uploads/xyz.jpg?X-Amz-Signature=...",
  "place_id": "ChIJt3t3t3t3t3tRZ3333333333",
  "place_name": "첨성대",
  "place_coordinates": { "latitude": 35.8347, "longitude": 129.2192 },
  "mission_description": "첨성대 배경으로 단체 사진 찍기"
}
```

**타입 정의**

```python
class Coordinates(BaseModel):
    latitude: float
    longitude: float


class VerifyRequest(BaseModel):
    image_url: str
    place_id: str
    place_name: str
    place_coordinates: Coordinates
    mission_description: str
```

- `place_name`이 필요한 이유: 사진 판정 모델에 "목표 장소"로 함께 전달된다. 모델은 이 이름을 보고 사진 속 대상이 그 장소인지(`landmark_confidence`)를 판단한다.
- `place_coordinates`가 필요한 이유: 사진이 찍힌 위치와 비교해, 명백히 다른 곳에서 찍힌 사진을 VLM 호출 전에 걸러내는 데 쓰인다.
- `mission_description`이 필요한 이유: 판정 기준이 "그 장소에 갔는가"가 아니라 "미션대로 찍었는가"이기 때문이다. AI 서버는 DB를 갖지 않아 경로의 `mission_id`만으로는 미션 내용을 조회할 수 없으므로, 백엔드가 요청에 실어 보낸다.
- `place_id`와 경로의 `mission_id`는 현재 판정 로직에 쓰이지 않는다. 백엔드가 어떤 미션·장소에 대한 요청인지 식별하는 값이다.
- `image_url`의 형태: 사진은 S3에 저장되고 백엔드 DB에는 object 키만 남으므로, 백엔드가 요청 시점에 그 키로 presigned URL을 만들어 전달한다.
- `image_url` 검증(SSRF 방지): 허용 목록에 등록한 S3 버킷 호스트에서 온 URL만 받고, 그 외는 422로 거부한다(임의 URL을 그대로 fetch하면 내부망을 스캔당할 수 있는 SSRF 위험이 있기 때문이다). 호스트는 URL 문자열 포함 여부가 아니라 파싱한 hostname으로 비교한다.
- presigned URL은 그 자체가 접근 권한이므로, 만료를 짧게(수 분) 두고 요청 로그에 URL 전체를 남기지 않는다. AI 서버는 요청을 받는 즉시 이미지를 가져오므로 짧은 만료로 충분하다.

```python
class DetectedLabel(BaseModel):
    name: str      # 사진에서 알아본 것 (일반명사)
    matched: bool  # 미션 조건과 관계있는지 — 화면 강조 표시에 쓰임


class VerifyResponse(BaseModel):
    result: Literal["success", "retry", "fail"]
    reason: Literal["location_mismatch"] | None = None
    match_score: float = Field(ge=0, le=100)
    detected_labels: list[DetectedLabel]                    # 빈 배열 허용 (위치 조기 반려 시 빈 배열)
    landmark_confidence: float | None = Field(ge=0, le=100) # 인식 신뢰도가 임계값 미만이면 null
    retry_hint: str | None                                  # retry가 아니면 null
```

- 점수(`match_score`, `landmark_confidence`)는 0~100 범위다. 범위를 벗어난 값은 응답 스키마 검증에서 걸러진다.
- `result`: `match_score`를 임계값과 비교해 코드가 정한다(모델이 등급을 직접 정하지 않는다). 임계값은 평가셋 측정 후 확정한다.
- `reason`: 등급과 별개로 "왜"를 구분한다. `location_mismatch`는 위치가 명백히 불일치해 VLM 호출 없이 조기 반려된 경우에만 채워진다. 일반적인 VLM 판정 결과에는 없다(`null`).
- `message`는 **없앴다.** 기존엔 `"사진에서 유적지가 확인됐어요"`처럼 대상이 고정된 문장을 AI가 반환했는데, AI는 이 미션이 어떤 카테고리(유적/음식/활동 등)인지 모른다 — `verify` 요청에 `matched_preferences`가 없기 때문이다. 반면 프론트엔드는 미션 카드를 만들 때 이미 그 값을 갖고 있다(`photomissions/generate` 응답의 `Mission.primary_category`). 문장 조립에 필요한 재료가 이미 프론트에 있으므로, AI가 문장을 만들어 보냈다가 다시 받는 왕복을 없앴다.
- `detected_labels`/`landmark_confidence`/`retry_hint`: 4단계 파이프라인의 6번 단계(VLM 판정)가 한 번의 호출로 함께 산출하는 값이다. `landmark_confidence`는 임계값 이상일 때만, `retry_hint`는 `result`가 `retry`일 때만 노출된다. 각 필드의 의미는 4단계 "프롬프트" 절 참고

## ✅ 해당 API가 서비스 전체 구조에서 차지하는 역할과 연동 관계에 대한 설명

### 서비스 구조에서의 역할

```
[프론트엔드] → [백엔드 서버]  --(내부 API, 위 엔드포인트)-->  [AI 서버]
                    ▲                                    │
                    │ (2) 영업시간 배치 조회                 │
                    │  Phase 4: /internal/places/       ▼
                    │  opening-hours:batchGet         [LLM Provider]
                    └──────────────────────────────   [지도/장소 API] (1) 후보 검색
```

백엔드는 여행방·설문 데이터를 모아 위 입력 스키마로 변환해 AI 서버를 호출하고, 응답을 그대로 저장했다가 프론트엔드에 전달한다. AI 서버는 사용자에게 직접 노출되지 않는 내부 서비스이며, 백엔드-AI 서버 간 통신은 Bearer 토큰으로 인증한다.

**호출 방향이 한 곳에서 뒤집힌다.** `/trips/generate` 처리 중 AI 서버는 (1) 지도 API로 후보 장소를 실시간 검색한 뒤, (2) 후보들의 영업시간을 확인하려고 백엔드가 제공하는 Phase 4 조회 API(`/internal/places/opening-hours:batchGet`, 장소 영업시간 데이터 파이프라인 문서 참고)를 호출한다. 이 지점만 AI→백엔드 방향이라, 백엔드가 API를 설계할 때 "우리도 AI 서버로부터 호출을 받는 엔드포인트가 하나 있다"는 걸 알고 있어야 한다.

### 호출 예시 (`POST /photomissions/generate`)

아래는 로컬 서버에서 실제로 호출한 결과다(2026-09-18). 무료 할당량 제한으로 운영 모델(`gemini-3.1-pro-preview`) 대신 `gemini-3.1-flash-lite`로 생성했다.

```bash
curl -X POST http://127.0.0.1:8123/photomissions/generate \
  -H "X-Internal-Token: <internal-service-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "itinerary_id": "it1",
    "places": [
      {
        "id": "p1",
        "displayName": { "text": "첨성대", "languageCode": "ko" },
        "selected_for": ["u1"],
        "matched_preferences": ["HISTORY_CULTURE"]
      }
    ]
  }'
```

**실제 응답 (HTTP 200)**

```json
{
  "missions": [
    {
      "mission_id": "ms_8a16b4083680",
      "place_id": "p1",
      "description": "첨성대의 곡선과 쌓아 올린 돌의 질감이 잘 보이게 정면 담기",
```

### 호출 예시 (`POST /photomissions/{mission_id}/verify`)

```bash
curl -X POST https://ai.planit.internal/photomissions/ms_8a16b4083680/verify \
  -H "X-Internal-Token: <internal-service-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "image_url": "https://planit-photos.s3.ap-northeast-2.amazonaws.com/uploads/xyz.jpg?X-Amz-Signature=...",
    "place_id": "p1",
    "place_name": "첨성대",
    "place_coordinates": { "latitude": 35.8347, "longitude": 129.2192 },
    "mission_description": "첨성대의 곡선이 잘 보이게 사진 찍기"
  }'
```

아래 두 응답은 팀원이 경주에서 직접 찍은 사진으로 판정한 실제 결과다(2026-09-22, `gemini-3.1-flash-lite`). 모델이 낸 판정값을 실제 등급 변환·응답 조립 코드에 넣어 만든 응답이며, 임계값은 측정 전 임시값(success 70 / retry 40 / 랜드마크 노출 60)이다.

**실제 응답 — 첨성대 야간 사진 (HTTP 200)**

```json
{
  "result": "success",
  "reason": null,
  "match_score": 90,
  "detected_labels": [
    { "name": "유적", "matched": true },
    { "name": "조명", "matched": false },
    { "name": "야경", "matched": false }
  ],
  "landmark_confidence": 100,
  "retry_hint": null
}
```

**실제 응답 — 동궁과 월지 사진을 첨성대 미션에 제출 (HTTP 200)**

```json
{
  "result": "fail",
  "reason": null,
  "match_score": 0,
  "detected_labels": [
    { "name": "정자", "matched": false },
    { "name": "연못", "matched": false },
    { "name": "야경", "matched": false }
  ],
  "landmark_confidence": null,
  "retry_hint": null
}
```

두 장소가 1km도 떨어져 있지 않아 위치 조기 반려(5km)로는 걸러지지 않지만, VLM이 사진 속 건물이 첨성대가 아님을 알아보고 0점을 줬다. 위치 판정은 멀리서 찍은 사진을, VLM은 가까운 다른 장소의 사진을 거르는 역할로 나뉜다.

**에러 응답 (HTTP 422 — `image_url`이 허용 호스트 밖)**

```json

}
```

### 오류 처리 / 인증

- 인증: 서비스 간 호출이므로 사용자 로그인 토큰이 아닌 별도 내부 서비스 토큰(Bearer)을 사용한다.
- 입력 검증: Pydantic 스키마로 검증, 실패 시 422 + 필드별 에러 메시지
- LLM 응답 파싱 실패: 내부적으로 재시도(최대 N회) 후에도 실패하면 500 + 재시도 안내
