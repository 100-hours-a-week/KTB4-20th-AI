# 장소 선정 모델 용어집

작성일 2026-10-18. 이 프로젝트의 장소 선정(trips `/trips/place-selection`)에서 쓰는 키워드와 정의를 모았다. 새 세션이나 새 팀원이 대화 맥락 없이도 각 말이 무엇을 가리키는지 알 수 있도록 하는 것이 목적이다. 설계 이력은 `docs/trips/place-selection-evolution.md`, 결정의 근거는 `docs/adr/`의 ADR-0000, 0002~0006에 있다.

## 1. 전체 흐름 한 줄

장소 ID → 코드 → 토큰 → (트라이 + 모델 입력) → 로그확률 → 빔 서치 → 1위 선택 → 문맥에 추가 → 다음 슬롯. 오프라인에서는 여행로그와 장소 임베딩으로 코드와 모델을 만들고, 온라인에서는 후보 필터링 → 모델 추론 → 폴백 순서로 응답한다.

## 2. 기존 규칙 방식

- **규칙 경로 (ADR-0000)**: LLM 없이 설문 점수와 DB 조회로 장소를 고르는 기존 방식. 현재 운영 기본값이다.
- **그룹 취향 점수 (ADR-0002)**: 구성원별 카테고리 점수 평균에서 표준편차×0.5를 뺀 값. 규칙의 슬롯 카테고리와 모델의 취향 상위 2개를 정한다.
- **슬롯 계획**: 하루 장소 5~6곳의 자리 배치. 1·3번째는 취향 1위 카테고리, 4번째는 2위, 2·5번째는 FOOD, 조건 충족 시 6번째는 야간형 ACTIVITY.
- **규칙 점수**: `평점 × 0.6 + log(평가 수 + 1) × 0.4`. 규칙이 후보를 줄 세우는 기준이며 모델의 선택에는 쓰이지 않는다.
- **방식 A (카테고리 보충)**: 한 카테고리 후보가 모자랄 때 다음 순위 카테고리에서 순차로 채우는 규칙. 모델 경로도 같은 취지로 후보 합집합에 다음 순위를 더한다.
- **품질 필터**: 영업 중(`OPERATIONAL`), 평점 3.0 초과, 평가 수 10 이상. 장소 DB 10,165곳 중 6,206곳이 통과한다.
- **hex grid**: 장소를 사전 수집한 지역 격자. DB 조회는 격자 중심점 반경 안의 장소만 가져온다(ADR-0001).
- **회피 type 제외**: 회피 조건(예: 야외 활동 회피)에 해당하는 Google place type을 후보에서 빼는 것.

## 3. 데이터와 정답

- **AI-Hub 국내 여행로그**: 학습 데이터. 서비스 사용자 설문·행동 로그가 없어 대신 쓴다. 서비스 5개 지역(서울, 부산, 경주, 전주, 제주)만 사용한다.
- **하루 시퀀스**: 한 여행자의 하루 방문 순서. 서비스가 5~6곳을 만들어 로그의 앞 6곳까지만 쓴다. 학습 가능한 하루는 12,870일.
- **정답 신호**: 만족도·재방문 의향·추천 의향이 모두 4 이상인 방문만 정답으로 쓴다.
- **취향 입력(학습)**: 여행 미션 코드를 카테고리 4개(역사·문화, 자연·힐링, 액티비티, 편의·쇼핑)의 0/1로 바꾼 값. 방문 행동으로 만들면 정답이 입력에 새어 들어가서(누수) 쓰지 않는다. FOOD는 대응하는 미션 코드가 없어 제외한다.
- **대응 (방문지 ↔ DB 장소)**: 로그 방문지를 이름 임베딩이 가장 비슷한 DB 장소에 연결하는 것. 유사도 0.607 미만이면 DB 범위 밖으로 보고 정답에서 뺀다(앞 문맥에만 쓴다).
- **여행자 단위 분할**: 학습 70% / 개발 15% / 최종 15%. 같은 여행자가 두 몫에 걸치지 않게 나누며 시드는 20261015.
- **최종용 (final)**: 모델을 고치는 데 쓰지 않고 한 번만 여는 평가용 몫. 2026-10-16에 슬롯 제약이 없는 조건으로 한 번 열었고 다시 열지 않는다.
- **개발용 (dev)**: 모델 선택과 조건 비교에 쓰는 몫.

## 4. 장소를 코드로 바꾸기

- **임베딩 (BGE-M3)**: 장소 텍스트(정규화한 이름 + 시도·시군구, 카테고리 라벨 없음)를 1024차원 벡터로 바꾸는 오픈 모델(MIT).
- **RQ-VAE**: 임베딩을 3단계로 나누어 양자화하는 모델. 단계마다 256종 코드를 부여해 비슷한 장소가 앞 단계 코드를 공유하게 한다.
- **Semantic ID (코드)**: 장소를 의미 기반 코드열 `(c1, c2, c3, n)`로 표현한 것. 모델은 장소 이름이 아니라 이 코드를 생성한다.
- **구분 번호 `n`**: 세 단계 코드가 같은 장소끼리 구분하려고 붙이는 번호(최대 묶음 5).
- **코드 사전**: 장소 `google_place_id` ↔ 코드의 일대일 표(10,165곳). 모델 가중치와 같은 버전이어야 한다.
- **코드 일치율**: 같은 장소로 판정된 로그 방문지와 DB 장소가 같은 코드를 받는 비율(첫 단계 89.7%, 앞 3단계 69.0%). 장소 정렬이 잘 되었는지 보는 지표.
- **서빙 묶음 (bundle)**: 배포하는 모델 파일 `model.onnx`와 코드 사전 `codes.json`의 한 쌍. 해시로 짝을 고정한다.

## 5. 모델과 디코딩

- **토큰 / 어휘**: 모델 입력의 최소 단위. 어휘 791종: 패딩·시작 2, 취향 8, 지역 5, 코드 768(3단계×256), 구분 번호 8.
- **헤더 토큰**: 문맥 맨 앞의 6토큰. 시작 토큰 1개, 취향 4개(0/1), 지역 1개. 서비스는 취향 상위 2개 카테고리만 1로 둔다.
- **문맥 (context)**: 모델에 넣는 토큰열 전체. 헤더 + 앞에서 고른 장소들의 코드 4토큰씩.
- **소형 트랜스포머**: 사전학습 없이 처음부터 학습한 디코더 모델. 채택 모델 3.37M 파라미터(차원 256, 4층, 드롭아웃 0.2). 비교한 큰 모델은 10.96M.
- **개발 손실 / 조기 종료**: 개발용 몫에서 다음 코드 토큰을 맞히는 정도(교차 엔트로피)와, 이 값이 더 안 내려가면 학습을 멈추는 방식. 두 모델 비교에 쓴 유일한 지표.
- **autoregressive 생성**: 앞에서 낸 토큰을 문맥에 이어 붙여 다음 토큰을 내는 방식. 장소를 4칸으로 만들고, 슬롯도 앞 장소를 이어 붙여 다음 장소를 만든다.
- **다음 토큰 로그확률 (`log_softmax`)**: 모델의 출력. 문맥 마지막 위치에서 어휘 전체 791종 각각의 로그확률.
- **트라이 (prefix tree)**: 후보 장소의 코드 4토큰 경로를 나무로 묶은 구조. 후보가 곧 허용 경로이다.
- **제약 디코딩**: 트라이가 허용한 토큰의 확률만 읽어 후보 안에서만 고르는 방식. 허용 토큰끼리 확률을 다시 정규화하지는 않는다.
- **첫 장소 무작위 (`first_k`, `seed`, ADR-0007)**: 첫 슬롯만 빔 서치 상위 `first_k`(기본 30, 상한 100)곳 중 시드로 하나 고르는 방식. 시드는 요청 본문 JSON의 SHA-256 앞 15자리라 같은 요청은 같은 결과다. `first_k=1`이면 이전 동작. 나머지 슬롯은 이 장소를 문맥에 붙여 결정론적으로 생성한다.
- **빔 서치 / 빔 폭**: 칸마다 누적 점수가 높은 앞부분(prefix)을 빔 폭 개수(기본 10)만 남기며 4칸을 채우는 탐색. 후보 전체를 정확히 줄 세우지 않는 근사이다.
- **장소 점수**: 코드 4토큰의 로그확률 합. 점수가 같으면 토큰 번호가 작은 쪽이 앞이라 같은 입력의 결과는 같다(결정론). 첫 장소만 예외로 ADR-0007에서 상위 K곳 중 시드 무작위로 고른다.
- **후보 제한 (슬롯별 후보 목록)**: 슬롯마다 모델이 고를 수 있는 장소 ID 집합. 2·5번째는 FOOD, 6번째는 야간형 ACTIVITY, 나머지는 취향 상위 2개 카테고리의 합집합(ADR-0006).

## 6. 평가

- **Recall@k**: 실제 다음 방문 장소가 추천 상위 k곳 안에 있는 비율. 합격 지표는 Recall@10 하나이고 분모는 DB에 대응된 모든 정답 방문(품질 필터 통과 여부와 무관).
- **teacher forcing**: 평가에서 문맥에 모델이 고른 장소가 아니라 실제 앞 방문(정답)을 넣는 방식. 서비스는 모델 선택을 넣으므로 평가가 더 후한 조건이다.
- **기준선**: 비교 대상. 규칙(슬롯 카테고리 안에서 규칙 점수 순)과 인기순(지역 후보를 규칙 점수 순).
- **비열세 검정 / 마진**: 모델이 규칙보다 나쁘지 않은지를 신뢰구간으로 판정. 마진은 개발용 규칙 기준선 Recall@10의 10%(0.245%p). 하한이 −마진 위면 통과, 걸치면 보류, 상한이 아래면 불합격.
- **여행자 단위 묶음 부트스트랩**: 같은 여행자의 방문은 독립이 아니므로 여행자를 단위로 다시 뽑아 신뢰구간(95%)을 구하는 방식.
- **상한**: 정답 장소가 후보 안에 들어 있는 비율. 어떤 방법도 이 값을 넘을 수 없다(서비스 조건 20.0%).
- **평가 조건**: 같은 모델을 후보 제한만 바꿔 잰 네 가지(개발용 Recall@10). `free`(제약 없음 13.4%), `food-slots`(FOOD 슬롯만 제한 9.3%), `top2-slots`(FOOD 외 슬롯을 취향 상위 2개로 제한 5.9%, 서비스 채택), `rule-slots`(규칙의 슬롯 카테고리 고정 4.2%).
- **서비스 조건**: 평가 조건 중 실제 서비스와 같은 `top2-slots`.
- **불변식 (invariant)**: 결과가 항상 지켜야 하는 네 가지. 5~6곳, 2·5번째 FOOD, 회피 type 없음, 장소 중복 없음. 7,680건 조합 테스트(지역 5 × 회피 조건 부분집합 × 대표 설문)로 확인한다. 첫 장소 무작위(`first_k=30`)를 켠 상태에서도 위반 0건(2026-10-18).
- **일정 단위 지표**: 생성한 일정의 질. 취향 일치(FOOD 외 추천이 취향 상위 2개에 속하는 비율), 연속 장소 거리, 서로 다른 장소 수, 상위 1% 장소 점유율.

## 7. 서빙과 운영

- **ONNX / onnxruntime**: 학습한 모델을 프레임워크와 무관한 파일로 내보낸 형식과 그 실행기. PyTorch와의 출력 오차는 2.4e-5.
- **RunPod Serverless 엔드포인트**: GPU 컨테이너를 요청이 올 때 띄우는 서비스. 장소 선정 모델 전용 엔드포인트가 따로 있다(포토미션 VLM과 분리).
- **워커**: 엔드포인트가 띄운 컨테이너 한 개. `Active`는 상시 워커 수(0), `Max`는 최대 수(현재 0으로 일시 정지, 이미지 v2).
- **`/runsync`, `/health`**: 요청을 동기로 보내는 호출, 워커와 요청 수를 읽는 조회(과금 없음). `jobs.completed` 증가로 GPU 경로 사용을 확인한다.
- **콜드 스타트 / 따뜻한 상태**: 워커가 내려가 있다가 첫 요청에 다시 뜨는 지연(RTX A4500에서 약 10~13초)과, 워커가 떠 있을 때의 지연(총 약 1.3초).
- **Idle timeout**: 마지막 요청 뒤 워커를 유지하는 시간(현재 5초). 늘리는 중간안은 ADR-0004 대안 5.
- **GPU 우선 / 폴백**: 기본 경로는 RunPod GPU, 실패하면 CPU 경로(AWS에는 배포하지 않는 가정), 그다음 규칙 경로.
- **서킷 브레이커**: GPU 호출이 연속 3번 실패하면 60초 동안 GPU를 부르지 않는 장치. GPU 호출 제한은 20초.
- **`rule_fallback`**: 모델 경로가 실패하거나 5곳 미만이어서 규칙 경로로 응답한 경우.
- **`PLACE_SELECTION_MODE`**: 제거된 환경변수(ADR-0010). 이전에는 `rule`(기본) 또는 `model`로 2·3안을 만드는 방법을 갈랐다. 지금은 2·3안을 항상 모델 경로로 만들고, 모델이 실패한 안만 규칙 변형으로 채운다. 모델 경로에는 `RUNPOD_MODEL_URL`, `RUNPOD_MODEL_API_KEY`가 필요하고 `MODEL_DIR`은 비운다. `.env`에 이 키가 남아 있으면 설정 로딩이 실패한다.
- **GPU 세대 고정**: 최신 세대 GPU는 현재 이미지(CUDA 12.4)에서 첫 요청이 43~48초라, 엔드포인트를 Ada·Ampere 16GB 그룹으로 고정했다.

## 8. 산출물과 문서

- **`$AIHUB_ROOT/derived/semantic_id/v1/`**: 학습·평가 산출물 위치(레포 밖, 여행자 ID·좌표 포함). 구조는 `m1/`(분할·하루 시퀀스), `m2/`(임베딩·RQ-VAE·코드 사전), `m3/`(모델·서빙 묶음·평가 결과), `experiments/`.
- **`MANIFEST*.json`**: 산출물 파일별 sha256. `manifest --verify`로 변경 여부를 확인한다. 기존 MANIFEST는 덮어쓰지 않고 새 파일만 새 MANIFEST에 추가한다.
- **ADR**: 아키텍처 결정 기록. ADR-0000(규칙, 대체됨), 0003(Semantic ID 모델), 0004(서빙), 0005(학습·평가), 0006(슬롯 후보 제한), 0007(첫 장소 무작위). 모두 Accepted.
- **핸드오프 (`.grill/handoff-semantic-id.md`)**: 세션 시작 때 먼저 읽는 현재 상태 요약.
